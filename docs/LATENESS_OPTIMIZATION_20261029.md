# 入库背压与期限优化：实现、结果和使用方法

日期：2026-10-29。本文承接[扩仓与三型号交付](MEETING_DELIVERY_20261028.md)，说明100×90m候选中23项晚点的原因、尝试过的方案和本轮保留的可选策略。

## 1. 本轮做了什么

我们逐条还原了23项晚点任务的完整生命周期，确认主要等待发生在入库口准入前。随后比较入口疏通奖励、期限准入、取货距离感知和在线取货节拍预测，保留表现较好的 **online 疏口候选**，通过配置显式启用。

固定对照保持以下条件：100×90m、40架1920位，100台机器人按A1/R2/X3=15/15/70配置，速度0.8m/s，取货10秒、放货12秒，每个入库口6件暂存。1728项任务在一小时内发布，864件初始库存；允许发布结束后排空，原任务ID、位置、发布时间、截止时间和全部安全检查保持。

**选中的online候选全部完成1728项，晚点由23项减到5项，平均流转472.48→454.80秒，P99流转1125→1005秒，排空4419→4328秒。零晚点目标尚未达到。** 本轮没有把该策略部署到正在使用的14186或14188，默认仍为fifo/off；启用候选需要另开新run。

## 2. 为什么晚点：入口的6个位置被占住了

一个入库任务依次经历：

```text
task_released：货到入口外，任务已公开
received：目标货位可用、仓内有容量、入口有空暂存位，货进入仓库
ready / assigned：成为可执行任务，分配机器人
picked：机器人实际拿起货，入口暂存位才释放
placed：货物实际放入货架，任务完成
```

对原23项晚点，完整journal逐事件重建得到：

- 全部是INBOUND，其中IN-8有20项、IN-1有3项。
- 发布到准入平均938.09秒；共21576任务秒等待，全部且仅由对应端口已满6件造成。
- 这23项等待期间，目标货位占用/预留、仓库总容量不足均未构成阻塞。
- 准入后等ready平均3.17秒，ready后等分配平均0.70秒；分配到拿起货仍平均101.74秒，随后到完成平均117.74秒。
- 这些尾部任务自身派单很快；此前货物在暂存位停留过久，延误逐渐传到队尾。全部入库任务在不同入口平均等派75—106秒，再等101—117秒到取货。

### 一个具体例子

`V3-T-0000888`在IN-8：1863秒准入，2165秒才分配，2351秒实际取走。它占住一个暂存位**488秒**，其中302秒等分配、186秒等机器人到达和取货。它在2525秒完成，早于自身2835秒期限；后面的紧任务却一直等这个位置空出来。

这类似一个只有6个取餐格的窗口：格中某份餐不着急，后方新餐却放不进来。调度器需要把“后方队列快来不及”的信息传给正在占格的取货任务，尽早让机器人把货拿走。

归因校验包含9102条连续事件、完整批checksum、23项各自唯一的发布/准入/分配/取放记录。逐事件端口始终0—6件，仓内始终0—1920件，实际仓内峰值936件。单任务无拥堵运输下界没有直接超过期限的个案；这仅排除单任务显然不可能的情况，全局按时能力仍靠实际执行验证。

## 3. 保留的可选策略如何工作

### 3.1 将后方紧迫度传给正在占口的货物

`backend/scheduling_v5/port_relief.py`只查看**已经发布**的任务。某waiting入库任务仅因源端口满6件而等待，且目标货位和仓库容量均可用时，才给同口已准入的入库任务提供临时疏口优先级。

任务原始`due_second`、状态和货权不被改写。匹配成本加入取货点ETA的额外权重，偏向更快到达入口的机器人；能力禁配、failed-pair、SOC、目标预留及连续避碰仍由原链检查。优先级只帮助选择可行任务，不会把不可行任务强行执行。

### 3.2 用过去实际取货节拍预测队列风险

online版本从已发生的`received_at / picked_at`重建各口历史。相邻两次取货之间，后一次货在前一次取货时已经准入，才把这个间隔视作有货等待时的服务间隔。对最近最多12个有效间隔取中位数；没有样本时回退到取货10秒；估计值限制在10—60秒。

将队列按期限密度排列后，用这个服务节拍估计后方任务能否及时轮到入口，提前疏通有风险的口。它使用过去实际事实，包含当时空驶、交通等影响；这是**有界预测**，不能当成物理可行性的必要或充分证明。历史可以由检查点中的实际任务事实重建，无需读取未来CSV计划。

### 3.3 默认与探索项

- `inbound_admission_policy="fifo"`、`port_relief_policy="off"`保持默认行为。
- 本轮选中配置保持FIFO准入，显式启用`port_relief_policy="deadline"`，采用online节拍预测的冻结代码。
- EDF按任务截止时间排序准入也做了独立对照。
- LST按“截止时间减去静态运输与取放时长”的最迟开始时刻排序准入，仅作为研究对照。LST及online+LST组合没有胜过online，**未纳入本轮选中配置与接口**。

## 5. 运行方法与接入位置

选中冻结源的完整Python回归为758项，751通过、7项可选跳过，真实退出码0。新机制的能力、禁配、容量、发布边界、AST副本和恢复测试保留在测试集中。最终集成与Git提交由本轮收尾记录确认。

配置入口是`--config-json`。完整配置文件为 `config/warehouse-balanced-port-relief.json`，包含机队、能源、交通、速度等原有参数及显式疏口开关；不要把只有两个开关的片段当作这次实验的完整配置。

```bash
bash run_in_lade.sh python -m backend.warehouse validate \
  --scene data/layouts/expansion-candidates/balanced/layout.json \
  --dataset /absolute/path/to/balanced-dataset

bash run_in_lade.sh python -m backend.warehouse run \
  --scene data/layouts/expansion-candidates/balanced/layout.json \
  --dataset /absolute/path/to/balanced-dataset \
  --config-json config/warehouse-balanced-port-relief.json \
  --output /absolute/path/to/new-run --run-id unique-port-relief-run \
  --mode rules --knowledge-backend journal --commit-seconds 300 --frames
```

`/absolute/path/to/balanced-dataset`应使用对应地图SHA与位置表。用于纯物理策略对照时可显式使用rules+journal；真实历史授权使用`--mode required --knowledge-backend neo4j --resource-graph`及独立数据库。两类验证范围分别报告。

## 6. 来源身份、恢复和部署

运行来源由**全backend SHA、完整Config/配置SHA、输入SHA、run-id和冻结目录**共同描述。单独的V5`execution_sha`没有包含全部新开关，不能拿它区分同源不同配置。完整Config和源校验仍会拒绝跨配置/跨源码检查点恢复。

旧检查点使用旧冻结源和原配置恢复；新策略另开新run。没有把旧运行中途切换到新策略，也没有覆盖旧回归产物。正式14186与候选预览14188在本轮保持原服务和原策略。
