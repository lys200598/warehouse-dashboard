# 仓库 v3：冻结设计范围与验证契约

日期：2026-10-27。

**本文固定模型、接口、恢复策略与验收口径，不是远程实验成功报告。** 对具体运行是否通过，应读取对应目录的 `results.json`、日志、检查点和图谱审计；不同代码版本不得混用结果。100 台同时工作、100 个执行进程、百万级当前运行图谱及延迟联合指标，未在本文中宣布通过。

## 任务背景

用户侧负责仓库布局与运行算法，同学负责数据集生成。目标是形成足以支撑知识图谱实验的可信二维仓库仿真底座，而不是完成 LLM、SLAM、双足接触物理或商业车队协议。

前置原则：**不把正常调度造成的无路可退称为允许的“物理不可恢复”；布局和准入预防优先，异常恢复其次。** 同时明确故障覆盖范围，不承诺任意地图、任意数量机械故障或任意永久封路条件下仍能完成所有原任务。

## 关键结论

- v3 继续使用原 60×48m 地图、1728 货位、100 个停车位、24 个充电位和 16 个边界取放口，未为了跑通而删除机器人或缩小身体。
- 正常交通以完整时空预约和真实私有停车位安全尾段为主要预防手段；任务续接成功后才替换尾段。它不是任意问题上的完备多车最优求解器。
- 临时延迟采用有限冲突组件统一顺延；有限停车优先绕行/重排必要尾段，再使用明确的同步等待回退。所有方案先验证，成功后原子替换。
- 互助是两个实体机器人在静态合法且动态预约的相邻位置服务，完成后再转移唯一货物持有者；不是货物瞬移，也不模拟修好故障机器。
- 持久停车保留实体障碍和故障状态；无货后可按明确的断能隔离假设停止耗电。它不会自己修好或从地图上消失，重新启用必须显式外部 `clear_fault`。
- 多日输入契约最多 7 天，数据验证只证明文件身份、字段和逻辑依赖等条件，不代替真实运行容量/时限/交通验证。
- 接近真实的研究模型仍是有范围的简化：固定速度和身体包络、秒边界扰动、参数化能耗/装卸时间；不以这些实验替代实际机器人安全控制验证。

## 修改内容：冻结设计契约

### 1. 空间与货物模型

| 项目 | 约定 |
|---|---|
| 坐标与时间 | 米、秒；ISO8601 明确时区，与 manifest 起点一致 |
| 地图 | `warehouse100-v1.json`；原始 SHA-256 `744e69309c86d9ad5589805a0f5a7e04bd32347ce5f374afaa9efbf731816960` |
| 机器人 | 100 个持续存在的实体状态，0.7×0.7m 载货矩形由半径 0.55m 圆包络覆盖 |
| 机器人之间 | 连续扫掠距离至少 1.1m，非仅端点或稀疏采样避碰 |
| 路网 | 原 0.2m 静态几何上的 0.8m 骨架，带停车/充电精确进出连接 |
| 货架/搬运 | 36 架×48 货位；单机器人一次一件；机器人自行取放，无额外有限加工设备 |
| 边界 | 8 入库取货口、8 出库交付口；入库口每口暂存最多 6 件 |
| 容量 | 总在仓货物最多 1728，含入库暂存及在途未出界货物；运行时以实际状态门禁 |
| 出库 | 实际完成出库交付后出界，不增加业务订单/车辆装车系统 |

默认移动速度 0.8m/s、拾取 10s、放置 12s、相邻交接 10s。它们是仿真参数，不是某款实机的测量值。尚无加减速、制动距离、臂部接触或跌倒模型；秒边界停车是执行契约，不是实机紧急制动保证。

### 2. 布局审计的通过范围

完整布局审计文件：

`C:/E/projects/warehouse/research/scheduler-v3-layout-20261027/audit-reproducible-full.json`

- 1868 个位置 ID 初始可达；公共图 2976 节点、5582 条无向边、割点 0、桥 0。
- 所有停车/充电中心之间满足 1.1m 分离；其静止占用不侵入公共路网边。
- 3642 个去重停障碍探针覆盖全部路网节点中心及端点接近中心，避让相对半径 1.1m。未发现未被直接覆盖的业务端点被间接隔离。
- 12 个探针让一个无业务端点的边角节点脱离主图；340 个探针间接遮住停车或充电入口，最多 4 个端点。对这些局部不可用资源必须等待、换可达资源或受控降级，不能虚报全端点始终通达。
- 576 个货架地面接近位置加 16 个口，592/592 存在静态相邻交接候选。不同货架层可能共用地面点，计数不能变成可同时叠放的作业机器人。

**特别边界：**如果持久停车恰好覆盖唯一业务目标的合法作业空间，该目标可能暂停，甚至在清障前无法完成其任务。这不授权让货物穿过故障车；也不能从有限探针推导任意中途位置或多车故障必定可恢复。

### 3. 正常派单与交通预防

1. 按截止风险、等待年龄、路网预计时间等构造代价，批量匹配当前候选任务和机器人。
2. 实际提交前依次规划取货、交付及回私有停车位尾段，并检查取放停留、已有轨迹与能耗。
3. 某个机器人—任务组合失败后，短期屏蔽失败组合，同批有限次数重新匹配；失败任务回退，避免一直占据候选队列头。
4. 续接任务必须从实际已到达位置开始；新任务和安全尾段全部验证通过后才替换原返程。失败继续原有可执行返程，不无限停在公共作业点。

正常执行下完整预约使已提交车流具有明确释放计划，避免只占有局部路段又无退路地相互等待。**这不是全局完备性证明，也不保证任意待派任务最终可行或全部准时。** 有界 SIPP 搜索、有限候选、有限优先级重排都可能保守失败。

### 4. 延迟与有限停车

| 接口 | 范围与行为 |
|---|---|
| `inject_delay(owner, seconds)` | 活动车辆、非已故障；1–600 整数秒；冲突组件统一插入真实等待，再平移剩余轨迹 |
| `inject_stop(owner, seconds)` | 活动车辆的有限停车；1–3600 整数秒；优先绕行受影响尾段，必要时尝试明确的同步组件等待 |
| `_coordinated_replan` | 保留不受影响交通，对影响组尝试几种有界优先级顺序，未规划成员保持真实静止占用 |
| 原子替换 | 所有变更车辆首位置等于实际位置，时间/空间连续，检查新新、新旧轨迹关系；整组成功才提交 |

延迟会检查恢复所需电量，充电车辆的延迟等待仍按充电处理。成对交接时同步考虑 donor/receiver，不能单独修改一辆而丢失交接时刻。

若注入请求无法构造已验证的恢复事务，接口返回失败；实验 runner 将此场景标为未通过并停止，不悄悄跳过，也不继续沿冲突轨迹运行。有限停车结束是预先声明的故障持续时间结束，不等于模拟系统自行完成机械维修。

### 5. 持久停车、隔离与外部清除

`inject_stop(owner, None)` 表示持续存在的驱动故障：

- 车体留在实际位置，持久静止占用保留；不是删车、瞬移回停车位或在规划时忽略它。
- 未取货任务可重新排队，已取货任务保持唯一持有者，尝试有条件相邻接力。
- 若故障车仍持货，等待/交接消耗仍按模型计入。货物交出、无货且仍持久故障时，可以按**断能隔离**假设不再扣待机电；身体仍然是障碍。
- 断能不修复驱动，不让车自己走去充电。只有显式外部 `clear_fault(owner)` 并完成新的安全规划，才能重新启用。
- 持久占用使用远超 7 天契约的数值终点和专用静止障碍表示，不能按每 8 秒展开巨量预约桶。其长时间查询实现的修复/性能须由最终代码对应测试确认，不因数据结构设计声明就自动判为已通过。

对已经停住且彻底堵住唯一目标的故障，允许准确报告局部服务不可用；不承诺算法修复硬件或凭空创造道路。但正常调度不应主动把多个正常机器人送进无合法释放/撤离空间的困局。

### 6. 电量与互助

默认 `transport-assumed-v1`：

| 行为 | 净 SOC 变化假设 |
|---|---:|
| 空载移动 | 每小时消耗 15 个百分点 |
| 载货移动 | 每小时消耗 18 个百分点 |
| 取放/交接 | 每小时消耗 18 个百分点 |
| 等待/待机 | 每小时消耗 2 个百分点 |
| 充电到 80% | 每小时净增加 60 个百分点 |

另有旧参数与更高耗电/更慢充电的敏感性 profile；均标记 `hardware_calibrated=false`。超过 80% 可有分段减速，默认目标恰为 80%。默认临界补能阈值 35%、机会补能 55%、任务余量 20%、硬应急余量 10%，互助阈值 25%。

业务准入会检查任务完整尾段以及当前可规划的后续到充电位路线、预计等待和附加队列余量；后续充电可达性检查**不是当场替该业务锁定一个无限期未来充电位**。实际充电仍需独立安全预约，不将预计机会说成绝对保证。

相邻接力需要：

1. donor 确实携带该任务货物，receiver 空载且电量允许。
2. 两车位置合法、中心间距满足包络分离且在交接可达范围，receiver 真实行驶到相邻位置。
3. 两车共同服务时长完整保留，receiver 的后续交付/逃生及移动 donor 的补能尾段可行。
4. 完成标记时原子转移任务责任和唯一货物持有者，记录 `cargo_handoff`；原任务不能完成两次。

低 SOC 测量校正属于显式外部扰动，事件保留旧值和新值。互助/补能无法安全构造时必须暂停并报告失败，不通过悄悄抬高电量完成实验。若代码仅对部分阈值触发恢复，不据此扩大为“任意测量校正均已验证安全”；最终版本行为以测试和代码身份为准。

### 7. 进展诊断与恢复边界

持续记录实际移动、取放等进展，并保留任务年龄、失败类别与阻塞 owner。等待环只是候选；需结合重复观测、新鲜依赖、无实际进展和预计释放时间判断，不能看到一次环就强迫倒车。

当前实现的有界局部重排是一种恢复尝试，不是对全部死锁的完备求解器。正常完成充电和明确预约等待不等同于死锁；一小时窗口结束时正在携货的任务也不应算成永久堵塞。

### 8. 数据集交接：最多 7 天

任务 CSV 保持七字段：

```text
task_id,task_type,goods_id,release_time,due_time,source_id,target_id
```

输入需有初始库存和 manifest，并核查：

- 地图和两个输入 CSV 的 SHA-256、字段数、行数及任务数一致。
- 明确时区、整数秒精度；释放时刻在输入时域内，截止晚于释放；最长 604800 秒。
- 货物/任务 ID 合法且不重复；IN/OUT 端点类型正确，入出货物依赖与参考库存容量有效。
- CSV 不固定机器人 ID、充电阈值或接力决策；这些属于运行算法。

已有生成器支持均匀、峰值、局部热点与持续随机间隔场景。各场景总需求量可能不同，不能直接把吞吐差异归因于算法。参考释放顺序的库存重放，只验证逻辑关系；实际货位释放、在仓容量、暂存门禁和期限仍由运行验证。

### 9. 日志、图谱与可重复性

- 业务事件与状态经 Journal 持久化，图谱为幂等镜像；重放必须验证校验和，旧提交不能回退当前货物位置。
- 交接关系显式连接 `WHEvent` 到 donor、receiver、task 和 cargo；货物历史仍由父镜像写一次，不重复制造 custody。
- 延迟/绕行/停车等事件保留原因、受影响车组及完整 payload。图谱协作审计从唯一 `WHRun` 索引锚定，不以全库扫描增加超时来掩盖问题。
- 检查点恢复核对配置、输入和代码身份；不同源代码版本不能直接冒充同一次可重复恢复。
- 旧实验、失败结果、原网页服务和基线应保留。独立 CLI 能运行不等于用户网页已经切换到 v3。

## 后续建议：统一验证矩阵与停止条件

以下是验收要求，不是本文件声称已完成的实验清单：

| 层级 | 必须验证的内容 | 不可偷换的口径 |
|---|---|---|
| 基础几何 | 端点/包络/静止泊位/有限故障探针 | 图连通不代替动态恢复 |
| 事务与执行 | 连续避碰、失败不擦除旧路线、恢复不瞬移 | 计划可行不代替实际执行审计 |
| 业务与能量 | 库存/持有者守恒、真实充电、相邻接力、低电失败保留现场 | 增加充电位或免费补电不算算法收益 |
| 持久故障 | 车体长期保留，其他车合理绕行/降级，显式外部清除 | 不把自动删除车或静止断能说成维修完成 |
| 多场景长时 | 均匀/峰值/热点/持续、多日、多种子，停止到货后检查排空 | 只报已完成均值会遮住长期积压 |
| 图谱一致性 | 任务/货物/事件数量、持有者时间线、镜像 lag、协作关系 | 假事务单测不代替实际 Neo4j |
| 规模与并发 | 实际工作/移动/排队分布、调度周期 P95/P99、图规模与查询延迟 | 100 注册不等于 100 同时工作；单进程不等于 100 Worker |

停止条件应包含碰撞、货物重复/丢失、容量越限、SOC 突破硬余量、扰动无法恢复、未执行指定扰动、镜像/审计失败、墙钟预算与收尾未排空。失败保留原始原因，不在失败后删任务、放宽包络、提高电量或改验收门槛。

结论：本设计提供有明确边界的、预防优先的二维研究仿真底座；是否达到“足够好”，必须由最终冻结代码版本的实际矩阵结果支持。百万级及延迟硬指标仍是独立且不可省略的后续联合验收，不从本次设计说明中自动获得。
