# Scheduler v2：算法比较、实现来源与声明口径

核查日期：2026-10-27。实现范围：`backend/scheduling_v2/`。不改变原仓库根许可证，也不为原仓库或依赖重新授权。

## 1. 本次实际实现了什么

1. **批量线性分配**：独立编写矩形最小成本匹配，基于经典Kuhn–Munkres/匈牙利方法的原始对偶增广思路。显式dummy列允许不分配；硬不可行候选不交给执行层。求解的是当前估计代价矩阵，不是全天联合调度最优。
2. **空间路网与到达时间估计**：沿现有0.2m几何模型建立0.8m公共路网，增加100个停车位、24个充电位的准确进出连接。仍使用原0.55m规划半径和1.1m机器人间连续距离阈值；不是通过缩小身体或跳过障碍获得提速。批量派单用路网行程估计、期限风险与轻度任务量均衡；时变占用由下一层再精确检查。
3. **优先级安全时间区间搜索**：独立编写SIPP式搜索，状态为路网节点与安全区间，动作包括移动与合法等待；动态占用使用已提交轨迹，移动冲突做连续扫掠检查。规划有到达时域/展开数上限，失败保留旧计划或保持未分配，不宣称全车队完备性或全局最优。
4. **安全任务接续**：完成取放/补能后，尝试从当前位置续接任务。先完整规划候选任务及回真实停车位的安全尾段，检查成功才原子替换旧尾段；失败继续执行原尾段。不靠让机器人消失、在路口无限停车或提前释放货物解决问题。
5. **工程集成**：复用现有day1库存门禁、货物持有者转移、逐秒执行、独立连续碰撞审计、检查点/Journal/Neo4j接口；新增独立有界A/B入口。普通机会充电在可行任务分配之后处理，临界电量优先补能，能量硬准入保留额外行程和等待余量。
6. **有证据的计算优化**：空间与8s时间桶联合索引、仅对预约表合并同速度连续片段、标量相对运动最近距离、同安全区间较早到达的支配剪枝、路网边权和反向距离缓存。实际执行事件不合并，连续碰撞检查不改为采样，半径/搜索时域/展开上限不因性能优化缩减。代码自行编写，使用Python标准库；没有偷偷引入C++/NumPy/SciPy求解器。
7. **持久化与审计修正**：检查点先规范JSON对象键再计算摘要，恢复仍严格核对SHA与代码身份；图谱审计从唯一Run节点沿所属关系/Step查询，不再对全库大标签扫描，保留原5s查询超时和全部计数断言。实际用了scoped CALL语法，已在当前服务器验证，要求相应Neo4j版本支持；没有改全局数据库配置、加大全局超时或删除旧数据。

0.8m路网是离散规划骨架，不等于穷尽自由空间内所有可行轨迹；可能遗漏一些通行/会车选择。当前地图的全部任务点、100泊位与24充电位经过连通性测试。性能重放比较保持相同骨架、参数、初始状态和决策成本，仅优化计算实现，不把缩小几何搜索空间混入3.9倍的计时结论。

**没有实现：**完整openTCS/Open-RMF运行时、VDA5050协议兼容、多车联合RHCR、CBS、PIBT、显式等待环检测及多车联合解锁、已验证的真实能耗校准、100 Ray Worker或百万级延迟联合验收。当前仍预约已分配业务的完整候选轨迹，后段更新是事件触发的安全尾段替换，不将其包装为完整滚动窗口MAPF系统。派单没有接入图谱历史或学习式拥堵预测；动态冲突在SIPP层处理，Neo4j不是派单权威。

## 2. 比较与取舍

| 候选 | 优点 | 与本项目的适配/限制 | 本次决定 |
|---|---|---|---|
| 原逐任务贪心＋整链出发偏移 | 简单，轨迹容易确定并恢复 | 候选少、路线固定，远端冲突会推迟整个任务，空驶多 | 保留作可重放对照，不覆盖旧实现 |
| 批量线性分配 | 给定矩阵可求全局最低总分，支持矩形 | 代价只是估计，不能代替时空可行性；dummy须显式处理 | 采用经典方法，自行实现并用穷举小矩阵验证 |
| SIPP＋优先级规划 | 同时决定路径和等待，利用安全时间区间压缩时间状态 | 对既有轨迹优先，可能规划失败；搜索边界、尺度和停留必须明确 | 自行实现，保留真实身体与连续冲突检查 |
| CBS/有界次优CBS | 能联合解决冲突，理论性质清楚 | 联合搜索在拥挤/持续任务下计算代价可能大，不能先承诺100台实时 | 此轮不引入，后续可作局部冲突组对照 |
| RHCR | 适合持续到达的新目标，短期重规划 | 官方实现许可证带用途限制，且完整滚动前缀需要额外安全/末端处理 | 参考论文问题分解概念；不引入其代码、不称已实现RHCR |
| PIBT | MIT开源、每步局部优先级协调，适合大规模图任务 | 有限到达保证有图结构条件；本地图含泊位死端、持续取放、非统一边时长 | 核查后未采用，也未复制源码 |
| openTCS | 工业任务/路线/资源调度分层，真实逐段资源生命周期 | 是可扩展平台，不是任意地图开箱保证性能；Java适配有额外工程量 | 文档架构参考，不依赖其程序或复制代码 |
| Open-RMF | 共享轨迹时刻表与多车/多车队协商 | 引入ROS2/C++组件、适配器和执行契约，迁移成本高 | 对照研究，未安装、未调用其库 |

## 5. 试验入口

```bash
./run_in_lade.sh python -m backend.scheduling_v2.runner \
  --scene data/layouts/warehouse100-v1.json --dataset DATASET_DIRECTORY \
  --output NEW_RUN_DIRECTORY --run-id UNIQUE_RUN_ID \
  --variant v2 --until 3600 --max-wall-seconds 600 --knowledge-backend journal
```

`baseline` 为旧算法，`v2-no-chain` 为新匹配/规划但禁用任务接续，`v2` 启用接续。`--config-json` 可显式控制roadmap/euclidean代价、能耗等配置；比较必须说明哪些参数不同。`journal`对照不算Neo4j联合验收，真实图谱使用独立run_id的`--knowledge-backend neo4j`。
