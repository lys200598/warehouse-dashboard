# 连续多日仓库任务数据：七种典型波动

本生成器按此前确定的仓库边界，生成连续多天的进货、上架、下架和出货任务。默认示例为7天，每天一种代表性负载，共50,112条任务；库存、货物身份和参考在途任务在午夜继续延续。

先看每日场景，再看库存和期限规则；需要运行时可直接跳到第5节。仓库布局及调度背景见 [WAREHOUSE_DESIGN_GUIDE.md](WAREHOUSE_DESIGN_GUIDE.md)。

## 1. 七天各有什么特点

默认种子为`20261028`，日期为2026-10-28至2026-11-03。普通日每天6912条，第7天增加到8640条。前六天固定总量，便于观察时间集中、空间热点和进出方向变化；第7天专门提高负荷并留出低谷。

|日|profile|负载设计|本例任务／入库／出库|
|---|---|---|---:|
|1|`uniform`|全天均匀强度，在小时间隔内随机抖动释放时刻|6912／3459／3453|
|2|`fixed_peak`|08—10、14—16、20—22时承载约80%任务，其余时段保留背景流量|6912／3447／3465|
|3|`local_hotspot`|时间规律保持均匀，约70%需求偏向一片真实空间热点|6912／3467／3445|
|4|`batch_pulses`|三组2小时业务窗内，每150秒同时出现48条任务|6912／3500／3412|
|5|`moving_hotspot`|上午偏向一端热点，12时后切换到另一端热点|6912／3483／3429|
|6|`tidal`|前8小时偏出库，中间8小时偏入库，最后8小时回到中等库存|6912／3385／3527|
|7|`mixed_recovery`|增加25%总量；06—12高负荷叠加空间热点，12—18进入低谷|8640／4262／4378|

这些是公开参数构造的合成场景。数据组织借鉴LaDe的日期、任务、位置与运行记录分离方式；本例使用仓内位置编号，来源标注为合成仓库任务。

### 时间分布怎样生成

生成器先为一天固定任务总数，再依据公开小时强度分配释放时刻。采用分层随机分位：把累计强度切成若干小区间，在每个区间内随机选一点，既保持日量可比，也保留秒级抖动。

- 均匀日、局部热点日、热点迁移日、潮汐日：默认每小时288条。
- 固定峰值日：6个高峰小时约921—922条／小时，其余小时约76—77条。
- 批次日：08—10、14—16、20—22时有任务，48条同秒为一小批，批间150秒。
- 混合日：00—06时216条／小时，06—12时1008条／小时，12—18时72条／小时，18—24时144条／小时。

批次是一种任务出现方式，系统继续使用原有IN口受理、机器人取放与容量门禁。

### 空间热点怎样定义

热点直接由地图的货位地面坐标确定：从一端角落开始，按距离选取最近20%的活跃货位，构成热点A；从另一端选取热点B。混合日高负荷阶段使用30%的区域。

局部／迁移热点希望约70%任务落在当时热点；混合高峰希望约65%。选取时还要检查该格的参考占用与周转间隔，可用性不足时按明确规则回落到其他合法货位，回落次数写入报告。

本例实际情况：

- 第3日：4821／6912条落在热点，约69.75%；
- 第5日：4783／6912条落在对应时段热点，约69.20%，发生29次空间可用性回落；
- 第7日高负荷阶段：3925／6048条落在高峰热点，约64.90%。

### 进出潮汐怎样形成

潮汐日按照已存在的参考库存调整入库／出库倾向，三个阶段的目标约为活跃货位的25%、75%、50%。对全部1728格活跃的默认配置，目标分别为432、1296、864件。

本例三个8小时段的任务数量为：

|时段|入库需求|出库需求|
|---|---:|---:|
|00—08|857|1447|
|08—16|1591|713|
|16—24|937|1367|

算法依据已有库存做调整；如果某份小输入已经接近低库存目标，会维持该目标，避免凭空生成缺货出库。

## 2. 连续库存怎样保证

整个多日输入只有一份初始库存，默认864件。生成器从第一天开始维护同一份货物、货位、在途和周转状态；每日只切换到货强度与空间选择方式。

每个货位按实际参考状态交替产生任务：

```text
空格
  → 接收入库任务，计入仓内货物并预留该格
  → 参考上架完成，变为在架
  → 生成该件货的出库任务
  → 参考出库完成，货物离仓，格子变空
  → 满足周转间隔后再安排下一件新货
```

同一件货保持一个`goods_id`。初始库存货物可以直接出库；新货入库后，后续出库继续引用同一个编号。所有天数共享一个递增任务序列，因此任务编号在整个数据集中唯一。

### 两层校验

第一层是生成器的时间参考状态机：

- IN在参考接收时增加仓内数量；
- OUT在参考完成时才减少仓内数量；
- 目标格有货、预留或前一任务尚未参考完成时，不能接收下一件；
- 同格两次任务释放至少间隔1800秒，同时保留参考完成后的60秒周转余量；
- 跨午夜的参考取放、出库和可用时间继续保留。

第二层调用现有的`wide.data.validate_dataset`，独立读取已写出的CSV和manifest，重新检查文件摘要、表头、时间、位置、货物唯一性及逐货位参考进出依赖。

运行时中央仿真器继续检查实际仓容、IN口每口6件、货物真正上架、电量和交通。输入参考报告与运行结果分别保存，便于定位数据设计和执行表现。

### 本例的参考库存结果

```text
初始库存：864
参考已接收总数：25,003
参考完成出库总数：25,109
清空参考在途后库存：864 + 25,003 - 25,109 = 758

全程参考仓内最少：430
全程参考仓内最多：1316
仓库容量：1728
```

第7日结束时还有参考在途：仓内767件，其中在架751、入库在途7、出库在途9。完成剩余参考出库后为758件。报告同时列出“时段结束”与“清空在途后”两个时点。

每一天的期末状态直接成为下一天期初状态，逐日守恒使用当日参考接收数与参考完成出库数核对。本例还有5092件货物的入库与出库跨过午夜，可直接检查跨日身份延续。

## 3. 期限怎样计算

每条任务的期限都在仿真运行之前确定：

```text
due_time = release_time
           + 静态仓库路网的任务行程时间
           + 统一空驶参考余量
           + 取货10秒 + 放货12秒
           + 固定slack 900秒
```

`slack`是额外时间裕量。静态路网由当前地图与现有`WideRoadmap`生成，计算基准速度为0.8m/s。

空驶参考余量采用一个明确的路网规则：以IN-1为公共参考点，取路网节点及命名位置到它的最大静态时间，再乘2，作为经公共参考点连接两位置的统一余量。本地图算得348秒。默认期限跨度约1285—1408秒。

参考完成时刻使用行程、空驶余量与取放时间，固定900秒裕量留在期限中。所有计算独立于实际任务由谁接单、是否排队、是否交接和最终完成时间。

这套参数给出一致、可追溯的合成要求。实际完成数、迟到和交通表现由后续仿真衡量；新算法比较继续使用同一份输入。

## 4. 文件与数据边界

生成目录包含：

|文件|作用|
|---|---|
|`tasks.csv`|固定七字段任务输入|
|`initial_inventory.csv`|一次性初始库存|
|`manifest.json`|日期、种子、地图SHA、每日场景、期限规则和文件SHA|
|`profiles-report.json`|逐日IN／OUT、24小时分布、货架/端口分布、热点和回落统计|
|`reference-inventory.json`|参考收发、逐小时库存、时段末在途、容量与周转校验|
|`validation.json`|独立输入校验结果|

七字段保持原契约：

```csv
task_id,task_type,goods_id,release_time,due_time,source_id,target_id
```

所有日期使用完整ISO8601时间和显式`+08:00`时区。IN端点为`IN点→货位`，OUT端点为`货位→OUT点`。每任务一件货。

机器人分配、电量、故障、回充和接力选择继续归属于独立仿真配置及运行结果。数据集中只描述仓库边界任务，便于与不同算法公平比较。

## 5. 生成、校验与使用

### 5.1 生成默认7天

从仓库根目录执行，选择一个尚不存在的输出目录：

```bash
bash run_in_lade.sh python -m backend.wide.multiday \
  --scene data/layouts/warehouse100-wide-v2.json \
  --output data/datasets/seven-patterns-20261028/seed-20261028 \
  --days 7 \
  --tasks-per-day 6912 \
  --seed 20261028 \
  --date 2026-10-28
```

已存在的输出会拒绝覆盖。相同源码、地图、参数与种子在新目录生成的文件字节可复现。

本次已生成的示例为上述路径，共50,112任务，整目录约5.62MB。核心输入SHA-256：

```text
tasks.csv
f92781517b4007caa2b8f2799f3b987ded541c252b8d3cc592ca7101725e1e0a

initial_inventory.csv
5341a77ad9f4b02aba99a4e30012ea9346739da625b4744737d0d0d1ab85d8e2
```

### 5.2 再独立校验一次

```bash
bash run_in_lade.sh python -c \
  'import json; from backend.wide.data import validate_dataset; print(json.dumps(validate_dataset("data/layouts/warehouse100-wide-v2.json", "data/datasets/seven-patterns-20261028/seed-20261028"), ensure_ascii=False, indent=2))'
```

本地全量复核通过，50,112个任务ID全部唯一，输入文件SHA前后保持相同。批次日同秒任务最多48条，同秒单个IN口最多5条。生成器和输入校验已完成；完整7日运行的迟到、吞吐、电量与协作指标在后续实验中单列。

### 5.3 天数和场景可以扩展

`--days`接受任意正整数，默认场景循环为上面七种。可以指定自己的循环，例如连续10天交替平稳与峰值：

```bash
bash run_in_lade.sh python -m backend.wide.multiday \
  --scene data/layouts/warehouse100-wide-v2.json \
  --output data/datasets/ten-days-uniform-peak \
  --days 10 \
  --profiles uniform,fixed_peak \
  --tasks-per-day 6912 \
  --seed 20261028
```

`--max-tasks`默认250000，是本次生成工作的显式文件/内存预算，可以按需要提高。它控制预计任务总量，和支持多少天分开。更大时间范围仍应结合数据大小、报告规模及实际运行时间安排。

常用参数：

|参数|默认值|含义|
|---|---:|---|
|`--days`|7|连续天数|
|`--profiles`|七种循环|逗号分隔的逐日场景循环|
|`--tasks-per-day`|6912|普通日任务数|
|`--mixed-load-factor`|1.25|混合高负载日的日量倍数|
|`--active-slots`|全部1728|哪些货位产生任务，仓库总容量保持不变|
|`--minimum-slot-gap-seconds`|1800|同格任务释放最小间隔|
|`--deadline-slack-seconds`|900|预先固定的期限裕量|
|`--batch-size`|48|同秒批次任务数上限，允许1—48|
|`--max-tasks`|250000|显式任务总量预算|

如果给过少活跃货位安排了超过声明周转能力的需求，生成器会给出明确错误，保持选定到货分布，并让调用者显式调整参数。

### 5.4 用V5运行时保持新的发布身份

生成器与新的多日校验能力应随一个新源码发布启动，使用新的run-id及output。已有检查点继续配对原源码恢复。

运行入口仍是：

```bash
bash run_in_lade.sh python ops/warehouse_v5_release.py run -- \
  --scene data/layouts/warehouse100-wide-v2.json \
  --dataset data/datasets/seven-patterns-20261028/seed-20261028 \
  --output data/local-runs/seven-patterns-v5 \
  --run-id seven-patterns-v5 \
  --knowledge-backend journal \
  --commit-seconds 300 \
  --max-wall-seconds 14400
```

该命令是后续完整运行入口，墙钟预算可根据实际机器调整。知识实验另行声明状态采样间隔：100机器人按5秒采样，7天约产生1209.6万条机器人状态；任务输入规模与图状态规模分别统计。
