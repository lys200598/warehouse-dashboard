### 任务背景

在仓储项目中参考 `KG_Embodied` 的 Neo4j 图谱流程，将已经生成的 Warehouse100 数据包导入本项目独立的 Neo4j 服务。目标是先建立可复现的静态知识图谱基础，不修改现有前端，也不将模拟运行结果伪装成真实执行结果。

### 关键结论

- 图谱分为两层：布局层（仓库、库区、货架、货位、入/出库工位）和数据集层（初始货物、计划任务）。
- Warehouse100 的当前测试包将写入 4 个库区、36 个货架、1,728 个货位、16 个工位、864 件初始货物及 6,912 条计划任务。
- 每类实体均有 Neo4j 唯一约束；导入使用 `MERGE` 和 `UNWIND` 分批写入，同一数据包重复导入是幂等的。
- `Goods` 和 `WarehouseTask` 的 ID 含数据集命名空间；静态布局 ID 含布局版本命名空间，后续新数据集或新布局不会覆盖旧数据。
- 初始库存通过 `(:Goods)-[:INITIAL_AT]->(:Location)` 表示；任务通过 `CONCERNS`、`FROM`、`TO` 连接货物与源/目标位置。任务仍是计划数据，未声称已被机器人执行。
- 导入脚本默认离线 dry-run；只有显式加入 `--apply` 才会连接和写入 Neo4j，密码不会写入脚本或命令行参数。

### 后续建议

先在仓库根目录执行离线检查：

```bash
./.venv/bin/python scripts/import_warehouse_neo4j.py
```

确认输出为 6,912 条任务后安装驱动并导入（命令会安全地交互输入密码）：

```bash
./.venv/bin/python -m pip install 'neo4j>=5.26,<6'
./.venv/bin/python scripts/import_warehouse_neo4j.py --apply
```

导入后可在 Neo4j Browser 执行：

```cypher
MATCH (d:Dataset)-[:INCLUDES_TASK]->(t:WarehouseTask)
RETURN d.id, t.task_type, count(*) AS task_count
ORDER BY task_count DESC;
```

下一阶段应在后端把机器人实际分配、执行状态和事件增量写入图谱，并提供只读查询 API；待接口稳定后再决定如何在前端展示，避免提前修改既有页面。
