### 任务背景

在静态 Warehouse100 图谱和只读查询接口已经具备后，开发机器人运行态写入：将当前仿真的机器人状态、任务执行、事件写入独立 Neo4j 服务，为 100 个机器人工作过程的可追溯查询提供基础，同时不修改现有前端。

### 关键结论

- 新增运行态图模型：`Run`、`Robot`、`Execution`、`AgentState`、`RuntimeEvent`，均使用唯一 ID 和 `MERGE` 保证重试不会重复创建。
- 状态路径为 `Run ← IN_RUN ← Robot`，`AgentState → OF_ROBOT → Robot`，`Execution → ASSIGNED_TO → Robot`，`RuntimeEvent → ABOUT_ROBOT → Robot`。
- Neo4j 写入默认关闭；仅当 `WAREHOUSE_NEO4J_WRITE_ENABLED=1` 时启动后台写入队列，避免原有仿真服务启动即改动数据库。
- 队列长度为 1；写入滞后时丢弃过期快照、保留最新快照，不阻塞机器人仿真和 WebSocket 推送。
- 每个采样批次用 `UNWIND` 写入全部机器人状态。默认每 4 tick 记录一次位置/电量状态；事件即时批量落库且有本进程去重。
- 当前仿真仍是旧货架任务模型，因此 `Execution` 暂不错误关联到 Warehouse100 的静态 `WarehouseTask`。待仿真任务适配七字段数据集后再建立该关系。

### 后续建议

先确保静态图谱已导入，随后在仓库根目录启动 100 个活动机器人并开启运行态写入：

```bash
export WAREHOUSE_NEO4J_PASSWORD='你的Neo4j密码'
export WAREHOUSE_NEO4J_WRITE_ENABLED=1
./.venv/bin/python -m backend.server --backend local --max-active-robots 100
```

启动后从快照获得 `runId`，再查询一个机器人：

```bash
curl http://127.0.0.1:4173/api/snapshot
curl "http://127.0.0.1:4173/api/kg/warehouse/runs/<runId>/robots/1/subgraph"
```

确认实时数据正确后，下一步应先把 `backend/dataset.py` 和仿真调度适配到 Warehouse100 的七字段 `INBOUND/OUTBOUND` 数据格式，再建立 `Execution` 到静态 `WarehouseTask` 的关联。最后才进行百万级数据生成、索引设计、100 并发查询延迟压测。
