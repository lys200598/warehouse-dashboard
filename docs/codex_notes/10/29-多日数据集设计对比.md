# 多日数据集设计对比（wz vs 当前分支）

## 任务背景

用户要求参考 `wz/warehouse-design` 的 `docs/MULTIDAY_DATASET.md`，对比协作者的多日数据集设计与当前分支生成数据集的实际差异。本文只读比较文档、生成器源码、数据文件和 manifest。

## 关键结论

- **设计完全一致**：七种日型、普通日 6912 条、第 7 天 8640 条、总计 50,112 条、初始库存 864、跨日连续库存、期限公式、两层校验，两边文档和参数相同。
- **数据内容逐字节一致**：当前 `data/datasets/my-seven-days/` 与 wz `data/examples/seven-patterns-20261028/` 的 `tasks.csv`、`initial_inventory.csv`、`profiles-report.json`、`reference-inventory.json`、`validation.json` 五个文件 SHA-256 完全相同。
  - `tasks.csv`：`f92781517b4007caa2b8f2799f3b987ded541c252b8d3cc592ca7101725e1e0a`
  - `initial_inventory.csv`：`5341a77ad9f4b02aba99a4e30012ea9346739da625b4744737d0d0d1ab85d8e2`
- **唯一不同的文件是 `manifest.json`**，且差异只在 `generator_sources`：记录生成时 `multiday.py` / `wide_data.py` 的源码 SHA，不影响任务、库存或统计结果。
  - 当前样例：`multiday.py=d874eb…`、`wide_data.py=aa663f…`（正好是当前分支 HEAD 源码）。
  - wz 样例：`multiday.py=d874eb…`、`wide_data.py=bf3273…`（wz 的另一个历史版本）。
  - 用当前工作树重新生成：`multiday.py=ff41f7…`、`wide_data.py=d6216e…`，但 `tasks.csv` 与 `initial_inventory.csv` 仍逐字节相同。
- **打包方式不同**：wz 把六文件样例作为 Git 跟踪资产放在 `data/examples/seven-patterns-20261028/`，附 `README.md`、`SHA256SUMS.json`；当前分支样例在 `data/datasets/my-seven-days/`，被 `.gitignore` 的 `/data/*` 忽略，没有 README/SHA256SUMS。
- **布局与边界配对相同**：两边样例都配对旧 `warehouse100-wide-v2.json`（36 架、1728 货位）并使用具体 `IN-n`/`OUT-n`。当前分支新增的 100×90m/40 架/1920 货位 `balanced` 布局和自由 `INBOUND`/`OUTBOUND` 边界，未体现在这份多日样例中，需要单独生成/转换。
- **生成器代码已对齐**：当前工作树的 `backend/wide/multiday.py`、`scenarios.py`、`data.py` 与 wz 分支逐字节相同；当前分支 HEAD 与 wz 不同，未提交的布局迁移已经把协作者的生成器改动带入工作树。
- **测试相同**：两边 `tests/test_multiday_dataset.py` 都是 17 项测试，内容一致。

## 代码与文档差异

- `docs/MULTIDAY_DATASET.md`：当前分支只比 wz 少 6 行“已随分支提供的完整参考数据”说明；七类日型、库存、期限、参数表、测试说明完全相同。
- `backend/wide/multiday.py`：当前 HEAD 与工作树只差 1 行，把 manifest 里写死的 `1728` 改成 `len(slots)`，对旧布局输出无影响。
- `backend/wide/data.py`、`scenarios.py`：工作树与 wz 相同，但与当前 HEAD 有大量格式/校验/边界适配改动；对本样例的任务与库存输出无影响。
- 新 1920 布局若用于多日生成，`capacity`、`active_slot_ids`、`scene_sha256`、货位编号都会变化；不能把旧样例的地图身份直接套到新布局。

## 执行过的操作

- 阅读当前 `docs/MULTIDAY_DATASET.md` 与 `git show wz/warehouse-design:docs/MULTIDAY_DATASET.md`，逐段 diff。
- 对比 `backend/wide/multiday.py`、`scenarios.py`、`data.py` 在当前 HEAD、当前工作树、wz 分支三个版本的 SHA。
- 对当前 `data/datasets/my-seven-days` 与 wz `data/examples/seven-patterns-20261028` 的六个文件做 SHA-256 对比。
- 逐字段比较两份 `manifest.json`，确认唯一差异是 `generator_sources`。
- 用当前工作树在 `/tmp` 重新生成一份七天数据，验证 `tasks.csv`/`initial_inventory.csv` 与现有样例逐字节相同。
- 统计两份数据集的逐日任务量、IN/OUT 数量、释放时间分布、校验报告与测试数量。
- 检查 `.gitignore` 与 `git ls-tree`，确认当前样例未跟踪、wz 样例已跟踪。

## 后续建议

1. 若当前分支需要与 wz 一样的可复现样例，把 `data/examples/seven-patterns-20261028/`（六文件 + README + SHA256SUMS）纳入当前分支，保留旧 1728 布局作为冻结对照。
2. 新 1920 布局或自由边界必须另建输出：用 `--scene data/layouts/expansion-candidates/balanced/layout.json` 重新生成，不要复用旧样例的 `scene_sha256`；自由口再用 `convert-boundaries` 生成逻辑边界版本。
3. 比较数据集时应以 `tasks.csv` / `initial_inventory.csv` 的 SHA 为准，不要以 `manifest.json` SHA 判断内容差异，因为 manifest 会记录生成源码版本。
4. 可在当前 `docs/MULTIDAY_DATASET.md` 补上 wz 的“完整参考数据”段落，明确旧样例与 1920/free-port 新版本的对应关系。
