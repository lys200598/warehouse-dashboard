# 会议任务参考边界分析

## 任务背景

会议提出三项工作：设计仓储知识图谱存储内容、按白板流程复制仓库管理界面、用 AI 识别并存储图谱节点和关系。三项均要求参考 `KG_Embodied`，但当前仓储项目的界面与 LaDe（末端配送）界面看起来没有直接关联，需要明确可复用范围，避免错误照搬。

## 关键结论

- 这一判断成立：LaDe 的 `dynamic.html` 是无人机/配送任务的城市地图实验界面，与仓储货架、搬运机器人、库位和负载没有一一对应的视觉或业务关系，不能作为任务四的界面原型直接复制。
- 任务三与 `KG_Embodied` 的关联最强，应借鉴其图数据库写入、时间事件记录、任务分配与完成状态的建模方式，而不是其配送实体名称。
- 仓储图谱应至少包含 `Robot`、`WarehouseTask`、`Rack`、`Slot`、`Zone`、`Cargo`、`Event`、`RobotState` 等节点；关系包括任务分配、取货、放货、占用、位于、事件发生和状态快照，并统一保留时间、来源和关联任务 ID。
- 任务四应以白板流程和现有仓储页面为准。现有页面已经具备机器人运动、状态、任务及电量等基础展示；可从 LaDe 借鉴实时流、指标卡、事件明细、时间回放和查询面板等交互模式，但不应复制城市地图、无人机或配送控制项。
- 任务五中，`KG_Embodied` 的 LLM 主要承担任务规划、区域协调和图谱上下文查询，并没有实现“由 AI 任意识别节点关系后直接入库”的通用机制。
- 对仓储系统，仿真/WMS 产生的结构化任务、库位和机器人事件应通过确定性规则直接写图；AI 更适合用于解析非结构化工单、告警、文本日志或图像识别结果。AI 输出必须经过模式校验、置信度和来源记录后再入库。
- 推荐依赖顺序是：先完成任务三的数据模型与写入规范，再按该数据契约补齐任务四的展示，最后实现任务五的 AI 增强链路。否则前端和 AI 都没有稳定的存储目标。

## 执行过的操作

- 阅读 `KG_Embodied/dynamic.html`，确认其为 LaDe 无人机配送实验界面，包含城市/日期、无人机数、任务上限、Ray 和 LLM 等控制信息。
- 阅读 `KG_Embodied/src/dynamic_app.mjs`，确认其前端通过 SSE 接收实时帧并展示指标、事件、表格和回放。
- 阅读 `KG_Embodied/src/dynamic_query.mjs`，确认其提供人工 Cypher 查询界面。
- 阅读 `KG_Embodied` 中的 `LLMPlanner`、`RegionLLMCoordinator`、`TemporalKnowledgeStore` 和 `Neo4jKnowledgeStore`，核实 LLM 的职责是规划/协调与图谱上下文使用，图谱事实由任务生命周期事件写入。
- 对照当前仓储项目已有的机器人仿真、WebSocket 快照和前端画布展示能力，完成参考范围判断；未运行服务，未修改业务代码或页面。

## 修改内容

- 新增本文档，记录会议三项任务与 `KG_Embodied` 的正确参考边界、图谱建模方向及建议的实施顺序。
- 未修改现有前端、后端、仿真逻辑或测试数据。

## 后续建议

- 提供或确认白板流程图及“复制到哪个目标项目/页面”，再把任务四拆成明确的页面区域、字段和交互清单。
- 为任务三先确定图谱的唯一 ID 规则、节点/关系属性、事件时间语义、数据来源、幂等写入规则和保留周期，并以此生成 Neo4j 约束与索引。
- 在不改变现有页面风格的前提下，为任务四优先补充与图谱数据契约对应的任务流、机器人负载/货物状态、事件明细和统计展示。
- 为任务五明确 AI 的输入来源（工单文本、告警日志、图像或语音）及人工复核策略；没有非结构化输入时，不建议为了“使用 AI”替代可靠的结构化事件写入。
