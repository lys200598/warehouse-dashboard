# 测试数据生成代码评审

## 任务背景

用户询问当前测试数据生成代码是否有需要改进的地方。本次评审覆盖单日生成器、场景生成器、多日生成器、百万运行态生成器和相关校验/测试，只读分析，不改代码。

## 关键结论

- **核心设计没有发现正确性缺陷**：多日生成器的连续库存参考状态机、两层校验、逐日守恒、跨午夜身份延续都成立；单日生成器在 1728 和 1920 两种布局下都能通过 `backend.wide.data.validate_dataset`。
- 主要改进空间不在算法，而在**单一验证标准、布局/位置表护栏、CLI 一致性、遗留脚本收敛和测试覆盖**。
- 单日生成器 `scripts/generate_warehouse100_dataset.py` 自带一个简化的 `validate()`，没有调用统一的 `validate_dataset`；它写出的 `validation.json` 缺少 `hashes_verified`、`duration_seconds`、`hourly_tasks`、`daily_tasks`、`runtime_feasibility_claim` 等字段。
- 单日生成器的 `--layout` 与 `--locations` 是两个独立输入，只校验货位数量/端口类型，不校验位置表是否真的属于该布局；1920 布局的 `manifest.json` 已有 `scene_sha256` 和文件 SHA，但生成器没有使用。
- 所有生成器都把初始库存固定为容量的 50%（`len(slots)//2`），没有 `--initial-ratio`/`--initial-count`；要做低库存/高库存实验必须改代码。
- 三个生成器的期限公式不一致：单日固定 `+1800s`；场景用曼哈顿距离 + `width+depth` 空驶；多日用真实路网 `WideRoadmap` + 348 秒空驶。同一布局下不同生成器的任务期限不可直接比较。
- 场景生成器和多日生成器硬编码 8 个 IN/OUT 端口（`IN-1..8`、`OUT-1..8`）以及多日的 `IN-1` 公共枢纽；当前候选布局都是 8 个口，但新布局若改端口数量/编号会直接失败。
- 存在遗留/易混淆入口：`scripts/generate_warehouse_dataset.py` 生成 21 列 `WT-*` 的 `putaway` CSV，不是 V5 的七字段契约；`scripts/generate_current_layout_graph_dataset.py` 硬编码 540 货位的旧 demo 布局，名字却像“当前布局”。
- 测试覆盖不均：多日有 17 项测试；单日生成器只有 1 项测试，没有覆盖布局/位置表不匹配、统一校验、1920 布局、逐字节复现和端口包络。

## 建议改进（按优先级）

| 优先级 | 改进项 | 现状/证据 | 建议 |
|---|---|---|---|
| P0 | 统一验证器 | 单日生成器自带简化 `validate()`；同一份输出能通过 `validate_dataset`，但报告字段不同 | 写完后调用 `backend.wide.data.validate_dataset`，用统一报告替换/合并 `validation.json` |
| P0 | 布局与位置表交叉校验 | 只查 slot 数量与端口类型；1920 布局的 `manifest.json` 有 `scene_sha256` 但未读取 | 校验每个 location 的 rack/level/face/bay/坐标与 `layout.json` 一致；把布局 manifest 的 `scene_sha256` 写入数据集 manifest |
| P0 | 初始库存可配置 | 所有生成器固定 `capacity//2` | 增加 `--initial-ratio` / `--initial-count`，并在 manifest/report 记录 |
| P1 | 期限公式统一 | 单日 +1800s；场景曼哈顿+尺寸；多日路网+348s | 抽公共 `due_time` 助手，至少在同一布局下使用同一参考；或在文档中明确不可跨生成器比较 |
| P1 | 端口假设参数化 | 场景/多日硬编码 8 口和 `IN-1` | 从 scene 的 `stations` 派生 IN/OUT 列表与 hub，不写死编号/数量 |
| P1 | 遗留脚本收敛 | `generate_warehouse_dataset.py` 是 21 列旧格式；`generate_current_layout_graph_dataset.py` 是 540 货位 demo | 标记 deprecated/移到 `ops/legacy`，或在 README 明确“只用于旧图谱实验，不能喂 V5” |
| P1 | 内容身份与 provenance 分离 | `manifest.generator_sources` 让相同数据在不同源码版本下 manifest SHA 不同 | 增加 `data_sha256`，或把源码哈希移到独立 `provenance.json`；文档说明比较内容看 `tasks.csv`/`initial_inventory.csv` SHA |
| P2 | 百万级校验/写入性能 | `validate_dataset` 全量读入内存；百万状态生成逐行写 JSONL | 增加流式校验或内存预检；JSONL 增加分批/可选 gzip |
| P2 | 逻辑边界一键生成 | 固定口生成后还要 `convert-boundaries` | 给生成器增加 `--boundaries fixed|logical`，或提供组合命令 |
| P2 | 测试补强 | 单日只有 1 项测试 | 增加布局/位置表不匹配拒绝、统一校验、1920 生成、逐字节复现、端口包络测试 |

## 已验证的事实

- 单日生成器默认 1728 布局：6912 任务（3456 IN / 3456 OUT）、864 初始库存，`validate_dataset` 通过。
- 单日生成器 1920 平衡布局：7680 任务（3840 IN / 3840 OUT）、960 初始库存，`validate_dataset` 通过。
- 端口包络：高峰数据集同一秒同一 IN 口最多 3 件；七天多日同一秒同一 IN 口最多 5 件；单日生成器最多 1 件。当前默认都在 6 件上限内。
- `data/datasets/my-seven-days` 与 wz `data/examples/seven-patterns-20261028` 的 `tasks.csv`/`initial_inventory.csv` 等五个文件逐字节相同；只有 `manifest.json` 的 `generator_sources` 不同。

## 后续建议

1. 先做 P0 三项：统一验证器、布局/位置表交叉校验、初始库存可配置；改动小、收益直接。
2. 再做 P1 的期限公式统一和端口参数化，保证 1728/1920/未来候选布局都能生成可比较的数据。
3. 把遗留生成器明确标记或移走，避免有人把 21 列 `WT-*` CSV 当成 V5 输入。
4. 单日生成器补 5 项测试后再改代码，避免引入回归。
