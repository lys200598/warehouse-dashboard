# 知识图谱工作台优化建议

## 任务背景

评估当前“仓储知识图谱工作台”页面，并结合 LaDe 项目的动态图谱、运行时间轴、协助解释和查询性能展示能力，提出面向仓储分拣闭环的优化方向。本次只做静态阅读与方案设计，不修改业务代码、不启动服务。

## 关键结论

- 当前页面已经能读取静态数据、任务/机器人/运行态追溯、全局记录、交接记录和预置查询；它不是功能空壳。
- 最大问题是结果主要是文字时间线或原始 JSON。使用者能“查到”，但很难快速看出图谱如何支撑派单、状态校验和异常处置。
- LaDe 最值得迁移的是“实时帧时间轴 + 受控上下文查询 + 协助解释 + 查询耗时分层展示”，而不是其配送地图、城市/区域模型或完整 UI 布局。
- 第一优先级应把 `Run.latest_step`、`Step.complete`、100 台回执数量、状态采样 tick 和调度状态来源放到同一张运行态总览卡中，明确当前展示是否为完整图谱状态。
- 第二优先级是将任务追溯改造成结构化生命周期：静态任务、分配、取货、交接/负责人变更、完成、异常，各阶段可定位到 tick、机器人和证据节点。
- 第三优先级是为机器人增加“调度决策上下文”视图，展示自身状态、正在执行任务、近期事件、可协作机器人、候选待派任务；这与 LaDe 的 LLM/KG 上下文查询模式一致，也最能说明图谱对调度的作用。
- 不建议在百万级图谱中默认渲染整图。应只绘制任务/机器人为中心的 1--2 跳有界子图，并始终使用完整 Step 或明确的时间上界。

## 执行过的操作

- 阅读当前页面 `dist/kg.html`：确认已有数据集/连接闭环、运行态追溯、全局记录、任务追溯、机器人追溯、预置只读查询、浏览器与后端查询耗时及 JSON 导出。
- 阅读 `backend/warehouse_graph_query.py`：确认后端已经支持 `Run.latest_step`、完整 `Step`、`AgentState`、`ExecutionState`、`RuntimeEvent`、`Handoff`、`RunStat`、`DispatchState` 的有界查询。
- 阅读 LaDe 的 `dynamic.html`、`src/dynamic_app.mjs`、`src/dynamic_timeline.mjs`、`src/dynamic_query.mjs`、`src/dynamic_assistance.mjs` 及其上下文查询脚本：确认其运行帧缓冲、拖动回看、协助角色标识、只读查询防护、分阶段耗时和决策上下文查询的实现方向。

## 修改内容

- 新增本说明文件；未修改前端、后端、Neo4j 数据或运行配置。

### 建议的页面演进顺序

| --- | --- | --- | --- | --- |
| P0 | 运行态总览卡 | `latest_complete_step`、`RunStat`、`DispatchState`、`/api/health` | 当前帧、连接状态与时间轴头部 | 显示 Run、最新完整 tick、100/100 回执、写入积压、调度来源（memory/neo4j）和数据新鲜度，避免把不完整状态用于解释或派单。 |
| P0 | 任务生命周期追溯 | `task_execution_trace` 的静态任务、`Execution`、`ExecutionState`、事件、`Handoff` | 事件时间轴 | 取代长字符串：分配→取货→交接/换负责人→入库/完成→异常，每项都带 tick、机器人和可展开证据。 |
| P0 | 机器人运行态卡片 | `robot_trace_context`、`runtime_state_trace` | 运行帧状态和协助角色 | 以电量、位置、阶段、任务、货物、采样 tick、状态滞后组成摘要，点击可展开最近轨迹和事件。 |
| P1 | 异常与协同面板 | `Assist`、`Handoff`、全局 `RuntimeEvent`、负责人变更 | LaDe 的 requester/helper 视觉语义 | 让低电接力、任务转移、撤销重派不再混在普通日志中；明确“谁请求、谁接手、为什么、何时结束”。 |
| P1 | 调度决策上下文 | `robot_context_rows`、`DispatchState`、完整 Step 状态 | LaDe 的 i0--i8 上下文查询包 | 固定展示“本机、近期轨迹、活跃任务、近期事件、候选协作机器人、临期任务”，证明图谱可为图谱驱动派单提供输入。 |
| P1 | 受控子图视图 | 任务/机器人追溯返回的节点和关系 | 有界上下文而非全图 | 只展示选中任务或机器人 1--2 跳关系：任务—执行—机器人—事件—交接；节点数设上限，点击节点同步筛选时间线。 |
| P2 | 查询与写入健康度 | 已有前后端耗时、`RunStat`、全局 writer 状态；可补充队列深度 | LaDe 分阶段查询计时、并发查询脚本 | 以最近 N 次 P50/P95/P99、失败数、最后写入时间、状态滞后展示“查询 <500ms”的证据，而非只显示一次查询结果。 |
| P2 | 从 4173 跳转定位 | 4173 的任务 ID、机器人 ID、Run ID、tick | LaDe 主页面到查询面板的入口 | 在仿真页点击任务/机器人/异常事件后，直接进入工作台对应追溯，避免人工输入 ID。 |

### 推荐的信息架构

1. **顶部：运行可信度。** 显示 Run ID、状态来源、最新完整 Step、实际/期望回执、当前数据是否可用于图谱派单。
2. **中部：业务闭环。** 左侧为任务生命周期，右侧为机器人上下文，异常/交接单独高亮。
3. **底部：证据与性能。** 放有界子图、原始事件证据、预置查询结果、查询耗时和 writer 健康度。原始 JSON 移到“技术详情”折叠区。

### 实施边界

- 保持现有仓储主界面和协作者的布局职责不变；上述改动限于知识图谱工作台及其查询接口。
- 默认查询必须继续以 `Run.latest_step` 和 `Step.complete=true` 为时间锚点，避免显示未收齐回执的跨机器人混合状态。
- 新增查询应复用现有复合索引与 `run_id + tick` 时间窗口，不引入全图扫描；图可视化必须有节点、关系和时间范围上限。
- 图谱驱动派单目前是可选校验模式，页面应如实显示 `memory` 或 `neo4j`，不能将内存派单误标为图谱派单。

## 后续建议

1. 先实现 P0 的“完整 Step 运行态总览”和结构化任务时间线；这两项工作量可控，最能改善展示效果。
2. 再实现 P1 的异常/交接面板和机器人调度上下文，使知识图谱的调度与协同价值可被非开发者理解。
3. 等协作者稳定主进程的图谱状态来源后，增加 4173 到工作台的带 Run/robot/task/tick 参数跳转。
4. 最后补 P2 的性能趋势和有界子图；不要以默认整图渲染作为展示方案。
