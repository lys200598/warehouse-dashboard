# 查询尾延迟：增量摘要、真实 API 计时与 32D 向量选型

本文保存V2阶段原始来源与结果。最新S9代码、原生入口、当前固定百万前缀及动态长尾的完整结论见[2026-10-29总总结](29-自由进出货口与查询长尾优化.md)，两阶段数值分别计量。

## 任务背景

本轮降低仓库知识查询的长尾。保留原查询作为对照，将生产查询、HTTP 客户端处理、独立验真分别计时。所有规模测试读取已有真实周仿真；当前正式实时服务、旧数据库、原始回归输入及失败原件均保留。

## 关键结论

- `global`、`local_awareness` 的主要开销来自每次遍历全部任务、查找最新版本并重新分组。新增按 `run + created_at + seq + checksum` 绑定的增量摘要，当前固定百万前缀测试的最大 HTTP 延迟降至 **236.08 / 233.41 ms**，各 101 条无超过 500 ms 请求。
- 摘要进入生产查询工厂及 live 启动入口。每次请求仍获取新的 Neo4j 版本围栏，检查目标和当前 head 的 checksum；历史查询读取对应 seq，未来任务不会混入。
- 完整 32D ANN 的一部分原长尾来自集中压测客户端。保持同一生产 ANN 源码、同一服务进程和连接池，在八个客户端进程下，128 个真实压力请求的四轮测试得到 **均值 122.52、P99 264.22、最大 318.08 ms**，521 条全部小于 500 ms；每轮真实 API 峰值 **117 / 126 / 107 / 103**。
- 单个客户端进程仍保留其原始长尾：同样 521 条均值 291.73、P99 660.86、最大 682.45 ms，102 条超过 500 ms。两组服务端实际区间均值约 117 / 113 ms，Bolt 均值约 94 / 93 ms，有助于定位客户端调度、接收和解析开销。
- 做了一个完整 **32D、float64、全候选穷举 Flat** 对照：保持查询点和所有返回命中的真实图谱来源校验。它比现有 HNSW 更慢，留作研究对照，生产继续使用原 ANN。100 个查询的 ANN 相对 Flat 数值 Top5 平均 recall@5 为 **0.976**。
- 本文独立测试共 **4,102 条完整 HTTP 响应**已逐条后验通过（1,424 摘要 A/B + 818 Flat A/B + 818 百线程客户端 A/B + 1,042 压力客户端 A/B），没有过滤失败、冷启动或预热样本。历史 V1 失败、工具报错及冷慢值完整保留。
- 当前这些数值的范围是**固定最终提交点的真实百万图谱读取**。动态写入、实时控制链及自由口数据的联合资格，由同源 live 联合回归另行记录。

### Flat32 选型与停止判据

独立原型位于工作区 `research/query-tail-20261029/flat32.py`，远程 `/data/workspace/wz/warehouse-flat32-v2-20261029`，未加入生产查询工厂。

- 原型每次评分全部当前 seq 之前的候选；每次获取新的图谱 created/checksum/query vector，并从 Neo4j 读取及校验全部 5 个命中的源 payload/vector/历史 checksum。

## 修改内容

### 生产模块

- `backend/query_views/summary.py`：只读原 journal，事务化消费新增批次；按截止时间推进 overdue；保存每个 seq 的不可变摘要和源 checksum；完整检查 run、创建版本、metadata、config、原始批次连续性。失败时整段回滚。
- `backend/query_views/catalog.py`：使用摘要替换重复的全任务扫描；保留每请求 Neo4j 新鲜围栏、原任务数量预算、精确历史 cutoff；对不可变 fleet 做有界私有缓存，公开返回仍经完整 JSON 隔离。
- `backend/query_catalog/service.py`：显式 `summary_root` / `summary_cache_root` 工厂参数、分段计时；旧默认入口继续可用。
- `ops/warehouse_live.py`：接入 `--query-acceleration summary`、`--summary-root`、`--query-summary-cache`；启动准备耗时与正式请求分开；向 live runtime 传递 summary 参数。

主会话对接 live runtime 的发布顺序：原 journal 写入成功 → Neo4j mirror 成功 → checkpoint → summary 追赶及核对 → 发布 frame。写入或摘要失败按错误传播，旧点保持可追溯。

例如一个 seq 新发布 20 个任务、10 个任务完成，摘要只处理新增批次和到期变化，并保存这一 seq 的计数。查询上一 seq 时返回上一 seq 的任务压力；查询最新 seq 时校验图谱已经提交的点，再读取这一点的摘要。

## 后续动态 S2 联验的负结果与只读定位

主会话同源 S2 owned-live 的后续实际联验记录了新的集成瓶颈：100 客户端、真实 API 峰 100、20,056 条请求，服务端均值约 1.73 s、P99 7.62 s、最大 10.24 s，20,047 条服务端区间超过 500 ms；其中一条 global HTTP400 为 `catalog source point absent`，其余 20,055 条完整响应逐原 journal/RealOracle 验真通过。原件位于工作区 `research/free-boundary-20261029/live-joint-v2/`。固定前缀测试与该动态集成结果保持各自范围。

主会话定位了 live 路由在事件循环调用 `runtime.latest()`、锁内 deepcopy 整个约 109 KB frame 的开销，已准备以只读标量 `query_point()` 作单变量下一轮回归；该改动和后续动态资格由主会话记录。

本子任务对唯一 HTTP400 做了只读调查：

- 写入器将 WHStep/状态、`committed_seq`、`real_last_seq` 在同一个 `execute_write` 事务中提交，未发现分事务发布 head 的路径。
- 失败包由 route 默认补 run/seq，当时没有记录补完后的内部 seq；相邻帧发布在 seq33→34，无法将失败请求的实际 seq 事后确定为其中一个。
- 对实际 S2 数据库 17691 做 EXPLAIN，版本为 Neo4j **5.26.32 / SLOTTED**。原 POINT_QUERY 的 WHERE、head-key、RETURN 都使用 **`cache[r.committed_seq]`**；LATEST_QUERY 也已缓存。源码重复引用不等于该执行计划重复读取物理属性，因此当前证据不支持把显式 `WITH head` 宣称为已验证修复。
- 当前图谱 head=real_head=70，WHStep 33、34、35、70 的节点/checksum 齐全；原 seq34 fence 当前返回完整一行。这个事后状态用于排除永久缺点，保留当时瞬态原因未决。
- Neo4j [并发访问官方文档](https://neo4j.com/docs/operations-manual/current/database-internals/concurrent-data-access/)说明 read-committed 可能有非重复读，并建议需要复用的属性只取一次。此处仍须结合实际执行计划和原始失败参数判断。

诊断脚本：工作区 `deployment/query-fence-readonly-diagnosis.py`；只读原件：`research/query-tail-20261029/fence-readonly-diagnosis-v1.json`。V2 生产文件未修改，S2 冻结源及失败资格保持不变。建议下一轮服务包装器记录 executor 收到的完整 `run_id/seq/query_id/request_id` 与异常，保留首次错误；目前没有加入盲重试或吞错逻辑。
