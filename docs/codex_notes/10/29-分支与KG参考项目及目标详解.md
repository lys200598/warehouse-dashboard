## 三、参考项目 KG_Embodied

### 3.1 它是什么

`KG_Embodied` 是团队在 LaDe 末端配送数据基础上扩展的**多无人机配送仿真 + 知识图谱可视化**项目：

- 数据：LaDe delivery CSV（城市、订单坐标、接受/送达时间、AOI、region）。
- 仿真：每个 region 一个固定 depot；无人机从 depot 取货飞往订单目的地。
- 并行：local 单进程 / Ray actor（每个 drone 一个 actor）。
- 调度：`AuctionCoordinator` 规则拍卖，或 `RegionLLMCoordinator` 区域级 LLM 批量派单，失败回退规则。
- 知识：默认内存 `TemporalKnowledgeStore`；设 `KG_BACKEND=neo4j` 才写 Neo4j。
- 页面：`dynamic.html` + `/events` SSE 实时帧；`simulation.html` 静态回放。
- 端口：8010；可选 vLLM 6666、Ray Dashboard 8265。

它不是「知识图谱本体/推理引擎」，也不是人形机器人项目；它提供的是**把多智能体运行事实沉淀为时序图、再服务于查询和决策**的完整样板。

### 3.2 图谱模型

Neo4j 节点：

| 节点 | 含义 |
|---|---|
| `Run` | 一次实验批次，所有数据按 run 隔离 |
| `Drone` | 无人机智能体 |
| `Task` | 配送任务 |
| `Region` | 城市区域 / depot 所属区域 |
| `Event` | 离散事件（派单、取货、完成、低电、充电、接力、接管） |
| `Step` | 每轮仿真的整体摘要（完成数、未完成数、各状态 drone 数、总里程等） |
| `AgentState` | 可选，每个 step 的每个 drone 状态快照 |

核心关系：`IN_RUN`、`IN_STEP`、`OF_DRONE`、`HOME_REGION`、`CURRENTLY_IN`、`BELONGS_TO`、`ABOUT_DRONE`、`ABOUT_TASK`、`ASSIGNED`、`CARRYING`、`COMPLETED`、`ASSISTS`、`HANDOVER_TO`、`TAKES_OVER`。

三个关键设计：

1. **Run 隔离**：`KG_RUN_ID` 绑定一次实验，`Drone/Task/Region/Event` 都挂到 `Run` 下，查询必须带 run。
2. **Event / Step / AgentState 分工**：Event 是「发生了什么」，Step 是「这一轮整体如何」，AgentState 是「某个 tick 的个体快照」，不能混用。
3. **索引先行**：`AgentState` 写入前检查/创建 `(run_id, drone_id, step_index)` 等复合索引；否则百万级标签扫描会到秒级。

### 3.3 查询资产

- `simulation/graph_query.py`：只读 Cypher 服务。
  - 词法白名单（只允许 MATCH/RETURN/WITH/UNWIND/只读 CALL/SHOW 索引）。
  - 数据库 `EXPLAIN` 校验 `query_type == "r"`，事务最后不 commit。
  - 上限：200 行、32,000 字符、5 秒默认超时、单连接池。
- `scripts/lade_llm_context_templates.py`：i0–i55 共 56 条「决策上下文」查询，覆盖 self / task / event / energy / peer / memory / local / global / feedback / recovery 等类别。
- `scripts/lade_cypher_templates.py`：q0–q55 基准模板，按 smoke / online / analytics / collaboration / resilience / quality 六类组织。
- `scripts/concurrent_neo4j_query.py`：100 agent 并发压测，逐请求 JSONL、p50/p95/p99、QPS、成功率、连接池参数。
- `scripts/lade_cypher_benchmark.py`、`lade_llm_context_queries*.py`：分阶段计时、冷/热缓存、查询包级汇总。

这些资产被当前仓库映射为 `backend/query_catalog/kg56_mapping.json`：56 条 i 查询 → 11 个仓库查询包；其中 28 条 covered、23 条 warehouse-adapted、4 条 planner-owned、1 条 not-applicable，**没有一条声称与无人机语义一一对应**。

### 3.4 性能证据与边界

KG 项目自己的历史结果：

- 100 并发 `agent-state`（100 次成功、0 失败）：平均 240.339ms、p50 238.764ms、p95 294.416ms、p99 302.609ms、max 303.965ms、303.7 qps。
- 但这是**同一类查询**、100 个客户端循环使用 50 个 drone ID 的结果，不是 100 个不同智能体的完整业务查询。
- 12 类上下文查询在**没有属性索引**时出现秒级：i1 平均 2.47s、i6 5.55s、i7 5.29s；建立 `AgentState(run_id, drone_id, step_index)` 等索引后，该组 p95 约 301ms、最大 653ms，且 i2 还有 `BETWEEN` 语法错误。
- 结论：**索引、查询模板、run/时间窗约束**决定成败；节点数本身不说明性能。

这些数字不能直接当作仓储项目的验收结果，因为数据、schema、查询和硬件都不同。

### 3.5 与当前仓库的映射

| KG_Embodied | warehouse-dashboard | 迁移方式 |
|---|---|---|
| `Run` / `Drone` / `Task` | `Run` / `Robot` / `WarehouseTask` | 语义替换，保留 run 隔离 |
| `Region` / depot | `Warehouse/Zone/Rack/Location` / 工位 | 换成仓库空间模型 |
| `Event` / `Step` / `AgentState` | `RuntimeEvent` / 提交水位 / `AgentState` | 保留「事件-摘要-快照」三层 |
| i0–i55 查询 | 11 个知识包 + 56 条映射 | 只迁移查询意图，不搬无人机 Cypher |
| `graph_query.py` | `kg.html` + 预置查询 | 暂未开放任意 Cypher；当前以预置追溯为主 |
| 100 并发压测 | `query_v2` / `real_scale` / `query_catalog` | 方法已迁移，标准化验收未完成 |
| LLM 调度 | 当前分支不交付 | 明确排除，避免把 LLM 放进实时控制回路 |

## 四、当前项目的目标

### 4.1 三层目标

**第一层：课题/研究目标**（`KG_Embodied/项目目标.txt`）

面向边端具身智能的多设备协作知识管理，解决多智能体知识隔离、决策信息不完整、跨设备协同效率低的问题；重点是多智能体共享记忆与知识库、实时推理引擎、多模态智能体、数据中间件；关键技术是时序图谱构建、自然语言交互式查询优化、云边端协同数据治理；最终形成分布式知识管理引擎原理样机并在多智能体协同探索场景验证。

牵引性指标：

- 向量、图、时序统一数据管理；
- 百万规模图数据下，**云端单节点跨模态复杂查询 ≤200ms**；
- 支持 **≥100 个智能体节点**的时序知识图谱协同查询，**端侧具身设备百万规模图查询 <500ms**；
- 在 Megaverse、RoCo、EmbodiedBench 等 benchmark 上达到国际领先（此项当前项目未涉及）。

**第二层：Task2 指标**（`KG_Embodied/task2指标.txt`）

> 指标 1.2：支持 ≥100 个智能体节点的时序知识图谱协同查询，端侧具身智能设备下百万规模图数据下查询延迟低于 500ms。

考核方式：第三方测试；统一构建的标准化测试数据集（百万级图 + 向量 + 时序），在指定硬件/软件环境，自动化工具记录平均响应、并发吞吐、稳定性；云端单节点、100+ 智能体并发、端侧设备各不少于 3 轮；以实测平均查询时间与连续稳定运行作为判定，形成性能测试报告。

**第三层：平台/阶段目标**（`warehouse-dashboard/AI_PROJECT_HANDOFF.md`）

用 100 机器人仓储场景承载上述研究，先完成可见闭环：

```text
测试 CSV 数据集 → 静态仓库图谱 → V5/4173 仿真 → 运行态图谱写入 → 回放与图谱查询
```

当前优先级：**数据集 → 静态图谱 → 4173 实时执行/写图 → 图谱查询**；压测和最终优化不属于当前代码交接阶段。原话还明确：不要为了保留旧演示动画而回退 CSV 数据源或机器人自主写图逻辑。

### 4.2 指标口径（必须说清）

1. **「100 个智能体」是并发查询口径**。迁移审计已确认：任务里的 100 个智能体指 100 个智能体并发查询知识图谱，不是 100 台机器人同时执行搬运。当前项目两者都做，但必须分别计量：机器人执行并行（100 台）≠ 查询并发（100 客户端）。
2. **百万级是「图 + 向量 + 时序」总量**，不是单看节点数。需要同时有 `AgentState`/`Event` 时序数据、图关系、向量/特征数据，并能跑跨模态查询。
3. **500ms 是端侧平均/分位口径**，200ms 是云端单节点跨模态口径；不能拿一次热缓存查询或页面帧率代替。
4. **第三方测试**要求标准化数据集、指定硬件、3 轮、云端/并发/端侧三类环境，输出平均、吞吐、稳定性报告。KG 项目的历史结果与 wz 的 S9 结果都只是内部证据，不是第三方验收。
5. **不包含**：LLM 调度/自然语言控制不在当前分支交付范围；LLM 只能作为后续受限查询/建议层，不能进实时主控制回路。

## 五、对当前工作的判断

1. **先合并，再加功能**。当前分支已有 wz 的布局/调度核心，缺的是 live console、resource graph、query views 和数据资产；这些正是「实时统一」和「查询长尾」的关键。
2. **先提交工作区，再合并**。回放录制、14185 服务、启动脚本是独立的一批改动；不要和分支合并混在一起。
3. **实时入口应统一到 V5 提交点**。14186 是 V5 真实协调器；14183/14185 是历史回放；4173 是旧 `SimulationCoordinator` + 坐标映射。正确目标不是让三个页面长得一样，而是让同一 `runId` 在三个地方读到同一份已提交事实。
4. **性能验收要单独排期**。先把「同一 run 的实时/回放/图谱一致」做出来，再用标准数据集、100 客户端、云端/端侧三类环境做 3 轮压测；不要用 1046 万节点或单次查询宣称达标。
5. **修复 `live` 入口**。合并 wz 的 `ops/warehouse_live*.py` 后，`python -m backend.warehouse live` 才能工作；否则应删掉该入口，避免误导。
