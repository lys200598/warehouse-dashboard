# 图谱节点关系优化空间评审

## 任务背景

参考 KG_Embodied 的时态图谱设计，评估当前仓库图谱的节点和关系是否仍有优化空间，并避免为了图谱规模而过度拆分。

## 关键结论

- 当前静态核心节点和运行态核心节点已经足够支撑任务追溯、机器人追溯和状态回放，不应重做基础模型。
- 最有价值的下一层节点是低频 `RunFrame`（或 `WarehouseState`）：每个状态采样 tick 一条，保存任务完成/等待/执行数、活跃机器人数、阻塞数、低电量数等全局摘要。
- `RunFrame` 应通过 `(:RunFrame)-[:IN_RUN]->(:Run)` 表示，并与同 tick 的 `AgentState` 以属性 tick 对齐；不必给百万个状态都额外建立 `IN_FRAME` 关系。
- 任务生命周期应优先使用 `RuntimeEvent`：`task_assigned`、`task_picked_up`、`task_completed`、`task_blocked`、`charge_started`、`charge_completed`；Execution 保存派发/取货/完成 tick 摘要。
- 若后续实现电量与充电，应增加静态 `ChargeStation`（可复用 Location 的 kind=charge）和事件关系，不应马上新增“Battery 节点”。
- 若后续实现路径规划，可增加 `RoutePlan` 作为一次任务执行的计划节点；但逐步路径点应存为压缩属性或外部轨迹文件，不应每步建立 PathPoint 节点。
- 货位占用的完整逐 tick 历史不应直接图谱化；只有库存变化事件或低频聚合快照值得保存。

## 执行过的操作

- 对照 KG_Embodied 的 `Run—Step—AgentState—Event` 分层、Step 查询和 LLM 图谱上下文模板。
- 对照当前仓库的静态节点、Execution 生命周期、AgentState 与 RuntimeEvent 模型。

## 修改内容

- 本次仅进行模型评审，没有修改产品代码。

## 后续建议

1. 现在可做：增加低频 `RunFrame` 全局摘要，为回放提供完整的任务/集群指标。
2. 随调度功能做：增加任务阻塞、充电、协助等 RuntimeEvent 类型，并更新 Execution 生命周期字段。
3. 仅在路径规划落地后做：增加 RoutePlan，不创建每一步路径节点。
4. 暂不做：电池节点、状态类型节点、每 tick 的货位节点、每一步路径节点；这些会放大数据量而不提升当前查询价值。
