# 多日数据与 dev_261028 生成规则对比

## 任务背景

对比 `wz/warehouse-design` 分支的连续多日生成器（`backend.wide.multiday`）与 `dev_261028` 分支现有生成脚本，明确两类数据的生成规则、图谱用途和不可直接混用的边界。

## 关键结论

- `dev_261028` 已经包含 `backend/wide/multiday.py`。它和协作者最新分支的多日生成逻辑实质相同；本次逐文件比较仅发现一处变化：协作者将参考容量提示从固定 `1728` 改为按实际地图的 `len(slots)` 动态生成。因此，`MULTIDAY_DATASET.md` 的七类负载、连续库存和跨日规则可直接用于理解 `dev_261028` 内的该入口。
- 两者的主任务包都使用相同七字段 CSV 和 `initial_inventory.csv` / `manifest.json`，可以复用静态图谱的基本任务、货物、货位和时间模型。
- `dev_261028` 额外的 `generate_warehouse100_dataset.py` 是单日、均衡、确定轮转生成器：1728 容量、864 初始库存、默认每件初始货物做 4 次“出库后 300 秒入库”，因此固定生成 6912 条任务（3456 IN + 3456 OUT）。
- 两个分支共有的多日生成器则是连续库存状态机：默认七天 50112 条，货物、待完成参考事件和货位可用时间跨午夜保留；七天分别覆盖均匀、峰值、空间热点、批次、热点迁移、潮汐和混合恢复。
- `dev_261028` 的期限统一固定为发布时间后 1800 秒；多日生成器按静态路网距离、公共空驶余量、取放时长和 900 秒裕量逐任务计算期限。
- `dev_261028` 的端口按任务序号轮转，位置与时间分布近似均衡；多日生成器可产生每小时峰值、48 条同秒批次、空间热点和进出潮汐，因此更适合验证调度、图谱追溯和查询在不同负载下的表现。
- 多日数据比 `dev_261028` 单日生成器多出 `profiles-report.json` 与 `reference-inventory.json`，可以作为 Dataset 的场景元数据和图谱审计附件；两者都不应把这些参考报告误标为真实机器人执行结果。
- `scripts/generate_warehouse_dataset.py` 与 `scripts/generate_million_runtime_dataset.py` 不是可执行仓库任务包：前者是旧的扁平图谱实验 CSV，后者只是百万级 AgentState/Event JSONL 压测数据，不能替代 V5 输入。
- 协作者最新逻辑边界允许 `INBOUND` / `OUTBOUND`；`dev_261028` 的静态导入器仍要求 source/target 都在位置表中，因此若启用逻辑边界，需要先扩展导入器以登记逻辑边界节点或使用协作者的转换/图写入实现。

## 后续建议

- 若目标是图谱闭环演示和多样化调度回归，以协作者多日生成器为主，保留 `dev_261028` 单日包作为最小闭环冒烟数据。
- 静态图谱导入前先按数据包的 `scene_sha256` 选择对应布局和位置表；不要用 1728 货位数据包导入 1920 货位布局。
- 接入逻辑端点前，先升级 `dev_261028` 图谱导入校验：允许 `INBOUND` / `OUTBOUND` 作为显式业务边界节点，并把计划端点与运行时实际端口绑定分开写入。
- 百万级图谱规模不要简单扩大任务 CSV；应结合多日任务、100 机器人状态采样、执行事件与保留策略，按 run ID 分批写入与查询。
