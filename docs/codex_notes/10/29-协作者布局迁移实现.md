# 协作者布局迁移实现

## 任务背景

将协作者 `wz/warehouse-design` 的最新扩展仓库布局迁移到以 `dev_261028` 知识图谱功能为基础的分支，保留协作者的布局、端口选择、充电/调度相关能力，同时保持原有静态图谱与运行态图谱闭环。

## 关键结论

- 已迁入 `balanced` 扩展布局：100×90m、40 架、1920 个货位、100 个物理充电/待命泊位，布局版本为 `warehouse100-expanded-balanced-v1`。
- 扩展布局与旧 90×76m、1728 货位 V2 布局并存；默认布局未被悄悄替换，旧实验可继续复现。
- 图谱静态导入器现在支持逻辑 `INBOUND` / `OUTBOUND`：它们作为非物理计划端点写入 `Location`，不会虚构为某一实际工位。
- 新数据包必须与同一布局的 `layout.json`、`task-locations.csv` 及 manifest SHA 一起使用；1920 货位布局的单日默认生成结果为 960 初始库存、7680 条任务。
- 迁入协作者的布局加载、候选布局、逻辑端点选择、端口压力、能力及调度更新；补齐了依赖模块 `backend.boundary_contract`。
- V5 平衡布局冒烟运行成功：100 机器人、1920 条一轮任务输入、10 秒运行，成功生成 `latest.json`、`frames.sqlite` 和 `checkpoint.json`。
- 未修改 4173 页面以渲染新布局；4173 与 V5 的实时统一仍是后续独立工作。

## 执行过的操作

- 在 `dev_261028-layout-migration` 分支比较并选择性迁移协作者布局相关代码。
- 迁入 `backend/wide` 的布局加载、逻辑端点、候选布局、能力、仿真和图写入适配，以及 V5 调度/端口策略所需模块。
- 运行 `./.venv/bin/python ops/generate_balanced_layout.py --output data/layouts/expansion-candidates/balanced` 生成并校验布局资产。
- 用 `scripts/generate_warehouse100_dataset.py` 为新布局生成临时数据包，并用 `scripts/import_warehouse_neo4j.py` 完成静态图谱离线干跑校验。
- 用 `backend.warehouse convert-boundaries` 生成逻辑端点任务包，并验证静态导入将其登记为非物理计划端点。
- 使用扩展布局完成一次 V5 10 秒、100 机器人、带帧记录的冒烟运行。
- 执行 `compileall`、`git diff --check` 与 30 项图谱、CLI、多日数据相关单元测试。

## 修改内容

- 新增 `data/layouts/expansion-candidates/balanced/` 的布局、位置表及几何审计文件。
- 新增/更新 `backend/wide`、`backend/scheduling_v5` 与 `backend/boundary_contract.py`，支持 1920 货位布局和运行时物理端口绑定。
- 修改 `backend/warehouse_graph.py`：支持逻辑边界 Location 节点与 `boundary_routing_json` 数据集元数据。
- 修改 `backend/warehouse/__main__.py`：避免将未启用的可选资源图参数传给旧知识运行时；该分支仍使用原有运行态图谱写入器。
- 更新 `启动与图谱数据操作手册.md`，增加新布局的数据生成、图谱导入和 V5 运行命令。
- 增加静态图谱对逻辑端点的单元测试。

## 后续建议

- 启动 Neo4j 后，按操作手册用扩展布局重新生成正式数据包并导入；旧 1728 货位 Dataset 与新 Dataset 可同时保留。
- 若采用自由端口调度，先通过 `convert-boundaries` 创建新数据包，再按 run ID 查询实际端口绑定事件。
- 后续将 4173 画布改为读取运行指定的布局 JSON，并由 V5 提交点推送实时帧，才能在同一实时页面看到新布局的搬运过程。
- 迁移完成后由用户在本地执行 `git add` 与 `git commit`；不要把临时 `/tmp` 冒烟输出加入仓库。
