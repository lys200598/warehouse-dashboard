# 协作者多日数据集分析

## 任务背景

阅读 `wz/warehouse-design` 分支最新的 `docs/MULTIDAY_DATASET.md`，识别协作者提供的连续多日任务数据的结构、运行边界，以及它和本项目知识图谱链路的对接条件。

## 关键结论

- 该数据集是确定性生成的合成仓储边界任务，不是来自真实订单、吉林数据集或已经执行的机器人轨迹。
- 默认完整样例覆盖 7 天、50,112 条任务：前 6 天每日 6,912 条，第 7 天 8,640 条；初始库存 864 件，任务、货物和库存状态跨午夜连续。
- 核心输入仍遵循七字段 CSV 契约：`task_id, task_type, goods_id, release_time, due_time, source_id, target_id`，因此可作为静态任务、货物、货位及时间关系的图谱输入。
- 每个数据包还包含 `initial_inventory.csv`、`manifest.json`、场景分布报告、参考库存报告和独立校验报告；这些文件适合写入数据集来源、校验摘要和场景元信息，不应被混同为真实运行结果。
- `MULTIDAY_DATASET.md` 中随附的七日样例绑定旧地图：90×76m、36 架、1,728 货位、具体 `IN-1…OUT-8` 端点。它不能直接换到协作者最新的 100×90m、40 架、1,920 货位地图运行。
- 协作者最新的自由边界机制允许 CSV 写入 `INBOUND` / `OUTBOUND`，仿真在运行时选择实际物理工位。图谱应同时保存静态计划端点和运行时已绑定的实际工位，不能用实际工位覆盖原任务计划。
- 多日数据本身不包含机器人轨迹、任务分配、电量、充电、故障或 Neo4j 快照；这些必须在 V5 运行时生成，再以运行 ID 写入动态图谱。

## 修改内容

## 后续建议

- 将七日样例保留为旧地图的可复现实验基线，不要直接导入新地图运行。
- 若采用协作者最新布局，先用 `backend.warehouse convert-boundaries` 生成一个独立的新数据目录，再运行 `validate`；如地图容量从 1,728 改为 1,920，还应重新生成或迁移符合新地图摘要的初始库存与任务包。
- 图谱导入应按“数据集静态层”和“运行态层”分开：静态层导入任务、货物、货位、计划端点与元数据；运行态层按 run ID 写入机器人状态、执行、物权变化和实际工位绑定。
- 前端实时页面若接入该数据，应订阅 V5 运行提交点；不能将 CSV 的计划端点直接渲染成已经发生的机器人搬运事实。
