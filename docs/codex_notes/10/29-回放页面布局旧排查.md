# 回放页面布局仍是旧的排查

日期：2026-10-29
回放服务：`http://127.0.0.1:14185/wide.html`
相关实时页：`http://127.0.0.1:4173/`（当前为停止状态；最后运行的是 medium 120）

## 一、结论

- **回放页面本身没有写死旧布局。** `dist/wide.js` 每次根据所选 run 的 `/api/scene` 动态取 `spec.width/depth/racks/capacity`，不存在固定 36 架/1728 货位的渲染常量。
- **旧布局来自所选 run 的 checkpoint。** 14185 原来只扫描到 5 个旧 run，默认选中 `console-warehouse-3fafa0f3f4cb`，其场景是旧控制台：**32.9×22.75、15 架、540 货位**，所以看起来还是旧布局。
- **medium live 的记录不会出现在回放里。** medium live 目录 `data/local-runs/wh-live-*` 只有 `latest.json`、`checkpoint.json`、`journal.sqlite`，**没有 `frames.sqlite`**；`backend/replay_service.py` 要求三者齐全，所以 medium live 的 run 不被列出。
- 已补一个 **medium 批量记录** `medium-replay-smoke`，带完整 `frames.sqlite`、120×90/48 架/2304 货位；现在 14185 会把它作为最新/当前 run，回放页应显示 120 布局。

## 二、证据

### 2.1 14185 原来的 run 列表

```text
console-warehouse-3fafa0f3f4cb  recorded      frames 1472  scene 32.9×22.75 / 15 racks / 540
visual-demo-20261028-160823     wall-time-limit frames 708  old 90×76
day1-full-20261028-155739      recorded      frames 611  old 90×76
day1-history                   wall-time-limit frames 1300 old 90×76
smoke-v5-20261028-153030       complete      frames 2    old 90×76
```

默认排序把 `console-warehouse-...` 放在前面（最新/当前），所以打开就是旧 32×22 布局。

### 2.2 回放页是动态的

`dist/wide.js:172-179`：

```js
const [data] = await Promise.all([fetchJSON(api('/api/scene')), refresh()]);
const scene = data.scene || data;
state.scene = scene;
set('sceneSize', `${scene.spec.width}×${scene.spec.depth}m`);
set('bayCount', canonicalBays(scene).length);
set('slotCount', scene.capacity ?? scene.racks.reduce((sum, r) => sum + r.capacity, 0));
```

所以布局完全由 `/api/scene` 决定；旧布局是旧 run 的 scene 数据。

### 2.3 为什么 medium live 不在列表

`backend/replay_service.py:44-45` 的扫描条件：

```python
if not all((directory / name).is_file() for name in
           ("latest.json", "frames.sqlite", "checkpoint.json")):
    continue
```

medium live 的 `wh-live-*` 目录：

```text
checkpoint.json
journal.sqlite
latest.json
live-manifest.json
writer.jsonl
```

没有 `frames.sqlite`，因此被过滤。`ops/warehouse_live_runtime.py` 只写 `latest.json`/checkpoint，不写帧库；这是 live 与 replay 的边界，不是回放页 bug。

## 三、已做的修复

我用原生批量运行生成了一个完整的 medium 回放记录：

```bash

  --scene data/layouts/expansion-candidates/medium/layout.json \
  --dataset data/examples/wheeled-medium-sample19 \
  --config-json config/wheeled-medium-100.json \
  --output data/local-runs/medium-demo-1800 \
```

注意：这是批量回放记录，不是 4173 live 的实时镜像；它用于让回放页和 120 布局一致。启动 4173 live 是另一个入口，见下一节。

## 四、如果要在回放里看到 4173 live

当前 `ops/warehouse_live.py` **不写 `frames.sqlite`**，所以无论 4173 跑多久，14185 都不会出现这个 live run。两个选择：

1. **批量重放**（已做）：用 `backend.warehouse run --frames` 生成同布局的回放记录；
2. **给 live 加帧录制**：在 `warehouse_live_runtime` 的提交点把 `sim.frame()` 压缩写入 `frames.sqlite`，并写 checkpoint/latest；这需要新增 recorder 和配置项，工作量更大。

如果不加帧录制，不要把 4173 live 的 runId 拿到 14185 里找；两个运行面不能混用。

补充：本次尝试在 4173 启动 medium live 时发现端口已被另一个进程占用（PID 2410213，runId `wh-live-20261029T120908Z-cef19fc8`，status=failed）。为了不误杀其他进程，本次没有停止它；因此 4173 live 当前仍是那个失败 run，回放侧使用刚生成的 `medium-demo-1800`。若要 4173 也跑干净的 medium live，先停 2410213，再执行：

```bash
kill -INT 2410213

./.venv/bin/python -m backend.warehouse live \
  --source-root . --dist dist/medium \
  --registry config/live-wheeled-datasets.json \
  --dataset-id medium1728 --output-root data/local-runs \
  --mode rules --knowledge-backend journal \
  --mobility wheeled --commit-seconds 5 \
  --max-active-robots 100 --port 4173
```
