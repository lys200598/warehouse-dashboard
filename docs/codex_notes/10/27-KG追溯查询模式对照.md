# KG 追溯查询模式对照

## 任务背景

用户认为当前仓库项目的任务/机器人追溯功能局限，要求参考 KG_Embodied 的实际图谱查询设计，明确可迁移的追溯方式。

## 关键结论

- KG 的追溯不是单个“详情页”，而是围绕决策和诊断组织的一组受限查询包。
- KG 基础查询覆盖：自身当前状态、截至目标 Step 的最新状态、历史轨迹、当前任务、近期事件、近期绩效、区域负载、同区域协同者、临期任务、全局 Step 摘要、区域事件和全局瓶颈。
- 当前仓库已有任务静态链路、Execution、AgentState、RuntimeEvent，已能直接实现机器人状态/轨迹/事件、任务全链路、同 tick 机器人分布和运行批次统计。
- 当前仓库缺少 RunFrame 全局摘要、精确任务生命周期时间、阻塞/充电事件和空间区域标签，因此尚不能严谨实现全局瓶颈、临期风险、充电协助等追溯。
- 应新增“仓库追溯查询包”，每个查询都必须以 Run、tick 或时间窗口为边界；不建议开放任意 Cypher 或继续堆叠详情卡片。

## 执行过的操作

- 阅读 KG_Embodied 的 `scripts/lade_llm_context_queries.py` 和 `scripts/lade_llm_context_templates.py`。
- 对照当前仓库的 `WarehouseTask`、`Execution`、`AgentState`、`RuntimeEvent` 和已有查询接口。

## 修改内容

- 本次为查询设计评审，没有修改产品代码。

## 后续建议

1. 第一批直接实现：机器人截至 tick 的最新状态、机器人近 N 个采样轨迹、机器人近期事件/任务绩效、任务执行时间线、同 tick 集群状态分布。
2. 第二批随模型补充实现：RunFrame 全局摘要、临期任务、货架/区域负载、阻塞诊断。
3. 电量功能完成后实现：低电量历史、充电站访问、可协助机器人候选。
4. 页面将查询包按“机器人 / 任务 / 集群 / 异常”四类呈现，输入 Run 与 tick 后自动带入上下文；不要要求用户手工猜 Task ID。
