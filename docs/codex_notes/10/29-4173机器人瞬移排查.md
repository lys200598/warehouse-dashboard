# 4173 实时仿真机器人瞬移排查

日期：2026-10-29
范围：只读排查 4173 页面显示；未修改代码、未重启服务、未改变仿真速度。
结论先行：**后端物理位置是连续的，瞬移来自 `dist/app.js` 的前端可视化映射层**，由 `17dccfe`（今天的布局迁移提交）引入。

## 一、结论

1. **不是调度/交通/路径问题**。对 4173 WebSocket 连续采样 85 帧，`tick` 每次只加 1，100 台机器人相邻帧的实际位移最大 1.20 单位，没有任何一帧超过 2.5 单位；阶段切换时的实际位移最大约 1.06 单位。后端位置是平滑的。
2. **前端 `visualTaskPoint()` 的插值公式写错了**：它把「上一帧已经插值过的显示位置」当作新的起点，又用「整段路程的累计进度」作为插值比例，导致每帧位移 = `progress × 剩余距离`。进度到 20% 时，一帧就会跨过剩余距离的 20%；60 单位的路程一帧跳 12 单位。
3. **两套坐标系在 `placing → returning` 处直接切换**：`placing` 用扩展布局的工位/货架坐标（例如出库位 `x=92.4`），`returning` 却用 `mapLegacyPoint()` 把 32×22 控制坐标映射到 82×76 工作区（例如 `x=43.3`）。一次切换跳 49.09 单位。
4. **4× 倍速放大了问题**：当前 `/api/snapshot` 的 `speed=4.0`，每个 tick 前进 1 个模拟秒、约 1.2 单位；进度每帧涨约 5%~7%，比 1× 时快 4 倍，所以瞬移更频繁、幅度更大。
5. `17dccfe` 之前的版本直接使用 `payload.x/payload.y` 作为 `renderTarget`，没有这层映射。`git show 17dccfe^:dist/app.js` 可确认；瞬移是布局迁移时新引入的显示回归。

## 二、证据

### 2.1 后端位置连续（WebSocket 采样）

对 `ws://127.0.0.1:4173/ws/simulation` 连续采样 45 秒：

```text
messages 85
tick range 16040 -> 16124
tick gap counts {1: 84}      # 每帧 tick 只 +1，没有丢帧
speed values [4.0]
big jumps >2.5: 0            # 实际坐标没有任何瞬移
max displacement per tick gap 1: 1.20 (均值 0.015)
```

最大 1.20 单位/帧正是 4× 下的正常值：`step_seconds 0.25 × speed 4 × 机器人速度 ~1.2 = 1.2`。阶段切换（`toRack→placing`、`toPick→picking`、`returning→idle`）的实际位移也都在 1.06 以内。

### 2.2 前端显示位置在跳

按 `dist/app.js` 的 `visualTaskPoint()`、`mapLegacyPoint()`、`slotGeometry()` 逐行复刻成 Python，用同一批实时快照计算「页面实际会画在哪里」：

```text
messages 46, ticks 16331 -> 16376, speed 4.0
visual jumps >2.0: 67，其中 same-stage: 62
```

典型样本：

| 机器人 | 阶段 | 两帧显示位移 | 说明 |
|---|---|---:|---|
| id 32 | `toPick→toPick` | **10.72** | `(39.8,31.0) → (33.3,39.6)`，进度 15.3%→20.3%，目的地 IN-8 (7.6,73) |
| id 40 | `toRack→toRack` | **14.66** | `(55.1,49.0) → (44.7,38.7)`，进度 31.9%→36.8% |
| id 89 | `toRack→toRack` | **18.68** | `(33.6,16.8) → (52.3,16.8)`，出库位 92.4 |
| id 89 | `placing→returning` | **49.09** | `(92.4,17.0) → (43.3,16.5)`，从扩展出库位切到 legacy 映射 |
| id 33 | `placing→returning` | **16.53** | `(22.5,16.7) → (34.8,27.8)` |
| id 40 | `placing→returning` | **15.72** | `(22.5,16.7) → (33.6,27.8)` |

注意：67 次跳变中 62 次发生在**同一阶段内部**。其中 `toPick` 22 次、`toRack` 14 次，是下面 3.1 的累进插值直接造成；`returning` 26 次是 `mapLegacyPoint` 把 32×22 放大到 82×76（x 方向 2.56 倍、y 方向 3.45 倍）后的正常位移放大（实际 1.2 单位会显示成 3~4 单位），不是主因。真正肉眼可见的瞬移是 10~18 单位的 `toPick/toRack` 跳变和 49 单位的 `placing→returning` 跳变。

## 三、根因

### 3.1 累进插值：`lerp(上一帧显示位置, 目的地, 累计进度)`

`dist/app.js:275-299`：

```js
const start = previous
  ? { x: previous.renderTargetX ?? previous.x, y: previous.renderTargetY ?? previous.y }
  : mapLegacyPoint(payload);
const progress = clamp((payload.distanceTravelled || 0) / Math.max(0.001, payload.stageDistance || 0), 0, 1);
return { x: lerp(start.x, destination.x, progress), y: lerp(start.y, destination.y, progress) };
```

`previous.renderTargetX` 是**上一帧的显示位置**，`progress` 是**整段路程的累计进度**。于是：

```text
v_n = (1 - p_n) * v_{n-1} + p_n * d
每帧位移 = p_n * |d - v_{n-1}|
```

而不是正确的：

```text
v_n = anchor + p_n * (d - anchor)
每帧位移 = (p_n - p_{n-1}) * |d - anchor|
```

当 `p=0.2`、剩余距离 60 时，一帧就跳 12 单位；`p` 越大跳得越多，直到接近终点才收敛。1× 时 `p` 涨得慢，但累计到 20% 时同样会跳；4× 时每帧涨 5%~7%，所以几乎每帧都在跳。

### 3.2 `placing → returning` 坐标系不一致

- `placing` 分支（`dist/app.js:289-291`）返回扩展布局的坐标：出库位 `outboundPoint(id)` 来自 `layout.stations`，`x=92.4, y=17..73`；入库则是 `rackTarget()` 的扩展货架坐标。
- `returning` 没有专门分支，落到最后的 `mapLegacyPoint(payload)`（`dist/app.js:133-142`）：
  - `x = 9 + clamp(x,0,32) * 82/32`
  - `y = 7 + clamp(y,0,22) * 76/22`

出库完成后，机器人从 `(92.4,17.0)` 瞬间切到 `(43.3,16.5)`，单帧 49.09 单位；入库完成则从扩展货架 `(22.5,16.7)` 切到映射区 `(34.8,27.8)`，约 15~17 单位。

这不是「运动快」，而是同一台机器人在两套坐标系之间切换。`mapLegacyPoint` 的注释也写明：4173 的协调器仍是 32×22 控制仿真，位置只应显示在扩展地图的工作包络内；`visualTaskPoint` 的任务阶段却用了扩展布局的真实工位/货架坐标，两者混用。

### 3.3 4× 倍速与浏览器掉帧放大

- 当前 `speed=4.0`：每 tick `delta_seconds=0.25×4=1.0` 模拟秒，机器人每帧约 1.2 单位。
- 进度 `progress` 每帧涨 `1.2 / stageDistance`；路程 18 单位时约 6.7%/帧，所以 3 帧就从 0% 到 20%，第四帧开始出现 10 单位级跳变。
- `backend/server.py:343-353` 的 WebSocket 队列 `maxsize=1`：浏览器稍慢就会丢快照。`dist/app.js:1704` 只有 `snapshot.tick === lastBackendTick+1` 才做连续插值；丢帧时 `continuous=false`，`origin` 直接取新位置，机器人会**整段吸附**到新目标，进一步放大瞬移感。
- `backend/server.py:409-410` 的循环只保证最小间隔，不补帧；页面按约 1.8 帧/秒接收，4× 下每帧信息量大，视觉更容易抖动。

### 3.4 附带问题：`rackId` 与 `slotId` 不同源

`rackId` 来自控制器的 `state.rack_id`（1~15 台控制货架），`slotId` 却是数据包的原始 ID（可能是 `R16`~`R40`）。`visualTaskPoint` 用 `rackById.get(payload.rackId)` 找到的是扩展布局的 1~15 号货架，再用 `R16...` 的 slotId 去里面找，找不到就回退 `rack.slots[0]`。这会让部分入库机器人的目标点落在错误的货架格位，但它解释的是「位置不对」，不是 49 单位瞬移的主因。

## 四、为什么之前没有

`git show 17dccfe^:dist/app.js` 中 `applyBackendSnapshot` 直接：

```js
renderTargetX: payload.x,
renderTargetY: payload.y,
```

没有 `visualTaskPoint`，机器人按后端真实坐标平滑移动。`17dccfe` 为了把 4173 的 legacy 控制状态画到 1920 货位扩展布局上，新增了 `visualTaskPoint` / `mapLegacyPoint`，但插值方式和坐标系没有统一，导致回归。

## 五、修复建议

### 方案 A：最小改动，保留「画在扩展货架/工位」的意图（推荐先做）

1. 每台机器人保存一个**阶段起点锚点** `visualAnchor`：
   - 阶段没变：沿用 `previous.visualAnchor`；
   - 阶段变化：锚点 = 上一帧的显示位置（`previous.renderTarget`），首次为 `mapLegacyPoint(payload)`。
2. `visualTaskPoint(payload, rack, slot, anchor)` 内改成：
   ```js
   return { x: lerp(anchor.x, destination.x, progress),
            y: lerp(anchor.y, destination.y, progress) };
   ```
   不再用 `previous.renderTarget` 当起点。
3. `returning` 也给一个稳定目的地：取 `payload.path` 最后一点（控制坐标）做 `mapLegacyPoint`，按 `distanceTravelled/stageDistance` 从 `placing` 的显示位置平滑过去，而不是直接 `mapLegacyPoint(payload)` 瞬切。
4. `idle/charging/queued/warning` 继续用 `mapLegacyPoint`；阶段切换时用锚点插值，避免硬切。
5. 修改后把 `dist/index.html` 的 `app.js?v=` 版本号改掉，强制浏览器刷新。

效果：同一阶段内每帧位移变成 `(p_n-p_{n-1})×路程`，4× 下约 2~3 单位/帧；`placing→returning` 从 49 单位硬切变成沿返回路径的连续滑动。

### 方案 B：坐标统一（更彻底，但外观会变）

不再使用扩展布局的 `rackTarget/outboundPoint` 作为任务阶段目的地，所有阶段都用：

```js
const point = mapLegacyPoint(payload.x, payload.y);
```

即完全按「控制器真实位置 → 工作包络」显示。优点：与 `mapLegacyPoint` 的设计注释一致，绝无坐标系跳变；缺点：机器人不再精确贴在 1920 布局的货架/工位上，视觉上会落在包络内的通道位置。若要画真实路径，可把 `payload.path` 逐点 `mapLegacyPoint` 后绘制。

### 方案 C：产品级投影（工作量最大）

建立一份「控制货架/工位 → 扩展布局货架/工位」的显式映射，任务阶段和 returning 都使用同一套映射后的坐标，再配合方案 A 的锚点插值。这样既能贴在扩展布局上，也不会瞬移。需要同时修正 `rackId`（控制 ID）与 `slotId`（数据集 ID）不同源的问题。

### 立即缓解

- 把页面速度切到 **1×**：不会消除根因，但进度每帧只涨约 1.7%，跳变幅度和频率都会明显下降，便于确认现象。
- 浏览器 **Ctrl+F5** 强制刷新，确认加载的是 `app.js?v=20261029-armfix`，排除旧缓存。
- 如果只是演示，可临时把 `visualTaskPoint` 的 `start` 改为固定的阶段起点，先压住最明显的跳变。
