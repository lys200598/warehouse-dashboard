# 页面刷新与任务续跑

## 任务背景

用户观察到 4173 页面刷新后会“重置”，询问已经完成的数据集任务会继续做还是从头开始。

## 关键结论

- **只刷新浏览器页面不会重置后端**。页面通过 `/ws/simulation` 重新连接，服务端继续用同一个 `runId` 推进；已完成任务不会重做。
- 页面刷新后“看起来重置”的是前端本地视图：相机、选中机器人、时间轴和本地事件列表会重新初始化；任务数、完成数、tick 会随后从 `/api/snapshot` 或 WebSocket 快照恢复。
- 当前实例验证：`runId=warehouse-3fafa0f3f4cb` 在多次检查中保持不变，tick 从 167 增长到 1491，说明刷新没有创建新 run。
- **重启后端进程**时：
  - 沿用同一 checkpoint 并加 `--resume`：从 checkpoint 恢复 `tick`、`elapsed`、`tasks`、`completed`、`dataset_cursor`、`dataset_ready` 和机器人状态；已完成任务不会重复派发。
  - 使用新的 checkpoint：新 runId，从第 1 条任务重新开始。
  - checkpoint 已存在但不加 `--resume`：服务会直接拒绝启动，避免误覆盖。
- **点击页面“重置”按钮**：明确调用 `_initialize_new_run()`，生成新 runId，`dataset_cursor=0`、`tasks={}`、`completed=0`，会从头开始。
- checkpoint 默认每 20 tick 保存一次；如果进程异常退出，恢复点之后最多 20 tick 的进度可能丢失并重做。正常停止时 `stop()` 会再保存一次。
- 已完成任务是否重做，取决于是否从 checkpoint 恢复；与浏览器刷新无关。

## 后续建议

1. 想继续当前 run：重启时使用原 checkpoint 并加 `--resume`；若代码已改，再加 `--allow-code-change`。
2. 想从头复现：使用新的 checkpoint 路径，得到新 runId。
3. 刷新前后用 `/api/health` 的 `runId` 与 `tick` 判断：`runId` 不变、`tick` 增长就是同一 run；`runId` 变化才是新 run。
4. 不要把页面“重置”按钮和浏览器刷新混为一谈：前者会真正清空进度，后者不会。
