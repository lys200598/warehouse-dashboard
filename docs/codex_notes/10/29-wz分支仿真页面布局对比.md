## 一、先看结论

1. 两个页面共用同一套「原版三栏调度台」外壳和 CSS，但**页面内容已经分叉**：
   - 当前 4173 是「旧控制台 + 1920 扩展布局映射」：顶部有 `kg.html` 和 14185 回放链接，左侧还是随机流量/插入任务，场景说明写死为 `32 × 22 单元`。
   - wz 14186 是「V5 真实运行控制台」：左侧是固定数据集、单步、保存检查点、另开 run；底部是共享知识查询；场景尺寸/货架/货位/泊位由 `/api/scene` 动态填写。
2. **仓库布局不是同一套**：
   - 当前 4173：页面加载 `balanced` 布局，**100×90m、40 架、1920 货位、16 工位、100 泊位**；但后端仍是 32×22 的旧控制世界，页面做了一层 `mapLegacyPoint` 映射。
   - wz 14186：真实 V5 场景，当前运行的是 `warehouse100-wide-v2`，**90×76m、36 架、1728 货位、16 工位、100 泊位**；没有坐标映射层，机器人直接按 V5 米制坐标绘制。
   - wz 最新分支额外提供 `medium` **120×90m、48 架、2304 货位（6×8）** 和 `large` **150×100m、60 架、2880 货位**；当前分支只有 `balanced`。
3. **渲染链路不同**：
   - 当前：`/ws/simulation` ← `backend.server` 的 `SimulationCoordinator` + 100 Ray actor；快照没有 `sourceKind`，页面走 legacy 分支，用 `/api/layout` 的 1920 布局 + `visualTaskPoint` 映射。上一轮排查的「瞬移」就出在这条分支。
   - wz：`/api/snapshot` ← `ops/warehouse_live.py` 的 V5 单写者；快照带 `sourceKind=live_simulation_memory`，页面通过 `original-platform.mjs` 的 `adaptPlatformFrame()` 转成视图模型，`renderTarget = payload.x/payload.y`，没有映射层。
4. wz 最新 4 个提交（`7db43b6` 之后）增加了：轮式仓库 `backend/wheeled`、`agent_runtime`、有限换电、机器人自主知识 IO、peak/day-window 回归数据、压测 GUI `dist/pressure-lab/`、可选 live 机器人激活上限。当前分支都没有。
5. 如果把 wz 的 `dist` 直接覆盖到 4173，**页面会进入 platform 模式但拿不到 `/api/scene` 和 `sourceKind`**，无法正确显示 V5 场景；两种页面不是简单换皮，后端入口也必须一起换。

## 四、渲染和数据链路对比

### 4.1 当前 4173：legacy 控制 + 布局映射

```text
backend.server (SimulationCoordinator + 100 Ray actor)
  → /ws/simulation（tick、x/y 为 32×22 控制坐标）
  → 页面 applyBackendSnapshot()
      ├─ 首次/重连：fetch /api/layout（balanced 100×90/40/1920）
      ├─ createRacks() 生成 40×48 个显示槽位
      ├─ mapLegacyPoint()：32×22 → 82×76
      └─ visualTaskPoint()：任务阶段再用扩展货架/工位坐标
  → renderTargetX/Y 为“映射后的显示坐标”
```

关键代码：
- `dist/app.js:133-142` `mapLegacyPoint`
- `dist/app.js:175-249` `createRacks`
- `dist/app.js:275-299` `visualTaskPoint`
- `dist/app.js:1650-1715` `applyBackendSnapshot`
- 后端：`backend/server.py`、`backend/simulation.py`

这条路径就是上一轮「机器人瞬移」的来源：任务阶段混用扩展布局坐标，`returning` 又切回 legacy 映射；`visualTaskPoint` 还用上一帧显示位置当起点、累计进度当比例。

### 4.2 wz：V5 真实帧 + 显式适配器

```text
ops/warehouse_live.py（V5 单写者）
  → /api/snapshot（sourceKind=live_simulation_memory，x/y 为真实米制坐标）
  → 页面 applyBackendSnapshot()
      ├─ 校验 runId/runtimeInstanceId/tick
      ├─ /api/scene 取真实场景
      ├─ adaptPlatformFrame(raw, scene, previous)
      │    ├─ 生成 scene.racks/slots（真实 48/架）
      │    ├─ 机器人 x/y 直接使用真实坐标
      │    └─ 轨迹只做连续帧观察，不伪造路径
      └─ renderTargetX/Y = payload.x/payload.y
```

关键代码：
- `dist/original-platform.mjs:5-40` `adaptPlatformFrame`
- `dist/app.js:1618-1636` platform 分支
- `dist/live-model.mjs` 帧校验/时钟
- `ops/warehouse_live.py`、`ops/warehouse_live_runtime.py`

因此 wz 页面没有 `mapLegacyPoint`/`visualTaskPoint`，机器人位置由 V5 真实坐标直接决定；页面尺寸、货架数、货位数、泊位数都来自 `/api/scene`，不是写死。

## 六、如果要把两边统一，应该注意什么

1. **不能只复制 `dist/index.html` 或 `app.js`**。wz 页面依赖：
   - `/api/snapshot` 的 `sourceKind=live_simulation_memory`
   - `/api/scene`、`/api/scene-point`
   - `ops/warehouse_live.py` 的 run/dataset/控制协议
   4173 当前都不提供，直接覆盖会显示空白或退回 legacy 分支。
2. **两种“布局”要分开决策**：
   - 页面布局：wz 的三栏外壳 + 数据集/单步/知识查询，是 V5 正式控制台；当前 4173 是旧控制台。
   - 仓库布局：当前 4173 的 100×90/40/1920 是页面映射目标，不是后端真实布局；wz 的 90×76/36/1728 是真实 V5；120 medium 是另一份 120×90/48/2304 资产。
3. **如果目标是消除 4173 瞬移**：优先修 `visualTaskPoint` 的固定锚点/坐标统一，或者把 4173 切到 V5 live 入口；不要指望换 wz 的 120 布局就能解决，因为瞬移根因是 32×22 → 100×90 的映射层，不是布局尺寸。
4. **如果目标是使用 120 布局**：需要整体迁移 `medium/layout.json`、`task-locations.csv`、`wheeled-medium-*` 数据、`backend/wheeled`、`config/wheeled-medium-100.json` 和 live 入口；不能只改 4173 的 `/api/layout`，否则控制世界仍是 32×22，会出现更严重的坐标错位。
5. **页面合并建议**：
   - 以 wz 的 `index.html`/`app.js`/`original-*.mjs` 为 V5 正式页面；
   - 保留当前分支的 `kg.html`、14185 回放入口、静态/运行态图谱 API；
   - 将当前 4173 保留为兼容/对照，或把它的 KG 查询入口并入 wz 的底部知识面板；
   - 统一后再用同一 `runId` 验证实时/回放/图谱三处一致。
