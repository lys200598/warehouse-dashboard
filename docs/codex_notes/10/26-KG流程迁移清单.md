# KG_Embodied 流程迁移清单

## 任务背景

当前仓储项目要参考 `KG_Embodied`，实现仓储机器人运行、百万级知识图谱、100 个智能体同时工作和图谱查询能力。需要确定应复现的端到端流程及功能边界，而不是将配送项目的代码和界面直接复制过来。

## 关键结论

- 应复现 `KG_Embodied` 的“配置启动 → 并行智能体运行 → 任务生命周期事件 → 图谱双层写入 → 查询/AI 消费 → 实时观测”的流程；不应复制无人机、城市路网、配送订单等领域实现。
- 当前项目已有仿真协调器、机器人 Actor、WebSocket 快照和基础仓储画布，因此运行控制与实时状态的骨架已存在；主要缺少可持久化图谱、任务事件出图、查询服务、批量生成/导入和性能验证。
- 图谱写入应以仓储仿真/WMS 的确定性事件为主。LLM 不应成为基础事实的写入者，而应作为后置的非结构化信息抽取和图谱辅助决策能力。
- 百万级图谱与 100 并发查询的关键不是把机器人数量参数改为 100，而是图数据库约束/索引、批量写入、读写隔离、参数化查询、缓存和专门的压测门禁。

## 执行过的操作

- 对照阅读 `KG_Embodied` 的动态运行前端、SSE 实时帧处理、图谱查询页面、`TemporalKnowledgeStore`、`Neo4jKnowledgeStore`、`LLMPlanner` 与 `RegionLLMCoordinator`。
- 对照当前项目已具备的仿真协调、机器人并行执行、实时快照和前端画布能力。
- 未运行服务，未修改业务代码、前端页面或数据。

## 修改内容

- 新增本文档，给出按流程迁移的能力清单、优先级和不应迁移项。
- 未修改现有项目实现。

## 后续建议

- 先确认 Neo4j 部署方式、图谱查询的真实业务样例与白板流程，再进入实现。
- 以本文的 P0 清单建立最小闭环，随后进行百万级数据导入和 100 并发查询基准测试。
- AI 功能应在结构化事件写图闭环完成后单独接入，并保留审核与回退机制。

## 一、应复现的主流程

`KG_Embodied` 的可迁移流程可以按下图理解：

```text
运行配置
  → 并行智能体/调度器执行
  → 产生任务状态与领域事件
  → 图谱写入层（短期事件 + 长期实体关系）
  → 图谱查询/API/缓存
  → 前端实时观测、回放、告警、AI 规划或检索
```

将其替换为仓储语义后：

```text
仓库/班次/机器人/任务配置
  → 100 个仓储机器人 Actor 与任务调度器
  → 分配、到货架、取货、搬运、放货、充电、异常事件
  → Neo4j 图谱（实体关系 + 时序事件）
  → 图谱查询服务与性能缓存
  → 仓储界面、任务追踪、负载统计、AI 辅助识别/问答
```

这条链路应作为本项目的复现目标。

## 二、功能迁移判断

| --- | --- | --- | --- |
| 运行参数与场景初始化 | 仓库布局、班次、机器人数量、任务源 | 应复现 | 将配置统一为可记录的运行批次 `Run`，并保存配置版本、随机种子和数据集版本。 |
| Ray/多智能体并行运行 | 机器人 Actor 与协调器 | 已有骨架，需强化 | 保留当前并行架构；明确 100 个活跃机器人的资源配额、失败隔离、任务取消和运行指标。 |
| 任务分配/规划 | 入库、出库、补货、搬运任务调度 | 复现思路，重写领域逻辑 | 复用“任务分配过程可记录”的思想，不能复用无人机区域调度代码。 |
| 生命周期事件记录 | 分配、移动、取货、放货、充电、故障 | P0 必须迁移 | 在状态机转换处发出规范事件，作为图谱事实唯一来源。 |

| SSE 帧流、回放、指标表 | WebSocket 状态流与仓储画布 | 可借鉴 | 保持当前界面风格；后续可增加事件流、时间回放、统计卡片，不复制 LaDe 视觉。 |
| LLM 规划器/区域协调器 | 智能调度或异常处理建议 | P2 后置 | 先用确定性调度；验证收益后再让 LLM 读取受限图谱上下文提出建议。 |
| LLM 图谱识别 | 工单、告警、维护日志、图像识别结果 | P2 后置 | 用 AI 输出候选节点/关系，经 JSON Schema、置信度、来源与人工审核后落图。 |

## 三、建议复现的仓储图谱写入流程

### 1. 静态主数据初始化

在一次运行或数据导入前，创建或更新稳定实体：

- `Warehouse`、`Zone`、`Aisle`、`Rack`、`Slot`
- `Robot`、`ChargingStation`
- `Cargo`、`TaskTemplate`（如有）

静态关系包括：

```text
(Warehouse)-[:CONTAINS]->(Zone)-[:CONTAINS]->(Rack)-[:HAS_SLOT]->(Slot)
(Robot)-[:OPERATES_IN]->(Warehouse)
(ChargingStation)-[:LOCATED_IN]->(Zone)
```

### 2. 运行批次创建

每次仿真/生产排程生成一个 `Run` 节点，记录：`run_id`、开始时间、配置版本、布局版本、任务数据集版本、随机种子和软件版本。

```text
(Run)-[:RUNS_IN]->(Warehouse)
(Robot)-[:PARTICIPATES_IN]->(Run)
```

这对应 `KG_Embodied` 中以日期、场景和运行过程组织动态数据的思路，也使回放与问题复现可追溯。

### 3. 任务状态机驱动图谱事件

不要由前端定时快照推导图谱事实。应在后端状态机发生以下转移时写标准事件：

```text
CREATED → ASSIGNED → MOVING_TO_PICKUP → PICKED_UP
→ MOVING_TO_DROPOFF → DELIVERED / FAILED / CANCELLED
```

每个 `Event` 至少含：`event_id`、`event_type`、`occurred_at`、`run_id`、`task_id`、`robot_id`、来源、幂等键、置信度（AI 来源时）和原始证据引用。

关键关系示例：

```text
(Task)-[:ASSIGNED_TO {at}]->(Robot)
(Task)-[:PICKS_FROM]->(Slot)
(Task)-[:DROPS_TO]->(Slot)
(Robot)-[:CARRIES {from, to}]->(Cargo)
(Event)-[:ABOUT_TASK]->(Task)
(Event)-[:ABOUT_ROBOT]->(Robot)
(Event)-[:OCCURRED_IN]->(Run)
```

### 4. 分层存储与聚合

- 主图谱：保留实体、关键关系、关键任务事件和异常。
- 热数据：近时段机器人位置、队列和负载保留在内存/Redis/时序库，供实时页面使用。
- 聚合数据：每分钟/每班次生成任务量、利用率、拥堵和充电统计，避免每次界面查询扫描全部事件。
- 原始日志：保存到对象存储或日志系统，图谱只保留引用和可检索摘要。

这延续了 `KG_Embodied` 的时序知识与实体关系分层思想，同时控制百万规模下的图谱膨胀。

## 四、P0/P1/P2 开发优先级

### P0：先形成可验证的图谱闭环

1. 定义节点、关系、属性、唯一 ID、事件类型和保留规则。
2. 增加 Neo4j 连接层、约束与索引初始化。
3. 在仓储任务状态机中发布领域事件，并以幂等方式写入图谱。
4. 提供 4 至 6 个固定查询 API：机器人当前任务链、任务全链路、货物位置、库位占用、异常追溯、班次统计。
5. 编写百万级合成数据与批量导入脚本，导入后做数据完整性校验。
6. 用 100 并发客户端压测真实查询组合，分别记录 p50/p95/p99；500 ms 要以 p95 或 p99、数据规模和查询集合明确验收口径。

### P1：把图谱能力连接到仓储界面

1. 不改变当前画布风格的前提下，增加任务链、货物/库位追溯和事件详情的后端数据接口。
2. 增加运行批次选择、实时事件流、异常提示和聚合统计。
3. 支持按机器人、任务、货物或库位定位相关子图/时间线。
4. 开发环境提供只读的图谱查询调试工具。

### P2：AI 识别与辅助决策

1. 明确输入：工单文本、设备告警、维护记录、摄像头/OCR 识别结果等。
2. LLM/OCR 只输出结构化候选：节点类型、关系类型、属性、证据、置信度。
3. 用 JSON Schema、实体消歧、白名单关系、权限控制和人工审核验证后写入图谱。
4. 让 AI 通过受限查询工具读取图谱，生成调度建议、异常原因说明或运维问答；建议与实际执行命令必须分离。

## 五、明确不应直接迁移的内容

- `KG_Embodied` 的无人机、配送员、地址、城市区域和地理路径实体。
- LaDe 城市地图、无人机标记和配送参数控制界面。
- 将 LLM 直接放进每个机器人任务的主控制回路；这会不利于时延、可预测性和故障恢复。
- 允许浏览器或 AI 向生产 Neo4j 执行任意 Cypher 写操作。
- 把每一个位置刷新帧永久写成完整图谱节点；百万级目标下会迅速产生不可控数据量。

## 六、当前项目与目标的差距

当前项目已具备：机器人仿真、最多 100 个活跃机器人的配置能力、协调器、实时状态快照和基础画布展示。

仍需实施：

1. 生产级 Neo4j 图谱存储及图谱模式；
2. 由任务状态机触发的规范化事件写入；
3. 百万级图谱数据生成、批量导入、索引和校验；
4. 预定义查询 API、缓存和 100 并发性能基准；
5. 图谱数据驱动的详情/追溯展示；
6. 经过治理的 AI 识别、审核与入图流程。

因此，最值得立即开始的是 P0 的“事件—图谱—查询—压测”闭环；它是任务三、任务四和任务五共同依赖的基础。
