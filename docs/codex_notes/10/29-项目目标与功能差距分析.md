# 项目目标与功能差距分析

## 任务背景

用户要求从整体上判断：这个项目真正要解决什么问题、已经交付了哪些能力、还缺哪些能力。本文综合当前分支 `dev_261028-layout-migration` 的工作区、`AI_PROJECT_HANDOFF.md`、`启动与图谱数据操作手册.md`、`docs/WAREHOUSE_PLATFORM_GUIDE.md`，并对比协作者分支 `wz/warehouse-design` 后给出结论。

## 1. 用户目标（分三层）

### 1.1 研究目标（`项目目标.txt`、`task2指标.txt`）

面向边端具身智能的多设备协作知识管理：把向量、图、时序数据统一管理，支持 ≥100 个智能体节点的时序知识图谱协同查询，在百万规模图数据下端侧查询延迟低于 500ms，并能支撑跨模态复杂查询与云端/边端协同决策。

### 1.2 平台目标（`AI_PROJECT_HANDOFF.md`）

用仓储 100 机器人场景承载上述研究目标，形成可见闭环：

```text
测试 CSV 数据集 → 静态仓库图谱 → V5/实时仿真 → 运行态图谱写入 → 回放与图谱查询
```

当前阶段优先级明确为「数据集 → 静态图谱 → 4173 实时执行/写图 → 图谱查询」，百万级压测和最终优化不是当前代码交接阶段的主任务。

### 1.3 当前阶段目标

让实时页面、历史回放和图谱查询使用**同一套 V5 运行事实**（同一 `runId`、同一布局坐标、同一任务/机器人状态），然后把规模与延迟指标做实。

### 3.2 协作者分支已有、但当前分支未合并（关键）

`wz/warehouse-design` 比当前分支多 6 个提交，且与当前分支的分叉点是 `21a8271`。它不是当前分支的超集：当前分支独有的仓储静态图、运行态写图、`kg.html`、4173 CSV/Actor 写图也不在 `wz` 上。`wz` 独有：

- **V5 实时控制台 14186**：`ops/warehouse_live.py`、`warehouse_live_runtime.py`、`dist/original-platform.mjs`、`original-knowledge.mjs`；真实 V5 协调器、单写者、开始/暂停/单步/倍速、固定数据集注册表、按需知识查询、原版三栏界面。这正好覆盖 3.1 中最大的「4173 与 V5 统一」缺口。
- **货架资源图**：`backend/resource_graph/`、`resource_graph_mirror.py`、`rack_inventory` 第 12 查询包；已在独立 Neo4j 实例做过真实 required 运行与 36 架/1728 槽位核对。
- **自由边界完整结果**：1728 任务自由口场景全部按时完成、最紧提前 108 秒；固定口 23 项晚点的完整归因。
- **端口疏解候选**：`port_relief.py` 的 online 取货节拍策略，1728 任务晚点 23→5、平均流转 472→455 秒、P99 1125→1005 秒（仍未零晚点）。
- **三型号混合机队**：A1/R2/X3 = 15/15/70 的能力门禁与候选布局。
- **查询长尾与 query-only 进程**：`backend/query_views/`、`docs/QUERY_TAIL_DEPLOYMENT_20261029.md`；完整 HTTP P99 约 303ms，但仍有 24 条超 500ms。
- **七种日型参考数据包、medium/large 候选布局、完整周证据**：`data/examples/seven-patterns-20261028/`、`docs/evidence/`。

结论：当前分支与协作者分支是**互补关系**，不是简单的前后关系。很多看起来「没做」的功能，实际是「没合并」。

### 3.3 两个项目都还没有解决的

- 100 智能体并发、百万规模图/向量/时序、端侧 <500ms 的第三方验收报告。
- KG_Embodied 与 warehouse-dashboard 的图谱本体尚未统一（`Drone/Task/Region` vs `Robot/WarehouseTask/WH*`），跨项目查询与复用仍需适配层。
- LLM 调度/自然语言查询在当前分支明确不在交付范围；若研究目标包含「知识增强决策」，这是后续独立工作。
- 服务编排与运维仍以手工命令为主（Neo4j、Ray、多个端口分开启停），没有一键部署/健康巡检。

## 4. 关键判断

1. **真正的头号问题不是写新功能，而是合并两条分支**。`wz/warehouse-design` 的实时 V5 控制台 + 资源图 + 查询视图，与当前分支的静态图 + 运行态写图 + 4173 CSV 接入，合起来才接近完整平台。
2. 合并时应以「实时 V5 控制台」作为正式实时入口，14183 保留历史回放，4173 旧控制台保留为兼容/对照；不要继续维护 4173 的坐标映射层。
3. 合并后优先做真实 Ray+Neo4j 联调、全周回归、自由工位/端口疏解的正式配置验收，再谈百万规模压测。
4. 规模指标是唯一无法靠合并解决的硬缺口，需要目标硬件、标准化数据集、100 并发负载和第三方口径的测试报告。

## 5. 建议执行顺序

### 5.1 当前真正的第一优先级

不是继续加功能，而是把两条分支合成一条可验收主线：

1. 当前分支的布局迁移改动未提交，先跑针对性测试并建立可回滚提交。
2. 合并 `wz/warehouse-design` 的 live console、resource graph、query views、free-boundary 结果；同时保留当前分支独有的静态图、运行态写图、`kg.html`、4173 CSV/Actor 写图。
3. 合并后用同一 `runId` 验收「14186 实时 / 14183 回放 / kg.html 查询」三处一致。

只有合并完成后，实时运行源统一才是可交付状态；否则继续在任一支线上开发都会产生重复实现。

```text
1. 冻结并提交当前布局迁移改动（先跑针对性测试）
2. 以 merge/rebase 方式合并 wz/warehouse-design，解决 5 个独有提交与 6 个独有提交的冲突
3. 用 14186 实时控制台替代 4173 作为 V5 实时入口，保留 14183 回放
4. 迁移/启用 resource_graph 与 rack_inventory，跑真实 Neo4j 验收
5. 目标主机跑 Ray+Neo4j 双服务冒烟 + 七天全周回归
6. 最后做百万 AgentState / 100 并发 / 端侧 <500ms 的标准化压测与报告
```
