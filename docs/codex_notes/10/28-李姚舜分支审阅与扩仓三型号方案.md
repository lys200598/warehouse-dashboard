### 一、李姚舜设计值得复用的部分

PPT与分支对应的结构清晰：

```text
Warehouse → Rack → Location
Dataset → WarehouseTask → Goods
WarehouseTask → FROM / TO → Location
Run → Robot / Execution / AgentState / RuntimeEvent
Execution → WarehouseTask、Robot
```

- Warehouse/Rack/Location表达静态空间和物理包含关系。
- WarehouseTask与Goods表达计划任务、起终点和初始库存。
- Run隔离每次实验；Execution区分计划任务与实际执行；状态、事件用于历史追溯。
- `backend/warehouse_graph.py`、`warehouse_graph_query.py`、`warehouse_runtime_graph.py` 及 `kg.html` 可以按模块接入，保留原有V5物理控制。

#### “货架里装了哪些货”需要统一时态

`Goods-[:INITIAL_AT]->Location`表示初始位置。出库后仍然保留它有利于追溯；不能把它作为当前库存回答。

我们已有 `WHSlot/WHLocation/WHCargo/WHGoodsState` 的真实货物位置和事件链。建议将其与他的静态资源图谱通过明确身份映射连接，提供两种查询：

1. 给定run和已提交水位，某货架现在有哪些货、哪些货位可用。
2. 给定历史水位，某货物当时位于哪个货位、哪个机器人持有，以及转移原因。

静态资源使用地图版本/内容身份；实验状态使用run和seq。新旧图标签可以先通过映射增量对接，不急于重命名已有百万级数据。接力应保留交接双方、任务、货物、原因和时点，复用已有经过来源核对的货权链。

#### 整合版尚未包含我们后续实时工作

整合共同基线是 `21a8271`。Git历史中 `0b7e844` 记录了两个父提交 `21a8271` 与 `676efde`，说明其版本历史是整合提交；AI如何挑选和处理文件需要看实际内容，不能仅凭“用了或没用git merge”推断功能完整性。

我们的 `ops/warehouse_live_runtime.py`、原页面V5接入及后续实时验收不在该整合提交中。其附加运行图投影接入 `backend/knowledge_runtime/runner.py` 的批运行提交点；当前互动服务使用独立Runtime。正式统一时，需要统一提交出口和投影水位，而非仅复制runner补丁。

#### 已复现、需协作修正的两个接点

**1. Rack主键被原始属性覆盖。**

`warehouse_graph.py`第180—181行先指定带warehouse命名空间的id，再展开 `**rack`；原数据中的 `id=R01` 覆盖了前面的id。Location的 `rack_node_id` 仍是 `warehouse:...:rack:R01`。

离线结果：36个Rack的ID为R01…R36；1728个货位的引用都是完整命名空间ID；能匹配的引用为0。依照这批构造数据执行 `LINK_LOCATION_SLOTS` 时，MATCH无法连接这些Rack记录。现有测试检查了Location/Task命名空间，没有检查所有货位外键都能命中Rack。这是固定提交构造路径的复现；没有据此断言对方现有数据库一定没有手动补充的关系。

建议先展开原属性，再设置规范图ID，另保留 `rack_id=R01` 作为业务ID，并增加全部货位引用完整性与真实Neo4j关系计数测试。

**2. 不同输入使用相同Dataset身份。**

当前ID仅由版本和开始日期组成。seed11/12生成的任务/库存SHA不同，却都得到 `dataset:warehouse100-generated-day1-v1:2026-10-27`。同库导入会混用或覆盖同名Dataset/Goods/Task。

建议以不可变manifest/输入内容哈希区分数据集，保留日期、seed、scenario为属性。仓库地图也应纳入内容身份，确保改大地图后同名货位不会串到旧坐标。

### 二、扩仓方案：扩大面积，同时适量增加货架

|项目|当前已运行版本|推荐候选，待验证|
|---|---:|---:|
|仓库外框|90×76m|150×100m|
|面积|6840㎡|15000㎡，约2.19倍|
|货架数|36|60|
|每架容量|3层×2面×8列=48|保持48|
|总货位|1728|2880|
|机器人|100|100，混合型号|
|进/出货布局|西进东出、各8点|先沿用逻辑边界，端口位置随新地图校核|
|充电待命|100个共用物理泊位|先保留总量，按新库区分组布置|

这是仿真候选参数，不是已验证的现实工业仓库施工方案。

- 只增加通道宽度会降低会车冲突，但不一定增加需要执行的工作。
- 只密铺货架会重新加重交通难度；优先增加规则库区、货架排与横向联络，保持进出货动线可解释。
- 普通巷道可先沿用4.5m；主干道从当前6m起评估是否需要加宽到8m。尺寸需与机器人作业位、避碰半径、路网验证一起核定。
- 保留R01—R36及已有货位业务ID，新增R37—R60；坐标、地图版本、哈希与位置表同步更新。保留业务ID不等于旧地图/期限仍可直接使用。
- 当前6840㎡已经能出现98台移动/取放的保存帧；是否“需要100台”还由到货/出货率、行程、取放时间和充电决定。持续生产中一部分机器人充电/待命很正常。

可用工作量估计辅助选规模：平均同时作业数约等于每小时任务数×单任务平均忙时秒数/3600。例如800任务/小时、平均360秒忙时，对应约80台持续执行，再留充电和备份。这只是算例，不是当前实际测量或最终任务率。

**代码前置工作：**`backend/wide/data.py`第142—143行仍把总货位限制为1728，增加货架前需要将其改为地图声明与逐架求和的一致性校验，保留重复ID、边界、容量、库存及安全验证。还需同步生成器文案、位置合同、前端和新回归，不能只改JSON后宣称已支持2880位。

### 三、复用三种机器人：参数、调度、接力与界面一起接入

原始warehouse提交 `e721268` 已有：

|型号|maxLevel|maxHeight|extension参数|
|---|---:|---:|---:|
|A1|1|0.55m|0.18m|
|R2|2|1.05m|0.52m|
|X3|3|1.55m|0.92m|

这些是原项目仿真参数，未核实为真实机器人硬件规格。`extension`与垂直可达高度分开解释，不直接当作机械臂总长度。原编号分组为A1/R2/X3约40/40/20，可先作为对照；应按上层货位任务量评估是否需要更多X3。

当前 `backend/wide/sim.py`第97行统一初始化为X3，所以之前运行结果属于同型号配置。恢复三型后需要：

1. 从机器人profile初始化型号、可达层/高度与伸臂参数，图谱和界面使用真实profile。
2. 入库按目标货位、出库按源货位，进行取放可达性判断；任务CSV七字段不必新增机器人ID。
3. 派单评分前过滤不可达组合，重试/回退/任务接管也采用相同可行性条件。
4. 接力检查接收者能否完成余下任务；能到交接位置不等于能放到目标高层。
5. 低层任务优先合理使用A1/R2，给需要高层的任务保留X3；不足时明确排队，避免错误分配。
6. 保留二维移动与简化取放动作；本阶段无需引入完整机械臂动力学或IK。

新回归至少覆盖：A1拒绝L3、R2允许L2、X3允许L3、低层任务不挤占全部X3、接力能力不匹配的拒绝/替代、暂停恢复保持型号，以及图谱和前端型号一致。

### 会议补充：扩仓必须评估100台机器人的实际运力

用户明确担心货位太多、行程太长导致100台机器人忙不过来。将此作为新布局定稿前的必要检查；150×100m/60架仅为候选，不预先锁定。

- 逐级试验：当前布局作为对照，先中等扩展，再评估更大候选。先做布局/型号单变量对照，再测试组合，区分行程、货架数量、混合能力和交通的影响。
- 同负载对照：保留相同任务率、种子和时限，不通过减少订单或静默延长期限掩盖运力下降；新增货架需另有覆盖全部库区的任务场景，不能只测旧36架。
- 持续场景检查完成速率与到达速率、待分配队列/最老任务年龄及其趋势；高峰场景检查峰后能否回落、积压何时清空。
- 同时检查及时率、平均/P95/P99流转时间、载货/空驶距离、充电等待、备份余量、交通阻塞与恢复。
- 按A1/R2/X3和货架层统计负载，识别长臂机型忙不过来而其他型号空闲的能力瓶颈。
- 保留正常日、峰值、局部热点、连续多日的组合测试；必要时降低货架数量、缩短跨库路径或调整分区，不以全体长期排队表现“100台都在工作”。
- 仿真物理运力与规划计算耗时分别计量。提高播放/仿真倍速不算运力改进，机器人的速度和取放耗时不得为获得好看结果而改变。

以上为后续实施验收计划，本轮尚未运行扩仓候选或对新布局作通过结论。
