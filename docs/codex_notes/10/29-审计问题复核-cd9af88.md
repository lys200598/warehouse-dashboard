## 三、逐项证据

### 3.1 旧控制台 + 映射（未解决）

当前运行面：

- `/api/snapshot`：`sourceKind` 不存在，`backend=ray`，机器人 `x/y` 来自旧 `SimulationCoordinator` 的 32×22 控制世界。
- `/api/layout`：返回 `warehouse100-expanded-balanced-v1`，100×90m、40 架、1920 货位、100 泊位，`coordinateMode=legacy-console-mapped`。
- `dist/app.js:133-142` `mapLegacyPoint()`：32×22 → 82×76 工作包络。
- `dist/app.js:275-299` `visualTaskPoint()`：任务阶段又把机器人画到扩展布局的工位/货架。
- `dist/app.js:1650-1715` `applyBackendSnapshot()`：`renderTarget` 来自 `visualTaskPoint`，不是后端真实坐标。

同一页面里同时存在三套坐标：
1. 后端真实控制坐标（32×22）；
2. `mapLegacyPoint` 的显示包络（82×76）；
3. `visualTaskPoint` 的扩展货架/工位坐标（100×90）。

审计报告要求「让地图、机器人、货位、路径来自同一轮真实 V5 运行」；当前仍是旧协调器 + 三层显示投影，未统一。

### 3.2 远距离伸臂（表面消失，根因仍在）

当前 `placing` 帧实测（tick 18500）：

```text
placing id 98 type INBOUND
visual = (22.488, 35.32)
rackTarget = (22.4875, 35.32)
dist = 0.0
rackId = 4, slotId = R19-L3-C1-F1
```

原因：`cd9af88` 新增的 `visualTaskPoint` 在 `placing` 分支直接返回 `rackTarget`（`dist/app.js:289-291`），所以 `drawRobot` 的肩部位置和 `drawPlacementCargo` 的箱体位置重合，机械臂不再跨 34.94 单位。

但这不等于修复：

- 机器人实际仍在旧控制坐标（例如 (10.9,6.02) 附近），只是显示时被放到 (22.49,35.32) 的货架旁；
- 这正是上一轮排查的「机器人瞬移」来源：`placing`/`picking` 直接返回扩展坐标，`returning` 又切回 `mapLegacyPoint`；
- 审计要求的「只在真实相邻作业位、阶段匹配时绘制，缺少姿态不伪造跨架动作」仍未满足：当前是**把机器人画到货架旁**来让臂看起来变短；
- 如果 `dashboardLayout` 加载失败或 `slot` 不匹配，仍会回退到货架第一格/旧坐标，长臂问题会重新出现。

审计的 HR-085 样本在当前 `visualTaskPoint` 下不会再出现 34.94 的稳态长臂，但根因（显示位置不是真实位置、货位/姿态不同源）仍然存在，且被瞬移现象替代。

## 四、根因归纳

1. **单一根因是运行源没有统一**：页面用 100×90 的 balanced 地图，运行状态仍是 32×22 的旧协调器。`mapLegacyPoint`、`visualTaskPoint`、路径、机械臂都是在补这个差异，越补越容易出现瞬移/混坐标。
2. **`visualTaskPoint` 是 `cd9af88` 新增的补丁**：它把 `toPick`/`toRack`/`picking`/`placing` 的机器人画到扩展货架/工位，短期让伸臂变短，但代价是机器人瞬移、路径混坐标、显示位置不再代表真实位置。
3. **区域底色和标签是独立的遗漏**：`drawFloor` 不读 `zones`，`updateZoneLabels` 仍用旧坐标和 DISPATCH 文案；即使坐标统一，这两项也要单独补。
4. **8 列几何已修正**：`cd9af88` 的 `airfix` 生效；不要再按审计的 6 列结论处理当前代码。
