# KG 参考项目阅读（KG_Embodied）

## 任务背景

用户要求阅读 `/data/workspace/lys/projects/KG_Embodied`。该项目是 `AI_PROJECT_HANDOFF.md` 与仓库查询文档反复引用的参考项目（KG_Embodied / LaDe viewer），用于理解多智能体时序知识图谱、决策上下文查询与 100 智能体并发查询指标的设计来源。

## 关键结论

- `KG_Embodied` 是一个基于 LaDe 末端配送数据的**多无人机配送仿真 + 知识图谱可视化**项目，不是仓储项目；技术栈为 Python 3.10、Ray 2.59、Neo4j 6.4，入口 `run_local_sim.sh` / `run_ray_sim.sh`，页面端口 8010。
- 主链路：LaDe delivery CSV → `DeliveryTask` → 按 region 固定 depot → `DroneAgent` 集群 → `AuctionCoordinator` 或 `RegionLLMCoordinator` 派单 → `DroneAgent.step()` → `TemporalKnowledgeStore` / `Neo4jKnowledgeStore` → SSE 帧 → `dynamic.html`。
- 「知识图谱」有两层实现：默认 `TemporalKnowledgeStore` 只是**内存时序事件列表**（task_assigned / task_picked_up / task_completed / 低电返航 / 互助交接）；设置 `KG_BACKEND=neo4j` 后才写 Neo4j，节点为 `Run / Drone / Task / Region / Event / Step / AgentState`。
- 图谱按 `KG_RUN_ID` 隔离；`Event` 是离散事件，`Step` 是每轮仿真摘要，`AgentState` 是可选逐 step 快照；三者不能混用。
- LLM 调度主路径是 `RegionLLMCoordinator`：先用知识上下文筛选紧急任务与候选无人机，再把最近 30 分钟的 `recent_agent_performance` / `recent_events` 作为 `kg_context` 注入 Prompt；任何异常都回退到规则拍卖。`LLMPlanner` 是另一层单任务成本估计，默认未启用。
- 查询侧有两套重要资产：
  - `simulation/graph_query.py`：有界只读 Cypher 服务（词法白名单 + `EXPLAIN` 校验 `query_type == "r"` + 事务回滚），限制 200 行 / 1MB / 15 秒 / 单并发，通过 4173 类似的 `/api/graph-query` 暴露。
  - `scripts/lade_llm_context_templates.py`：i0–i55 共 56 条决策上下文查询；`scripts/lade_cypher_templates.py`：q0–q55 基准模板，按 smoke / online / analytics / collaboration / resilience / quality 六个查询包组织。
- 任务指标背景：面向 100+ 智能体节点、百万级图/向量/时序数据、端侧 <500ms 查询；仓库已有并发压测与分阶段计时脚本（`concurrent_neo4j_query.py`、`lade_cypher_benchmark.py`、`lade_llm_context_queries.py`），但第三方验收与最终端侧优化未完成。
- 与仓储项目的关系：仓储项目的 `knowledge_runtime`（历史授权/接力）、`query_catalog`（11 个知识包）、`query_v2`（轻量/ANN 上下文）和 Run/AgentState/Event 模型，基本是把本项目的设计迁移到仓库场景；`docs/WAREHOUSE_QUERY_GUIDE.md` 明确说明整理自 KG_Embodied 的决策上下文。
- 当前 KG 项目状态：`main` 分支停在 `899c50c 1026 备份`，工作区有 README/启动脚本的部署路径修复未提交；`HANDOFF.md` 中仍有作者机器绝对路径，README 已改为仓库同级 `../lade-deploy/.venv` 的相对路径方案。

## 后续建议

1. 若仓储项目要继续完善 `query_catalog`/`query_v2`，优先对照 KG 的 i0–i55 分类（self / task / assistance / progress / memory 等）与六个查询包，而不是重新设计一套查询语言。
2. 复用 `graph_query.py` 的只读查询防护思路（白名单 + EXPLAIN + 回滚 + 行数/字节/超时上限），但需把端口、库名和鉴权换成仓储项目自己的配置。
3. 100 智能体并发与百万级 <500ms 指标应以 KG 项目的压测脚本和分阶段计时方法为基线，明确「客户端耗时 / 服务端可用 / 消费完成」三类时间，不能只看页面帧率。
4. 注意两个项目的 Neo4j 端口不同（KG 默认 7687/17687，仓储为 47687/47474），不要把 KG 的连接配置直接复制到仓储项目。
5. 迁移模型时保持仓储已有语义：`WarehouseTask` 与 KG 的 `Task` 不是同一实体，`AgentState` 的采样周期与提交水位也不能照搬。
