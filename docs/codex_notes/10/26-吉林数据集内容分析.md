# 吉林数据集内容分析

### 任务背景

分析 `/home/lys/workspace/projects/KG_Embodied` 所使用的吉林（Jilin）配送数据集，判断其数据内容、图谱使用方式及对当前人形机器人仓储项目的复用价值。本次仅阅读和分析，未复制、生成或修改数据集。

### 关键结论

- 原始文件是 `/home/lys/workspace/projects/delivery/delivery_jl.csv`，共 31,416 行（1 行表头、31,415 条配送订单），约 4.74 MB；它是中小规模配送订单数据，并非百万级原始吉林数据。
- 每行对应一笔已完成配送订单，包含订单、区域、配送员、AOI、接单/送达时间、接单/送达 GPS 坐标和日期字段，共 17 列。
- KG_Embodied 将 `accept_time` 解释为任务释放时间，将 `delivery_time` 解释为仿真 deadline；这是实验建模，不应误解为数据集原始提供的承诺时限。
- 当前配送仿真加载器只使用 `order_id`、`city`、`lng/lat`、`accept_time`、`delivery_time`、`aoi_id` 和 `region_id`；`courier_id`、接单/送达 GPS 等字段主要服务于大规模图导入或后续分析。
- 吉林 run `jilin-0925-ray001` 的历史图谱记录约有 9,905 个 run 内节点、40,705 条去重关系，其中 Task=3,352、Event=6,404、Region=99、Drone=50；它不是百万级图。
- 该 run 的 100 并发压测是 100 个客户端循环查询 50 个 Drone，`agent-state` 查询 p95 为 294.416ms；这是万级图上的特定点查结果，不能外推为当前项目的百万级仓储验收结论。
- 吉林原始数据最多可经 `Task + 2 Event` 直接扩成约 94,246 个基础节点（未计 Region/Courier）；若目标是百万节点，需要合成更多任务、保留多 Step 的 AgentState，或使用其他城市/合并数据。
- 对仓储项目应复用其“订单/任务—事件—区域—执行体—时序状态”的建模模式和批量导入方式，重写为 `Robot / WarehouseTask / Rack / Zone / Event / RobotState`，不应直接复用地理配送语义。
