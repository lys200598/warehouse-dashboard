# 独立扩仓候选与容量参数化

### 任务背景

根据会议要求增加仓库面积与货架候选，并评估100台机器人运力。当前服务和冻结源必须保留；本子任务实现候选及严格容量合同，主任务负责进一步同负载仿真对照。

### 关键结论

- 生成medium 120×90m/48架/2304位、large 150×100m/60架/2880位，两者独立版本、目录与位置表。
- 实际静态审计均通过：medium路网13931节点/26860无向边，large19790节点/38408无向边；均单连通，无割点/桥，无不可达业务端点、无unsafe connector/edge。
- 原地图SHA仍为 `ce99154d80fc643610dcb6d27384ca3724f95dc9121b8d2934212d56ba9eda24`。保留0.55m规划半径、0.7m机体、100个单容量物理泊位和原业务ID。
- 容量按地图声明、逐架层面列乘积及全部唯一货位一致性检查，去除load_scene、V2准入、V3step中1728的固定物理限制。满额拒绝和溢出断言保留。
- 候选未设为默认，尚无吞吐/长尾/动态死锁通过结论。增大地图会增加规划路网规模，需要与行程及任务能力一起评估。

### 执行过的操作

读取AGENTS、会议方案、wide数据/路网、继承的V2/V3容量检查和既有测试。新增候选生成器并实际执行 `python -m backend.wide.layout_candidates --candidate ... --audit`。本机无可用LaDe环境，使用Codex捆绑Python运行标准库测试，没有安装新依赖或修改共享环境。

新增布局回归与原wide数据回归日志在 `C:/E/projects/warehouse/research/branch-review-20261028/expansion-layout-tests.log` 和 `expansion-existing-wide-data-tests.log`。本轮新增13项全部通过（30.982秒），原wide数据9项全部通过（1.486秒）。实际V5回归验证了1800件初库存上接纳第1801件；满2880件时，即使OUT已经取走、货位空闲，IN仍等待，必须实际出库确认后才重新准入。合成越界计数2881仍触发硬容量断言。

### 修改内容

- `backend/wide/data.py`：参数化容量并严格检查slotsPerRack、count和非空架集合。
- `backend/wide/layout_candidates.py`：确定性生成候选、位置表、源身份与可选静态路网审计；拒绝覆盖已有输出，支持显式rack-count的面积消融。
- `backend/scheduling_v2/sim.py`和`backend/scheduling_v3/sim.py`：仅将活跃继承路径中的固定总容量改为len(self.slots)，不修改派单策略或安全阈值。
- `backend/wide/multiday.py`、`scenarios.py`：容量元数据/文案与实际地图一致。
- `data/layouts/expansion-candidates/`：两个候选、位置表、SHA及几何证据；README说明使用与限制。
- `tests/test_expansion_layouts.py`：布局声明/端点/泊位/安全/迁移/不可覆盖/容量及实际V5高库存回归。

### 后续建议

主任务使用相同任务率、seed和时限对比当前、medium与large；另测新增货位全覆盖、峰值、热点、充电与混合型号。保留输入和原始失败；若积压持续增长，选较小候选或调整分区，不靠放松安全或延长期限掩盖问题。
