# 仓储图谱模型读写评审

## 任务背景

用户要求回到数据和图谱本身，参考 KG_Embodied 评审当前仓库项目的节点、关系、读取和写入设计是否合理。

## 关键结论

- 当前模型的两层拆分合理：静态层描述仓库/数据集/任务，运行态层描述 Run/Robot/Execution/AgentState/Event，适合作为仓库图谱的基础。
- 静态层 `Warehouse → Zone → Rack → Location` 与 `Dataset → Goods/Task` 的职责清楚；任务通过 `FROM/TO/CONCERNS` 连接位置和货物，优于把所有字段塞进 Task 属性。
- `Execution` 作为一次运行中的任务执行实例是合理的，它把静态 `WarehouseTask` 与动态 `Robot/Run/Event` 连接起来。
- 当前运行态读写尚未完全收敛：应先修正生命周期事件写入、Run 到 Dataset 的显式溯源、以及查询键后，再把它视为稳定的后续优化基础。
- KG 的关键可借鉴点是 `Run—Step—AgentState—Event` 的时态分层和 `AgentState(run_id, agent_id, step)` 查询键；不是照搬配送的 Region/Courier/Drone 实体。

## 后续建议

1. 必须修正：每个 Run 显式保存 `dataset_id` 并建立 `(:Run)-[:USES_DATASET]->(:Dataset)`；这样回放、任务追溯和多数据集并存时不会靠配置猜测来源。
2. 必须修正：运行事件无论发生在哪个采样 tick，都应驱动对应 `Execution` 更新；当前只有状态采样 tick 会生成 Execution 行，完成事件可能遗漏执行完成关系。
3. 必须修正：为 `AgentState` 冗余保存 `run_id`，并把回放查询改为 `{run_id, tick}`；当前仅按 tick 匹配再沿关系过滤，不是百万数据下的正确读取键。
4. 必须修正：Task 查询要以 `dataset_id + task_id` 定位，或建立相应复合唯一键；仅按 `task_id` 在多数据集下会歧义。
5. 应收敛：`Execution-[:ASSIGNED_TO]->Robot` 已表达分配，`Robot-[:ASSIGNED]->Execution` 是重复语义；`CARRYING/COMPLETED` 更适合作为带 tick 的生命周期属性或 Event 关系，避免长期残留的“当前关系”。
6. 可后置：增加 `RunFrame`/`WarehouseState`（每个采样 tick 一条）保存完成数、等待数、任务状态汇总和货位变更摘要，可支撑完整全局回放；不必把每个货位每 tick 都复制一遍。
