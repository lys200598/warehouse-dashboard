# 历史知识怎样进入实际仿真

本入口把共享知识读取接到选定的 V5 仿真执行器。正常移动沿用原来的能量准入、交通预约、库存守恒和货权事务；低电接力发生时，协调进程按需读取该任务、货物与协作历史。

## 1. 一次低电接力的调用链

```text
机器人报告低电
  → 先将扰动前的一致快照提交到本地日志和 Neo4j
  → report_soc → request_assistance
  → GraphHistoryProvider.cooperation_context（一次只读图查询）
  → 核对任务、当前货权、既往持有者、历史预约及提交水位
  → authorize_assistance_planning
  → 根据既往交接记录调整帮手候选顺序
  → 原调度器检查能量、路线和交通预约，提交接力计划
  → 交接发生前，重新读取已经提交的共享历史
  → authorize_transfer
  → 原货权事务检查交接位置、唯一持有者和接收方状态
  → 货物转移，并记录知识决策及实际动作
```

例如，37 号机器人正在运货，历史显示 31 号曾把这件货交给 37 号。接力规划会优先考虑其他可用帮手，减少来回接回同一件货的情况。候选继续接受原来的能量与交通检查；排序调整不会豁免这些条件。现有物理规划保留最多尝试 8 位候选的计算预算，因此这一启发式的收益仍需按场景比较。

独立测试从同一实际仿真检查点出发：无该历史时选 31 号；加入契约完整的 `31→37` 测试历史后，实际选择 32 号，完成 `37→32` 货权转移。该例验证历史影响选择的调用链，历史输入来自测试提供者。

## 2. 查询在什么时候触发

目前接入两个必要边界：**规划接力**、**实际交接前复核**。普通移动帧和每秒推进无需重复查询相同背景。一件货完成一次接力，通常需要两次协作上下文读取。

运行入口使用轻量的 `cooperation_context`，取得关联任务、货物历史及协作事件。它不执行全局向量检索。完整上下文接口的 ANN 长尾优化保留为独立查询服务，便于单独测试和对比。

## 3. 历史怎样保持可信

- 本地持久化水位与图谱已提交水位相同，且没有镜像错误。
- 来源批次的摘要、运行编号、配置和源码身份与当前运行一致。
- 查询只看指定已提交批次，校验对应摘要、任务完整载荷、货物身份及历史顺序。
- 完整首屏历史是授权输入；遇到截断、未来数据、外来任务或货权矛盾会拒绝授权。
- 默认图谱观察最多落后 30 **仿真秒**；这与 500 ms 请求响应指标分别计量。当前采样节奏为 5 仿真秒。
- 实际交接前先查询、预检整个时间步，再推进机器人，避免查询失败导致半个物理步已经执行。
- 交接令牌仅用于指定的交出方、接收方、任务和时间步，消费后立即失效。

`knowledge_decision` 保存知识水位、批次摘要、上下文摘要和历史事件编号；`knowledge_action_applied` 对应已预约接力或已实际转移货物。可沿这些记录追溯一次动作所依据的知识。

## 4. 运行、恢复与对照

在 Pro6000 的独立源码目录中运行：

```bash
cd /data/workspace/wz/warehouse-knowledge-runtime-20261028/code-v1
export LADE_ENV_DIR=/data/workspace/wz/warehouse-deploy/.venv
export PYTHONPATH=/data/workspace/wz/warehouse-validation-v2-20261027/driver-rust:$PWD
set -a; source ../neo4j.env; set +a
./run_in_lade.sh python -m backend.knowledge_runtime.runner \
  --scene data/layouts/warehouse100-wide-v2.json \
  --dataset /absolute/path/to/dataset \
  --output /absolute/path/to/new-output \
  --run-id unique-run-id \
  --knowledge-backend neo4j --knowledge-mode required --commit-seconds 5
```

Neo4j 凭据通过环境变量加载。固定输入可使用任意合法时长；文件加载和任务条数仍受机器资源约束。参数说明可通过 `--help` 查看。

- `required`：历史授权参与实际控制；读失败或校验失败会停止本次运行并保留现场。
- `rules`：同一源码中的原规则对照入口，关闭知识授权，保留原物理调度与图谱写入。
- `--resume`：以同一模式、配置、源码身份和扰动清单继续，先追平日志镜像。交接前重新查询，防止重复消费旧授权。

若外部低电测量已经改变机器人状态，随后知识读取失败，测量与失败尝试会持久化，并要求人工明确处理后再继续，避免自动恢复时重复注入。正常读失败发生在物理步预检期间，可在图谱恢复后按检查点继续。

## 5. 本轮运行位置

Pro6000 独立部署根目录：`/data/workspace/wz/warehouse-knowledge-runtime-20261028`。

- `code-v1/`：冻结源码，独立于原网页使用的 V5 版本。
- `neo4j/`：独立图谱，Bolt `127.0.0.1:17689`，HTTP `127.0.0.1:17476`。
- `runs/required/`：真实历史参与的仿真及分段恢复记录。
- `runs/rules/`：相同输入和扰动的规则对照。
- `runs/seven-patterns-prefix/`：新七天输入前1800秒的真实运行与低电接力。
- `inputs/seven-patterns/`：50,112 条连续七天典型波动输入。
- `logs/`：原始运行、回归日志与退出码。

已有网页和旧冻结实验保持原有入口。新能力通过上述运行器启用，便于比较与回退。

## 6. 已经实际验证的结果

|验证项|结果|
|---|---|
|一小时256任务，历史授权模式|256完成、0迟到、2次实际交接、4次历史读取|
|相同输入及扰动的规则对照|256完成、0迟到、2次实际交接、0次历史读取|
|两模式最终物理状态|16组字段逐一相同，包括机器人、任务、货物、货位、任务队列和交通恢复状态|
|任务流转时间|两模式平均128.758秒，P99为183秒，最大247秒|
|分段恢复|2400秒暂停，原日志继续至3708秒，扰动及交接各执行一次|
|独立来源审计|逐条重建4份知识上下文，15项来源、身份及控制链检查通过|
|实际图谱状态|历史模式74,800条实际机器人状态；规则模式74,500条，水位均追平|
|新七天输入的前1800秒|144任务已发布，134完成，10仍在处理，0迟到；2次交接、4次历史读取，36,600条实际机器人状态；独立控制链审计通过|

实际例子：600秒，66号携带任务`V3-T-0000049`的货物`INITIAL-00222`时报告低电。规划依据知识水位122，预约87号接力；交接前再次读取水位135，核对原货权和已提交预约，再由原物理事务完成66→87转移。1800秒另一件货执行9→69接力。每次都可沿事件编号、批次摘要、上下文摘要回溯。

这轮受控输入下，历史授权没有改变选中的帮手，因此两模式业务表现相同；独立的历史选择测试验证了存在既往交接时的实际选择变化。收益比较可在后续重复协作或异常场景中继续进行。

上述小规模控制链验证与百万实际状态上的100客户端查询测试分开记录。本轮控制样例最多18台同时执行业务，注册和持久化状态始终包含100台；原V5的100台同时业务活动验收保留原证据。完整七天物理仿真及其密集时序图谱应作为独立实验记录。

## 7. 查询性能按实际接口分别看

在17688的百万实际状态前缀上，另做100客户端同步压力，每轮均实际观察到100个API请求在途，8个工作进程；完整返回保留，查询阶段结束后逐条用来源Oracle核对。

|接口负载|请求数|平均ms|P99 ms|最大ms|超过500ms|
|---|---:|---:|---:|---:|---:|
|生产轻量上下文混合：robot/cooperation|3000|21.132|66.184|109.127|0|
|完整ANN上下文，优化方案默认配置|18000|87.983|208.414|526.024|2|

轻量负载含1485次机器人上下文和1515次协作上下文，覆盖100个真实机器人编号；冷首请求和全部等待计入，独立重复验真通过。完整ANN的两条慢请求为507.271和526.024ms，继续列为长尾缺口。

这项读取压力与本节前面的物理运行分别测量：100个API并发不等于100次物理交接并发，以上也单独计量浏览器/HTTP网络以外的服务层。详细长尾原理、负结果和全部慢样本见研究目录中的最终查询报告。
