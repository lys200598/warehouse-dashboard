# 扩仓、三型号与货架资源图交付

实验日期：2026-10-28；汇总日期：2026-10-29。给接手同学的阅读入口。

## 1. 本轮做了什么

本轮围绕三个接口完成增量：**地图与运力、机器人取放能力、货架及库存知识**。继续使用现有 V5 规则调度、任务 CSV、真实 journal、Neo4j 提交链和原来的 `index.html`。旧地图、旧服务、旧冻结实验均保留。

当前建议把 **100×90m / 40架 / 1920位** 当作优先讨论的扩仓候选。它相对原90×76m面积增加约31.6%，货位增加11.1%，普通通道5m、主通道8m，西入东出各8点，南北合计100个充电兼待命位。扩大空间的同时适度增加货架，控制运输距离。它尚未成为默认地图，强高峰下仍有晚点，见第4节。

## 2. 与李姚舜工作的衔接

已读取 `dev_lys_261026`（`676efdeed8b61549e6c617b361bcaf8aa27de2e1`）和整合分支 `dev_261028`（`1e73a75b54fdcf951d3255b43ae9c9ec3a1e8873`）。采用其 `Warehouse → Rack → Location`、任务关联货物、运行关联实际执行的分层思路；沿用我们的 `WHTaskState / WHGoodsState / WHEvent` 保存真实过程。

代码构造核对发现两处需处理：Rack主键可能被原始 `id=R01` 覆盖，Location却引用带命名空间的主键；Dataset仅版本与日期不足以区分不同seed输入。本轮资源适配器修正这两点，用完整地图/CSV/manifest SHA建立身份。该发现针对分支源码构造，不等同于对他现场数据库的断言。

```text
WHRun ─ USES_LAYOUT → Warehouse ─ HAS_RACK → Rack ─ HAS_SLOT → Location
  └── USES_DATASET → Dataset ─ INCLUDES_TASK → WarehouseTask → Goods
WHSlot / WHLocation / WHTask / WHCargo ─ INSTANCE_OF → 对应静态对象
WHSlotState、WHGoodsState、WHEvent：继续保存本run的时序事实
```

资源写入与原状态写入处于**同一事务**，推进 `resource_graph_seq`；纯状态批次不重建全部货架。`INITIAL_AT`保留初始位置；历史库存依据指定run/seq之前的槽位、货权记录还原。

新增第12个查询包 `rack_inventory`。例如R40有48个货位，返回各货位在指定水位是否为空、装哪件货、总容量和占用数。它目前是只读库存知识包，`used_by_live_control=false`；既有低电历史授权链继续工作。

静态Dataset/Task可以跨run共享。Agent须走run/cutoff限定的API，不能开放任意Dataset遍历后承诺未来任务全库不可见。当前仍是中央协调进程推进仿真与持久化，尚未变成100个机器人进程各自读写。

详细字段和事务接点见 [货架资源图指南](RACK_RESOURCE_GRAPH_GUIDE.md)。

## 3. 三种机器人如何进入仿真

复用原 `backend/domain.py` 定义，并在派单、恢复、交接、实际取放处检查能力：

|类型|可到层级|最大操作高度|额外水平伸展|
|---|---:|---:|---:|
|A1|1|0.55m|0.18m|
|R2|2|1.05m|0.52m|
|X3|3|1.55m|0.92m|

额外伸展指到达取放点后的附加能力，不是整条手臂的总长度。两面货架分别设置取放点，默认额外需求0；当前布局文件可按整架声明 `required_extension_m`。三种型号是二维运输中的能力约束，没有增加全身IK或接触仿真，也没有声称不同型号的速度/能耗已校准。

默认 `fleet_mode=all-x3` 保留原行为；混合示例：

```json
{"fleet_mode":"mixed","fleet_counts":{"A1":15,"R2":15,"X3":70},"speed":0.8}
```

已有任务三层分布和高峰负载会影响型号比例，40/40/20在本次强高峰下明显不足。不要只依据100台总数判断运力。仍有候选池队首阻塞的已知限制；研究性补位策略减少局部等待但使总完成时间变差，故未合入调度主线。

## 5. 持货速度核对与敏感性

官方A2 Ultra/Lite公开最高速度1.2/0.8m/s，未明确这些速度在最大负载持续搬运条件下成立；Walker S2官方载荷参数未给可直接标定的持货行走速度。来源及适用条件见 [速度核对](ROBOT_LOADED_SPEED_REVIEW.md)。因此本轮保留0.8基线，单列1.0假设。

保守候选提速后平均流转472.48→454.61s（约减少3.8%），最终完成4419→4384s（约减少0.8%），晚点23→18。中型平均630.25→601.17s（约减少4.6%），晚点183→156。收益存在，未消除所有延误，不能按直线移动时间减少20%外推整单收益。取放、交通、任务衔接等开销仍在；各自贡献本轮未作完整剖分。

速度测试保持移动SOC/秒不变，等价于固定移动功率假设；单位距离耗能会随速度下降。硬件持货速度与速度—能耗耦合均未标定，不能把此结果写成真实机器人加速后的续航收益。

## 6. 运行与界面

正式运行中的14186完全保留。本轮独立预览：<http://127.0.0.1:14188/>，沿用原页面和右键平移/滚轮缩放。默认是100×90m、15/15/70、0.8m/s、1728任务；初始暂停，点击“继续仿真”，20×/60×控制墙钟播放倍率，不改变机器人m/s参数。

1. 左侧选数据集，暂停后“保留记录，另开新run”切换；历史run和图谱继续保留。
2. 选机器人，右侧查看型号、层高和额外伸展。
3. 页面底部选择“货架库存 / 历史货位”，填 `R40`，点击“查询已提交知识”。使用本帧已镜像水位；取消勾选可选同run更早seq。
4. 小样例/高峰/速度假设均以不同run、输入SHA和冻结源区分。旧run不能中途静默开启资源图。

统一批运行示例（路径替换为自己的绝对路径）：

```bash
bash run_in_lade.sh python -m backend.warehouse run \
  --scene /absolute/layout.json --dataset /absolute/dataset \
  --config-json /absolute/mixed-config.json --output /absolute/new-run \
  --run-id unique-run --mode required --knowledge-backend neo4j \
  --resource-graph --commit-seconds 30 --frames
```

资源图仅在Neo4j模式显式启用。交互入口同样支持 `python -m backend.warehouse live ... --resource-graph`。本轮候选数据库17691/17478、预览14188，与正式17690/17477、14186独立。
