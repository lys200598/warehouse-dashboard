# 原型实测：机器人写图谱、`Step` 标记、从图谱读状态派单、100 Agent 并发取回决策上下文

日期：2026-10-30。作者：wz。原型：`ops/prototypes/kg_state_source.py`（研究工具，不是产品代码）。

## 1. 测什么

验证设计说明（[`ROBOT_ACTOR_DISPATCH_SPLIT_20261030.md`](ROBOT_ACTOR_DISPATCH_SPLIT_20261030.md)）里的四件事：

1. 每步 100 台机器人各自写入本机状态和事件，写完回执；
2. 回执之后，"全局写入"写 `Step(t)` 完成标记，并更新 `Run.latest_step`；
3. 下一步派单前，主进程从图谱读回全部机器人状态再派单（`KG_STATE_SOURCE=neo4j`），结果必须与读内存逐条一致；
4. 每 10 步，100 个机器人并发取回自己的决策上下文（6 条查询），与写入同时进行。

## 2. 怎么测

- **仿真**：轮式 medium 地图，19 任务样本，发布时间整体前移，跑到全部完成（1780 步）；原型以子类方式接入，不改产品代码。
- **机器人**：用 100 个独立进程模拟 100 个 Ray 机器人进程，每个进程有自己的 Neo4j 连接（`--procs`）。
- **图谱**：标签按 C 套（`Robot`、`AgentState`、`RuntimeEvent`、`Step`、`Run`）。机器人当前状态每步覆盖写在自己的 `Robot` 节点上；历史状态每 4 步追加一个 `AgentState`；本机事件每步写入，保留完整内容（含交接双方）。
- **决策上下文（6 条）**：最新一步摘要、自身状态、近期状态（最近 400 秒）、近期事件（最近 600 秒）、附近机器人、可求助对象。
- **百万规模**：在**被测的同一次运行**下，用负数步号预先造 9000 步历史（90 万历史状态、15 万事件、9000 个 `Step`），运行结束时该运行共约 110 万节点。
- **数据库**：单独起的 Neo4j 5.26 实例（端口 17695），连接线程池上限 256，堆内存和页缓存各 4G，测试期间无其他服务连接。

## 4. 结论

1. **从图谱读状态再派单，结果与读内存逐条一致。** 5 轮对照全部相同（19 次派单、每个任务的完成时刻）。机器人状态是 19 个平铺字段，转 JSON 存取不丢精度。
2. **百万规模下性能有很大余量。** 修复后，每步约 119ms（写入 83ms、读状态 17ms、`Step` 13ms），按实时速度每步预算 1 秒，约可跑 8 倍速；每个机器人取回决策上下文均值 21ms、P99 49ms。
3. **最初测得很慢，是测量方式的问题。** 100 个线程挤在一个 Python 进程里，被全局解释器锁（GIL）卡住，客户端 CPU 只有约一个核（106%），数据库在等它。真实设计中每台机器人是独立的 Ray 进程，应以多进程的数据为准。
4. **两条查询原本会随运行时间变慢，已修复。**
   - "最新一步"原来用 `ORDER BY tick DESC LIMIT 1`，执行计划显示是对全部 `Step` 逐个扫描（1 万个时已 49ms）。改为由全局写入维护 `Run.latest_step`，查询变为两次唯一键查找：2.9ms。
   - "近期状态"原来把该机器人的全部历史（9,446 条）读出后取最新 20 条。给时间范围加下界（最近 400 秒）后：5.6ms。近期事件同理（最近 600 秒）。
5. **有 0.16% 的长尾超过 500ms，来自 Neo4j 检查点。** 修复后那一轮有 28 次上下文超过 500ms（最大 757ms），同一时段写入最大 1.2 秒，所有查询同时变慢。Neo4j 日志显示，北京时间 12:10:27～12:10:33 有一次约 5 秒的检查点，正落在这一轮运行中；日志里没有虚拟机停顿（垃圾回收）记录。检查点按事务数量触发，逐台写入每步 100 个事务，触发更频繁。
6. **逐台写入约比合并写入慢一倍。** 每步写入 86ms 对 43ms（单进程下测得的 7 倍差距里混有 GIL 的影响）。这是"每台机器人自己写"这一架构选择的代价，仍在可接受范围内。
7. **两个实际问题：**
   - wz 原来的 Neo4j 实例（17692）连接线程池上限只有 32，100 路并发写会报 `NoThreadsAvailable`，必须调大；
   - 历史状态写入必须用 `MERGE`（按唯一编号合并），不能用 `CREATE`：一次运行中出现过重复写入导致的唯一约束冲突。

## 5. 没有覆盖的部分

- 不是真正的 Ray actor（数据库侧负载相同，但没有计入 Ray 调用开销）；
- 上下文是简化的 6 条，不是 LaDe 完整的 56 条；
- 只跑了约 30 分钟模拟时长，没有测一整天；
- 合并写入只在 4.6 万规模下测过，没在百万规模下测；
- 检查点的长尾没有调参验证（可选方向：合并写入减少事务数、调整检查点间隔、加大页缓存）；
- 测试期间数据库没有其他服务争用；
- 测的是 19 任务样本，派单较稀疏；高峰数据集（1728 任务）下每步的派单计算会更重。

## 6. 复现

```bash
# 需要 NEO4J_URI / NEO4J_USER / NEO4J_PASSWORD 指向一个连接线程池足够大的实例
python ops/prototypes/kg_state_source.py --procs --context-every 10 --compare --run-tag kgproto-a
python ops/prototypes/kg_state_source.py --procs --filler-ticks 9000 --context-every 10 --compare --run-tag kgproto-b
python ops/prototypes/kg_state_source.py --procs --batched --context-every 10 --compare --run-tag kgproto-c
python ops/prototypes/kg_state_source.py --cleanup   # 删除所有 kgproto- 前缀的数据
```

- 图谱模式用时 1011.39 秒；内存对照用时 364.63 秒。JSON 报告派单及完成时刻对照一致：`dispatch_identical=true`，记录 1728 次派单。
