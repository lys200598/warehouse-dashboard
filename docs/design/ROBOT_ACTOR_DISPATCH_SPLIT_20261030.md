## 1. 现状

### 1.1 一个 tick 里主进程做了什么

仿真每个 tick 推进 1 个模拟秒，入口是 `backend/scheduling_v3/sim.py` 的 `step()`。顺序如下：

1. **释放与派单**（`release_and_dispatch`）：发布到期任务；为空闲机器人挑任务；**一次性规划好整条路线**：一段段带起止时刻的计划（`job['parts']`），同时在交通预约表里订好时空格子，分配充电位或换电位，检查电量是否够用、激活数是否超限。
2. **逐台推进**：对每台机器人，找到当前所处的计划段，算出这一秒走到哪；更新位置、阶段、电量、里程、排队或工作时长；充电段增加电量。
3. **处理"标记"**：走到某段终点时，如果这段带有标记（取货、放货、接力交接、故障结束等），调用 `marker()`。它会修改**全局状态**（库存、货位、任务状态、进出口计数、接力配对），有时还会修改**另一台机器人**的状态（交接时货物从一台转到另一台）。
4. **任务完成**：计划走完，机器人回到空闲，从 `jobs` 中移除。
5. **汇总与检查**：全体机器人两两安全距离审计、电量下限、容量和机器人计数不变量、各项统计；每 60 秒清理一次交通预约，并检查库存守恒。

关键点：**机器人怎么走、什么时候到，在派单那一刻就已经算定了。** 之后每一步只是照着计划执行。这决定了拆分边界：计划由主进程做，执行可以交给机器人自己。

### 1.2 现在的 Ray 版本（lys，`backend/ray_medium/`）

- 100 个 `MotionActor`，每个占 0.1 个 CPU，命名空间是 `warehouse-medium-ray`。
- 每个 tick，主进程把"当前计划段和时刻"发给对应的 actor，actor 算出起点和终点位置后交回。**actor 不保存任何状态**，位置、电量、任务都还在主进程里。
- 打开 `--robot-graph` 后，主进程在每步结束时，把每台机器人的快照和事件发给对应的 actor，由 actor 写入 C 套图谱（`Robot`/`AgentState`/`Execution`/`RuntimeEvent`，状态默认每 4 个 tick 写一次）。
- 他自己的评估（`docs/codex_notes/10/29-Ray架构满足度评估.md`）结论是："目前满足的只是有 100 个 Ray actor 的形式"。

### 1.3 我们原来的 100 个进程（`backend/agent_runtime/`）

Python 原生 `multiprocessing` 起的 100 个进程，不推进运动，只负责通过 HTTP 读写图谱：每 30 个模拟秒上报一次观测（写入 A 套 `WHAgentObservation`），每 30 秒查询一次本机上下文。服务端写入前的检查很完整，详见第 5 节。**这套将由 Ray 机器人进程取代**，其中有用的规则搬过去，多余的检查删掉。

## 2. 目标结构

每步循环：**派单 → 所有机器人并行推进 1 秒 → 主进程汇总 → 下一步。**

### 2.1 职责划分

| 职责 | 现在 | 拆分后 |
|---|---|---|
| 发布任务、派单、路线规划、交通预约、充电或换电位分配、电量准入、激活上限 | 主进程 | **主进程（不变）** |
| 机器人状态：位置、阶段、电量、当前任务、携带货物、当前计划、里程与时长计数 | 主进程 | **机器人进程（权威）**；主进程保留一份只读副本，每步更新，供派单使用 |
| 按计划推进 1 秒：定位、耗电、充电、阶段切换、计划连续性检查 | 主进程（运动计算部分已在 Ray） | **机器人进程** |
| 到达标记（取货、放货、交接等）的识别 | 主进程 | **机器人进程**：只报告"我走到了某个标记" |
| 标记的处理：改库存、货位、任务状态、进出口计数、接力配对 | 主进程 | **主进程（不变）**：按机器人编号顺序处理，需要改动机器人状态时，把修改指令发回对应进程 |
| 全体安全距离审计、全局不变量、统计 | 主进程 | **主进程（不变）**，用本步汇总上来的位置计算 |
| 本机记录写入（状态、执行、本机事件） | 主进程触发、actor 写入 | **机器人进程自己决定写什么、何时写** |
| 本机知识查询 | 我们的 HTTP 进程 | **机器人进程** |
| 全局记录（跨机协作如接力、全局统计） | 主进程（A 套） | **全局记录写入进程（lys）** |
| 页面推送、控制（开始、暂停、单步、倍速）、保存与恢复 | 主进程 | **主进程（不变）** |

一句话：**计划和全局状态归主进程，执行和本机状态归机器人。** 派单算法本身一行不动，这也是"调度结果不变"最可靠的保证。

### 2.2 每步的消息

```text
主进程                                         机器人进程（每台一个）
  │ 1. 默认内存副本 → release_and_dispatch()；neo4j 仅可选同步对照
  │ 2. 新计划/改道/取消 ──── assign(job) ─────────▶ 保存计划
  │ 3. 推进 ──────────────── advance(now) ───────▶ 按计划走 1 秒、耗电/充电
  │                                                │ 检查连续性，识别到达的标记
  │ 4. ◀──────────── StepResult ───────────────────┘
  │    {robot_id, tick, x, y, stage, battery, task_id, carrying,
  │     counters_delta, markers_reached, events}
  │ 5. 按机器人编号顺序处理标记；需要改机器人状态时 ── apply(patch) ──▶ 更新
  │ 6. 汇总：安全距离、不变量、统计；全局记录 ──▶ 全局记录写入进程
  │ 7. 推页面；到保存点时保存
```

- 运动推进中，第 3 步的 100 次 `advance` 并行发出，用一次 `ray.get` 收齐；图谱写入另在后台并行。
- 生产 memory 路径把完整状态与事件放入有界异步写入队列；允许图谱 Step 暂时落后。队满时暂停推进，等已有写入确认追平后继续。只有收齐 100 台真实落库成功回执才提交对应 Step，不能因排队成功就推进 latest_step。实现、短测和完整普通/重推基准已通过，全天待验收。`neo4j` 整场一致性对照保留每步同步写入、等 Step、再读取的路径。
- 第 5 步的 `apply` 只在标记处理改动了机器人本身时才发生：取货、放货、充满电时更新所在位置，换电时更新电量，交接时同时改两台机器人。这些都发生在走到标记的那一刻，不是每步都有。任务计划走完回到空闲，是机器人自己的状态变化，由机器人进程自行完成，主进程只需把它从 `jobs` 中移除。

## 3. 怎样保证调度结果不变

### 3.1 主要风险：同一步内的先后顺序

现在的 `step()` 是**按机器人编号依次**推进的。如果 3 号机器人在本步走到交接标记，`marker()` 会立刻修改 7 号机器人（交接对象）的状态，而 7 号在同一步里随后才推进，用到的是已经修改过的状态。改成并行之后，7 号的推进和 3 号的标记处理会同时发生，**顺序可能不同，结果就可能不同。**

处理办法：

1. 每步分两段：先让所有机器人只根据**本步开始时**的自身状态并行推进；再由主进程**按编号顺序**处理全部标记，把需要的修改发回去。
2. 逐项检查 `marker()` 的每种标记，对照"原来的顺序"是否会让同一步内后推进的机器人看到不同状态。已逐层核对 V2、V3、wide、轮式和知识层的 `marker()`：其余标记只改机器人自身（所在位置、换电后的电量）或全局状态（货位、库存、电池池）；**会改动另一台机器人的只有交接**（`handoff_received`：交货方卸下货物，如果是持续故障，还要断电隔离）。
3. 如果确有差异，再在那几种标记上保留"处理完再推进"的顺序。代价是那一步的并行度下降，但只在交接发生的那一刻。

## 4. 主进程从哪里读调度状态

最新决定：**生产默认从内存派单**（`--kg-state-source memory`）。每台 actor 仍维护自己的状态与计划，主进程使用推进结果和全局标记处理后的副本，沿用原 V5 派单。任务、库存、货位、交通预约继续留在主进程；上下文查询只观察，不参与派单。

`--kg-state-source neo4j` 保留为可选的整场一致性对照，采用旧同步路径：100 台写完后等 Step，读取精确 tick 的完整 payload，原位替换副本，再执行同一派单。现有 `kg_state.py` 的 2 秒等待与缺帧报错只属于这个显式对照模式，不再作为生产每步的门槛。

### 4.1 有界异步图谱写入（完整普通/重推通过，全天待验收）

每步的完整 19 字段 payload 和事件按顺序保留，由机器人写自己的 C 套子图；历史 AgentState 仍按原采样。推进完成和写入入队不等于落库确认。对应 `Step(t)` 必须在 100 台真实写入成功回执之后提交，由全局服务完成 Step 并更新 Run.latest_step。

队列有界；满时暂停物理推进、等待未完成写入确认追平，再继续。允许 latest_step 暂时落后当前物理步，并在页面显示差值。不能丢弃排队快照、伪造 complete 或把内存入队当成落库回执；永久写入失败仍需报告。

## 5. 机器人进程的读写

### 5.1 写什么：用 C 套标签

沿用他的 `backend/warehouse_runtime_graph.py`（`Robot`、`AgentState`、`Execution`、`RuntimeEvent`）。理由：这是他正在使用、正在开发的一套，结构本来就是按"每台机器人写自己的"设计的。

- 机器人进程每步写当前完整 payload；历史状态仍每 4 个 tick 采样，事件保留完整内容。主进程控制步进和统一收集回执。
- 主进程使用共用 `robot_graph_snapshots` 整理本步最终状态与事件；actor 通过 lys 的写入器写自己的子图，不另造写入协议。

### 5.2 从我们 100 个进程里搬过来的规则

| 规则 | 处理 | 原因 |
|---|---|---|
| 每台机器人只能读写自己的数据 | **保留** | 防止数据串到别的机器人名下；现在由"每台一个进程"这个结构天然保证，不再需要令牌 |
| 写入幂等：同一条记录重复写不会重复，同编号不同内容则报错 | **保留** | 重试时不会写出重复数据；用 Neo4j 的 `MERGE` 加唯一键实现 |
| 记录的模拟时间必须等于对应提交的时间 | **保留，但改为构造时保证** | 机器人进程的时间来自主进程的 `advance(now)`，不再需要写入前去数据库核对 |
| 查询时间口径清楚 | **保留，改为按时刻** | "最新"取每台机器人各自的最新状态并标出时刻；"某时刻"的所有部分都按该时刻限定；不再依赖全局提交编号（见第 6 节） |
| HTTP 令牌鉴权、请求字段白名单、单条 60KB 上限、事件种类白名单、事件数上限 | **删除** | 内部进程之间调用，不经过网络，没有外部输入 |
| 先写本地 SQLite 日志、再写 Neo4j 的两次写入 | **删除** | 双写是性能负担；改为直接写 Neo4j，失败就重试，写入幂等保证不会重复 |
| 查询排队名额与超时预算 | **简化** | 每台机器人同时最多一个查询，自然限流，只保留超时 |

### 5.3 读什么：机器人要真正读图谱

lys 现在的 `MotionActor` 只有运动计算和写图谱两个方法，**没有读图谱的方法**。图上"每台机器人查询知识"这一条，必须由机器人进程自己发起查询来满足；网页能查、压测工具能查，都不能替代机器人的调用。所以机器人进程要补上读取方法：查询本机最近的状态和事件、当前任务，以及附近机器人和接力相关的信息。具体查哪些，以实际被派单或决策用到的为准，不一次做全。

我们现有的查询服务（`backend/query_v2`）、压测工具和联合验收脚本查的都是 A 套。机器人改为读写 C 套以后，压测负载也要换成机器人实际执行的 C 套查询。A 套上测得的性能结果不能直接当作 C 套的验收，要在 C 套上重新测：数据规模、100 路并发、耗时。

在 C 套能满足实际查询之前，A 套（主进程每 5 秒写一份全仓库快照）继续保留，现有查询和压测不受影响。之后再停掉主进程的 A 套写入。

## 6. C 套的取舍与早期缺口

本节保留拆分前的调查例子与设计依据；交接、负责人、Step 和完整 payload 已按本文开头的实施表补齐。它不表示这些早期缺口仍然存在。机器人查询的实际接入和联合资格以最终验收报告为准。

### 6.1 原则：按项目需求补，不照搬 A 套的机制

项目真正需要的能力是：分清每次实验、每台机器人、每个任务和每件货；查得到机器人状态、任务执行和关键事件；记录货物从哪里到哪里、低电接力时由谁交给谁；重复上报不重复记账，写入失败能发现并补写；用机器人实际的查询，验证百万级数据和 100 路并发下的性能。

A 套里以下机制服务于它自己的实验设计，不是项目需求，**C 套不搬**：

- 全局提交编号（每次保存一个编号，所有查询都按编号查）；
- 每次保存都写一份全体机器人和全仓库的快照；
- 接力前先等整个图谱追平的检查；
- 再存一份机器人观测，逐字段和正式状态核对的流程。

库存历史如果需要，用"初始库存 + 取货、放货、交接事件"推出来，不必每次复制全仓库的货位状态。

### 6.2 拆分前 C 套的四个具体缺口（历史调查）

以下例子都来自同一次真实的低电接力：19 任务样本，在第 250 秒按实时服务的扰动配置把一台载货机器人的电量报告为 24%。

| 模拟时刻（秒） | 发生了什么 |
|---|---|
| 230 | 任务 `V3-T-0000012`（把货物 `V3-G-0787-0001` 从 `IN-1` 送到 `R17-L2-C3-F1`）派给 5 号 |
| 250 | 5 号在 `IN-1` 取到货 |
| 251 | 5 号报告电量过低，请求接力，系统为它预约接收方 |
| 282 | 5 号在路上把货交给 6 号 |
| 322 | 6 号放货，任务完成 |

#### 缺口一：交接双方丢失

仿真产生的交接事件原样是：

```json
{"kind": "cargo_handoff", "tick": 282, "robot_id": 6, "task_id": "V3-T-0000012",
 "goods_id": "V3-G-0787-0001", "location_id": "ROBOT-6",
 "donor_id": 5, "receiver_id": 6, "reason": "measured_low_energy"}
```

按现在的转换规则（`ray_medium/sim.py` 的事件转换、`warehouse_runtime_graph.py` 的 `_event_rows`），写进 C 套后只剩：

```json
{"type": "cargo_handoff", "tick": 282, "robot_id": 6, "task_id": "V3-T-0000012",
 "cargo_id": "V3-G-0787-0001", "slot_id": "ROBOT-6", "rack_id": null, "text": "cargo_handoff"}
```

`donor_id: 5`、`receiver_id: 6`、`reason: measured_low_energy` 都丢了，事件只挂在 6 号名下。问"这件货是谁交给谁的、为什么交"，答不出来。

改法：机器人侧保留事件的完整内容；交接作为跨机协作，由全局写入记录交货方、接收方、货物、任务和时刻。负责：机器人侧 wz，交接记录 lys。

#### 缺口二：历史查询混用了"之后"的状态

问"第 260 秒时 5 号在做什么"，`warehouse_graph_query.py` 的查询会返回：

| 部分 | 是否按"≤260 秒"限定 | 返回 |
|---|---|---|
| 机器人状态 | 是 | 第 260 秒：前往目的地，载着 `V3-G-0787-0001` |
| 事件 | 是 | 250 秒取货、251 秒请求接力 |
| 执行记录 | **否** | 任务 `V3-T-0000012`：**已完成，完成时刻 322** |

每个任务只有一条执行记录，状态会随事件不断被覆盖。同一个回答里，一边说"正载着货在路上"，一边说"这个任务 322 秒已完成"，还容易让人以为是 5 号完成的。

改法：执行状态也按时刻取，可以从状态变化事件推出，也可以给执行记录分版本。负责：他的查询由 lys 改，机器人自己的查询由 wz 按同一口径写。

#### 缺口三：写入失败后不会补写

第 282 秒，主进程把 6 号的快照（含交接事件）发给 6 号的 Ray 进程去写。`ray_medium/sim.py` 的执行顺序是：先把"已处理事件"的游标推到最新（第 92 行），再发出写入；写入失败时，错误只放进一个最多保留 20 条的列表（第 138～147 行）；第 283 秒只发送新事件。

如果这一刻写入失败（例如 100 个进程同时写导致锁等待超时），这条交接事件就**永远不会进入图谱**。6 号的位置会在第 284 秒的下一次状态写入时恢复，从图上看不出丢了东西；运行越久，错误列表也早已被挤掉。

改法：机器人进程保留未确认写入的批次，失败就重试；写入按唯一键合并，重试不会重复。负责：wz（第 3 阶段）。

#### 缺口四：分不清"现在归谁"和"谁参与过"

每个任务一条执行记录。每次写入时，哪台机器人身上带着这个任务，就加一条"派给"关系（`ASSIGNED_TO`），只增不删（`_WRITE_EXECUTIONS`）。230～281 秒带着任务的是 5 号，282 秒以后是 6 号，所以最终执行记录同时连着 5 号和 6 号，两条关系没有先后，也没有"当前"的标记。

问"这个任务现在归谁"，得到两台机器人；问"5 号做过哪些任务"，会返回 `V3-T-0000012`、状态"已完成"，按此统计每台机器人的完成数，5 号和 6 号会各算一次。执行记录上的 `robot_node_id` 字段每次写入都被覆盖，最后停在 6 号，实际已能表示当前负责人，只是查询没有用它，含义也没有约定。

改法：约定"派给"关系表示历史参与，`robot_node_id`（或改名为当前负责机器人）表示当前负责人，交接时更新；查询按需选用。负责：双方约定，lys 改写入。

### 6.3 查询口径：用每步的 `Step` 节点作完成标记

100 台机器人各自写入，刚过第 t 步时查"最新时刻的全部机器人"，可能只有一部分写到了第 t 步。

推荐做法与 LaDe 相同：**每一步，100 台机器人写完并回执之后，全局记录写入进程写入一个 `Step(t)` 节点**，记录这一步的全局摘要（在线数、作业数、完成数、低电数等）。查询以"最新的 `Step`"为准：只要 `Step(t)` 存在，第 t 步的机器人状态和事件就一定已经写全。

全局写入在同一个事务里更新 `Run.latest_step = t`，查询通过它直接定位最新的 `Step`。原型发现，用 `ORDER BY tick DESC LIMIT 1` 找最新 `Step` 会对全部 `Step` 逐个扫描，耗时随运行时间线性增长（1 万个时已 49ms）；改为读 `Run.latest_step` 后为 2.9ms。同理，"近期"类查询都要给时间范围加下界（例如最近 400 秒），否则会读出该机器人的全部历史。

这其实就是一种每步的完成标记，但比 A 套的全局提交机制轻得多：每步只写一个节点，不需要把所有数据汇总到中心统一提交，也不阻塞机器人写入。它又正好落在全局记录写入进程"全局统计"的职责里。

其他可选做法及其不足，供对照：

| 做法 | 怎么做 | 不足 |
|---|---|---|
| 各取最新 | 每台取自己的最新状态并标出时刻 | 不同机器人时刻可能不一致，只适合实时展示 |
| 低水位 | 每台机器人记录 `last_written_tick`，查询取最小值 | 每次查询都要扫 100 个节点；与 `Step` 节点作用重复 |
| 延后查询 | 只查"现在往前 k 秒" | 写入卡住时仍可能不全 |
| A 套全局提交点 | 中心进程统一事务提交并编号 | 写入都要汇总到中心，与拆分目标相反 |

### 6.4 和全局记录写入进程的分界

按图上的设计，全局记录写入进程只做两件事：

| 记录 | 谁写 |
|---|---|
| 单台机器人的状态、执行过程、本机事件（阶段变化、充电、低电观测、取放货） | 机器人进程（wz） |
| 跨机协作：低电接力的配对与交接（交货方、接收方、货物、时刻） | 全局记录写入进程（lys） |
| 每步完成标记 `Step(t)`：本步的全局摘要，在 100 台机器人回执之后写入（见 6.3） | 全局记录写入进程（lys） |
| 全局统计（在线数、完成数、晚点等） | 全局记录写入进程（lys） |

主进程在处理完标记、做完汇总之后，把这两类记录交给全局记录写入进程，具体格式由双方约定。

### 6.5 图谱查询面向谁：每个 Agent 的决策上下文

按 LaDe 的原设计，"100 个 Agent 并发查询"指的是**每个 Agent 并发取回自己的决策上下文**：自身状态与能力、任务进展、近期记忆、局部协作候选、能量风险、数据新鲜度，按任务决策、能量安全、请求帮助、提供帮助、恢复等场景分包。在 LaDe 中，这些上下文的消费者是 LLM 决策层；文档也注明这套查询当时并未自动接入实时调度。

本项目不实现 LLM，因此：

1. **必做**：机器人进程真实、并发地取回自己的决策上下文（查 C 套），在百万节点规模上测延迟。这就是原始指标"100 Agent 并发查询 < 500ms"的测法。我们现有的查询目录（self、energy、assistance、memory、progress）与 LaDe 的上下文查询同源，只是查的是 A 套，需要改为查 C 套。
2. **暂缓**：决策上下文接入规则调度。本轮只记录真实查询耗时和结果条数，不改变派单结果。

查询结果还服务于人（知识图谱页面、演示）和事后分析，它们对实时性要求低，不作为验收主体。

## 7. 性能预期与需要实测的点

现在每个 tick 的耗时（medium 1728 任务、50 台激活）：仿真步进平均约 56ms，发布帧约 22ms；保存每 5 个模拟秒一次，约 1 到 2 秒。

拆分后新增的开销：

- **每步 100 次 Ray 调用。** 他现在的版本每步已经在做 100 次调用，但还没有单独测量过往返耗时。动手前先量出来。
- **主进程副本的更新。** 每步收到 100 份 `StepResult`，开销很小。
- **本机写图谱。** 不在关键路径上，但 100 个进程同时写 Neo4j 时，数据库本身的负载要单独看。他之前遇到过 100 个进程同时写 `Run` 节点引起锁竞争，已改为由主进程启动时写一次。

**原型实测结果**（详见 [`KG_PROTOTYPE_MEASUREMENTS_20261030.md`](KG_PROTOTYPE_MEASUREMENTS_20261030.md)）：用 100 个独立进程模拟 100 台机器人，该运行约 110 万节点：

| 环节 | 均值 | P95 / P99 |
|---|---|---|
| 每步 100 路并发写入（每台一个事务） | 83ms | P95 150ms |
| `Step(t)` 写入 | 13ms | — |
| 主进程读回 100 台状态 | 17ms | 最大 92ms |
| 每步总耗时 | 119ms | P95 212ms |
| 每个机器人取回决策上下文（6 条） | 21ms | P99 49ms |

派单结果与读内存逐条一致。17,800 次上下文取回中有 28 次超过 500ms（0.16%），与一次约 5 秒的 Neo4j 检查点重合。合并写入（每步一个事务）约为逐台写入的一半耗时（43ms 对 86ms，4.6 万规模）。Neo4j 的连接线程池需要足够大（原型用 256；wz 原实例只有 32，会报 `NoThreadsAvailable`）。

可能的收益：推进 1 秒的计算分散到 100 个进程，但这部分本来就不重，现在的瓶颈主要是派单尖峰和保存，拆分本身**不会**让仿真变快。拆分的目的是符合目标架构，而不是提速。这一点要说清楚，免得双方对效果有不同预期。

### 2026-10-31 演示积压预算

实时服务和全天实验的 `--robot-graph-backlog N` 默认改为120，仍限制为1～128，包含正在处理的frame。
启动脚本也支持 `ROBOT_GRAPH_BACKLOG=8` 覆盖；显式8可复现今天仍在运行的旧实验。改默认不改变已有进程。
120用于吸收短时写入波动，减少演示频繁进入背压；它不提高数据库持续吞吐量。写入持续跟不上时仍会填满，暂停新物理步并排空后继续；所有已接收快照按FIFO保留，Step仍要100台真实写入回执。
代价是更多内存、更大的图谱可见延迟，以及满队列后可能更长的一次追平暂停。页面应结合当前lag判断；需要更紧的可见延迟时显式设8。
8/120的400步真实对照已在原SSD全天自然结束后通过，401个Step各100回执、业务事实一致，两个新运行清理残留0。暂停与尾部追平耗时见最终验收报告；复现用 ops/kg_backlog_compare.py。
